# Aegis 的时间语义与输出契约

本文说明 Aegis 的两类硬边界：研究数据"代表哪个时间点"（时间语义），以及 Agent 最终产出必须满足的结构（输出契约）。前者解决"用哪天的数据判断当前状态"，后者解决"判断结果如何被确定性校验与下游消费"。文中形态以仓库已实现的代码为准。

---

## 1. 时间语义

### 1.1 `as_of` 的定义

`as_of` 是**本次研究实际用于判断的数据日期**，格式 `YYYYMMDD`。

- 它不是程序运行时间，也不是请求发起时间；
- 目标时间由任务语义决定，可能是当前有效交易日，也可能是明确的历史日期或区间；
- `as_of` 只记录最终真正被采用的那份数据所代表的日期。

例如运行时钟是 `2026-09-23`、当日日频数据尚未完整时，研究应采用最近一个数据完整的交易日，`as_of` 填 `20260922` 而不是 `20260923`。

### 1.2 五条时间规则

`internal/agent/market/prompt.go` 的 `instruction` 原文约束如下：

```text
时间规则：

1. 首先确定本次研究对应的目标时间。
2. 所有具有时间属性的数据应尽量使用一致的时间基准。
3. 如果当前交易日数据尚未完整，应使用最近一个数据完整的交易日。
4. as_of 必须填写实际用于判断的数据日期。
5. 不得把明显过期的数据当成当前市场状态。
6. 如果关键数据无法获得，应在 risk 中明确说明，不得编造。
```

| 规则 | 含义 | 违反后果 |
|---|---|---|
| 1. 首先确定目标时间 | 取数之前先判断时间意图（当前状态 / 指定历史日期 / 时间区间），再决定数据范围 | 先用工具默认区间取数，再拿旧数据解释"当前" |
| 2. 一致的时间基准 | 同一份判断所引用的数据尽量落在同一时间基准上 | 把不同时点的数据当成同一时点的证据比较 |
| 3. 允许退到最近完整交易日 | 当日数据尚未完整（未收盘、数据源未更新）时，可使用最近一个数据完整的交易日 | 用不完整数据冒充完整交易日 |
| 4. `as_of` 如实填写 | `as_of` 记录实际采用的数据日期 | `as_of` 与证据数据日期不一致，契约失真 |
| 5. 不得把过期数据当当前状态 | 明显偏早的数据不能用于描述当前市场 | 用数月前的行情得出"当前市场"判断 |

第 6 条不属于时间基准，而是数据缺失的处理方式：拿不到关键数据必须在 `risk` 中说明，不得编造。规则 1 与规则 3 合起来意味着"当前市场分析"可以合法地得到非运行日的 `as_of`。

### 1.3 核心原则：测试必须适配语义

**时间由任务语义决定，不能为了让测试通过而改写语义。**

这条原则源于一次真实故障：运行时间 `2026-09-22`，任务为"分析当前 A 股市场环境"，实际返回 `as_of = 20260122`，与目标时间相差约 8 个月。这不是"数据旧"的措辞问题，而是 `Temporal Intent = CURRENT` 与实际数据时间不一致的语义错误。

一种直觉式修法是在 `Validate` 中加：

```go
// 反面做法
if analysisTime.Sub(asOf) > 7*24*time.Hour {
    return errors.New("as_of is too stale")
}
```

它被否定的原因是：合法的历史研究（"分析 2026 年 1 月 22 日的市场环境"）必然超过 7 天，会被直接判错。同类错误做法还有把 `as_of` 写死成某个常量以匹配断言，以及强制 `as_of = Now`，让当前时间覆盖历史语义。

| 维度 | 错误做法（语义适配测试） | 正确做法（测试适配语义） |
|---|---|---|
| Validator | 加 `Now - as_of <= N 天`，或强制 `as_of == Now` | 只校验结构：`as_of` 非空、`regime` 合法、`confidence` 范围、`evidence` 非空 |
| Prompt | 把"当前"固定映射为运行日 | 由任务语义解析目标时间与时间范围 |
| 集成测试 | `if result.AsOf != "20260922" { t.Fatal(...) }` | `result != nil`、`result.AsOf != ""`、`len(result.Evidence) > 0` |
| 时间来源 | 把时间写死成常量以便断言 | 运行期由 Runtime Context 提供；单测注入可控时钟 |
| 结果 | 历史任务被误杀，或测试通过但语义错误 | 语义与数据一致，测试不随日历漂移 |

需要区分的是：**单测中对假模型（fake model）使用固定时间与固定输出是允许的**。假模型不参与语义判断，固定输出只用于验证 JSON 解析与结构校验的可重复性。被禁止的是在集成测试里硬断言 `as_of` 等于某一天，以及为迁就测试而修改生产侧的时间语义或 Validator 判定范围。

### 1.4 时间注入机制

时间不作为业务参数传入 Agent，`Analyze` 保持自然签名：

```go
func (a *Agent) Analyze(
	ctx context.Context,
	query string,
	opts ...adk.AgentRunOption,
) (*Context, error)
```

"现在是几点"属于运行环境事实，由 Harness 通过 Middleware 注入。时区以 IANA 名称配置（A 股取 `Asia/Shanghai`），`internal/runtime/runtime.go` 已声明该配置项：

```go
type Config struct {
	SkillsDir string
	TimeZone  string
}

type Runtime struct {
	handlers []adk.TypedChatModelAgentMiddleware[*schema.AgenticMessage]
}
```

时区**不硬编码在 Middleware 内部**：Middleware 只接受 `*time.Location`，由组装方决定取值，因此同一套 Middleware 可复用于不同市场（A 股 `Asia/Shanghai`、美股 `America/New_York`、加密市场 `UTC`）。

`internal/runtime/time_context.go` 的完整实现：

```go
package runtime

import (
	"context"
	"fmt"
	"time"

	"github.com/cloudwego/eino/adk"
)

type ContextMiddleware[M adk.MessageType] struct {
	*adk.TypedBaseChatModelAgentMiddleware[M]

	location *time.Location
	now      func() time.Time
}

func NewContextMiddleware[M adk.MessageType](location *time.Location) *ContextMiddleware[M] {
	return &ContextMiddleware[M]{
		TypedBaseChatModelAgentMiddleware: &adk.TypedBaseChatModelAgentMiddleware[M]{},
		location:                          location,
		now:                               time.Now,
	}
}

func (m *ContextMiddleware[M]) BeforeAgent(ctx context.Context, runCtx *adk.ChatModelAgentContext) (context.Context, *adk.ChatModelAgentContext, error) {
	now := m.now()
	if m.location != nil {
		now = now.In(m.location)
	}

	runCtx.Instruction += fmt.Sprintf(`
# Runtime Context

The following values are runtime facts provided by the Aegis Harness.

- current_time: %s
- timezone: %s

Rules:

- Treat current_time as the actual runtime clock, not as the target time of the user's research request.
- Determine the target research time from the user's language and intent.
- Relative expressions such as "当前", "今天", "最近", "昨天" may use current_time as their reference.
- Explicit historical dates or ranges must remain historical and must not be replaced by current_time.
- Domain-specific time decisions, such as trading days, market sessions, data completeness, and latest available market data, must be determined using the appropriate Skill or tools.
`, now.Format(time.RFC3339),
		now.Location().String())

	return ctx, runCtx, nil
}
```

`BeforeAgent` 执行后，Agent 的 Instruction 尾部会追加一段运行环境事实，形如 `# Runtime Context` / `current_time: 2026-09-23T13:10:00+08:00` / `timezone: Asia/Shanghai`。关键点：

- 通过嵌入 `*adk.TypedBaseChatModelAgentMiddleware[M]` 获得 Middleware 默认行为，只覆写 `BeforeAgent`。
- `now func() time.Time` 是可替换时钟源，默认 `time.Now`；测试可替换为固定时钟以获得可重复结果，而无需改动业务语义。
- 在**每次 Agent Run 开始时采样一次**，追加到 `runCtx.Instruction`。当前单次 `Analyze` 约数十秒，采样一次已足够；将来出现长时间会话或异步等待任务，再考虑 per-step 刷新。
- `location == nil` 时保持采样到的原始时区，不做转换。

注入只提供客观事实，不替 Agent 解释语义；领域时间判断交给 Skill 与工具。三者分工：

| 层 | 负责 | 不负责 |
|---|---|---|
| Runtime Context（`ContextMiddleware`） | 提供 `current_time`、`timezone` 客观事实 | 解释"当前/今天/最近"；判断交易日与数据完整性 |
| Market Agent（Prompt 时间规则） | 按任务语义确定目标时间或时间范围；如实填写 `as_of` | 依据模型自身知识猜测当前日期；把运行时间直接当作 `as_of` |
| Skill / Tool | 交易日历、交易时段、数据更新时间与完整性、最新可用数据 | 决定本次研究的目标时间 |

链路为单向：Runtime Time（环境事实）→ Temporal Intent（Agent 按语义解析）→ Target Market Time → Data Time（Skill / Tool 结合交易日历与数据可用性确定）→ `MarketContext.AsOf`。Runtime 与 Validator 都不决定目标时间。

### 1.5 时间相关的错误处理

时间相关的失败分为两类，处理方式完全不同：

- **`as_of` 缺失属于结构非法**：由 `Validate` 直接报错，`Analyze` 返回 error，不产出 `Context`。
- **数据拿不到属于业务事实**：不报错，写入 `risk` 字段如实说明，绝不允许编造或拿旧数据替代。

`internal/agent/market/validator.go` 是前者的实现：

```go
func Validate(v *Context) error {
	if v == nil {
		return errors.New("market context is nil")
	}

	if v.AsOf == "" {
		return errors.New("as_of is required")
	}

	switch v.Regime {
	case RegimeRiskOn, RegimeMixed, RegimeRiskOff:
	default:
		return fmt.Errorf("invalid regime: %s", v.Regime)
	}

	if v.Confidence < 0 || v.Confidence > 1 {
		return fmt.Errorf("confidence out of range: %f", v.Confidence)
	}

	if len(v.Evidence) == 0 {
		return errors.New("evidence is empty")
	}

	return nil
}
```

`Validate` **不判断 `as_of` 是否足够新、是否等于最近交易日、是否等于运行日**——这些是语义问题，不属于结构合法性。

| 维度 | 结构合法性校验 | 数据完整性 |
|---|---|---|
| 执行者 | `Validate`（`internal/agent/market/validator.go`、`internal/decision/decision.go`） | Agent 判断，结论写入 `risk` |
| 判定对象 | 字段是否存在、枚举是否合法、数值范围、必需数组是否为空 | 数据是否真的取到、是否过期、是否相互冲突 |
| `as_of` 缺失/为空 | 结构非法，返回 `as_of is required` | — |
| 数据拿不到 | 不报错 | 写入 `risk`，明确说明缺失，不得编造 |
| 失败后果 | `Analyze` 返回 error，不产出 `Context` | 正常产出 `Context`，但降低 `confidence` 并在 `risk` 中说明 |
| 修复方式 | 修正 Prompt 约束、修正解析、重新生成 | 继续调用工具、换数据源、如实披露缺失 |
| 典型反例 | 校验 `Turnover > 0`、`len(Indexes) > 0` | 用旧数据凑出"当前市场" |

设计理由：`Validate` 只判定"是否按 Aegis 的协议输出了一个合法结构"，不判定结论对不对。结论正确性属于 Agent 的研究判断，Go 侧不做业务裁决；拿不到数据应进入 `risk`，不能逼 Agent 编数据。

### 1.6 数据冲突的处理要求

不同工具或数据源的结果彼此冲突时（例如技术指标与日线收盘价不在同一时间基准，或消息面与价格走势矛盾），要求：

1. **必须明确指出冲突**，写入 `risk` 或 `evidence`，不得静默择一。
2. **降低 `confidence`**，冲突越实质性，下调越明显。
3. **优先重新获取匹配时间范围的数据**；仍无法获得时，明确说明数据时间不一致或数据缺失。

Prompt 中的对应约束：

```text
如果不同工具返回的数据存在冲突，必须明确指出冲突，并降低判断置信度。

不得将不同时间基准的数据直接当作同一时点的数据进行比较。
如果工具返回的数据与本次任务的目标时间范围不一致，应优先重新获取正确时间范围的数据。
如果无法获取符合目标时间范围的数据，应明确说明数据缺失，不得使用无关或过期数据替代。
```

正确行为序列：数据时间与目标时间不一致 → 不得用于本次判断 → 重新调用工具并传入正确时间范围 → 仍拿不到则在 `risk` 中说明缺失或时间不一致 → 降低 `confidence`。

## 2. 输出契约

### 2.1 结构化输出的必要性

Agent 最终不能返回大段自由文本，必须形成明确的 `Decision` / `Context` 结构。理由有二：

1. **确定性校验**：字段化之后，Go 侧才能确定性地检查枚举值、数值范围与必需数组，给出明确的通过/失败结论。
2. **下游消费**：结构化对象可被程序直接解析、存储与组合，自由文本不能。

由此确立边界：**LLM 负责判断（判断什么、调哪些 Tool、如何解释），Go 负责契约（格式是否合法、字段是否合法、数值是否合法）。** Market Agent 的 `Analyze()` 拿到输出后立即解析并校验：

```go
result, err := parseContext(output)
if err != nil {
	return nil, err
}
```

### 2.2 JSON 输出的完整要求

- 最终输出必须是**合法 JSON**（Market Agent 为单个 JSON object）。
- **不要使用 Markdown 代码块包裹**。
- **不要在 JSON 前后添加任何文字**。
- `evidence` 与 `risk` **必须是 JSON 数组**，即使只有一项；**禁止**输出为单个字符串。
- 不得输出 JSON 之外的任何内容。

数组要求必须显式写进 Prompt，因为"合法 JSON"不等于"符合契约"：模型可能输出 `"risk": "主要风险是……"`，语法合法但违反字段类型契约。因此 Prompt 同时给出类型声明与正确示例：

```text
evidence 和 risk 必须始终输出为 JSON 字符串数组。
即使只有一条 evidence 或 risk，也必须使用数组，不能输出为单个字符串。

正确示例：
{
"symbol": "600519",
"market_view": "当前短线状态判断",
"evidence": ["证据1", "证据2"],
"risk": ["风险1", "风险2"],
"action": "WATCH",
"confidence": 0.6
}
```

Decision 字段类型：

| 字段 | 类型 | 约束 |
|---|---|---|
| `symbol` | string | 股票代码，必填非空 |
| `market_view` | string | 当前市场/短线状态判断，必填非空 |
| `evidence` | string[] | 支持判断的主要证据，必须是数组且至少一项 |
| `risk` | string[] | 当前主要风险，必须是数组（允许为空数组，但不得输出为字符串） |
| `action` | string | 只能取 `WATCH` / `AVOID` / `CANDIDATE` |
| `confidence` | number | 必须落在 `[0, 1]` |

`action` 语义固定为：`WATCH` 继续观察、`AVOID` 当前不考虑、`CANDIDATE` 进入短线候选池；不输出 `BUY` / `SELL`。对应结构体：

```go
type Decision struct {
	Symbol     string   `json:"symbol"`
	MarketView string   `json:"market_view"`
	Evidence   []string `json:"evidence"`
	Risk       []string `json:"risk"`
	Action     Action   `json:"action"`
	Confidence float64  `json:"confidence"`
}
```

Market Agent 另有市场上下文契约 `market.Context`，字段为 `as_of`、`regime`、`indexes[]`、`advance_count`、`decline_count`、`limit_up_count`、`limit_down_count`、`turnover`、`leading_sectors[]`、`evidence[]`、`risk[]`、`confidence`，其中 `regime` 只能取 `RISK_ON` / `MIXED` / `RISK_OFF`。契约中应尽量避免隐含单位：`turnover` 采用统一的基础货币单位数值（CNY），而不是需要靠自然语言猜测"亿元"的裸数字。

### 2.3 DeepSeek 的 JSON 模式配置

模型侧启用 DeepSeek 的 JSON Output，而不是在 Go 侧截取 `{...}`：

```go
return agenticdeepseek.New(
	ctx,
	&agenticdeepseek.Config{
		APIKey:  apiKey,
		BaseURL: cfg.BaseURL,
		Model:   cfg.Model,

		ResponseFormatType: agenticdeepseek.ResponseFormatTypeJSONObject,
	},
)
```

`agenticdeepseek.ResponseFormatTypeJSONObject` 的底层取值为 `"json_object"`；同一类型下仅有 `"text"` 与 `"json_object"` 两个值。

它解决的问题是：模型在最终 JSON 之前插入自然语言，导致从第一个字符开始解析就失败。典型故障输出为 `I'll gather the necessary data for 600519.{"symbol":"600519", ...}`，对应错误为 `invalid decision JSON: invalid character 'I' looking for beginning of value`。启用后 API 直接返回 JSON 对象，边界变为 `DeepSeek → JSON Mode → 合法 JSON 字符串 → json.Unmarshal → Validate()`，而不是"任意文本 → 猜测哪里是 JSON → 截取 `{}`"。

需要注意 JSON 模式的保证范围：它**只保证返回一个合法 JSON 对象，不保证字段类型符合 Go struct**——当前 `agenticdeepseek` 只提供 `text` 与 `json_object` 这类 JSON Mode，没有 JSON Schema 级别的 strict structured output。因此 `json.Unmarshal` 失败或字段类型不匹配是该模型组合下必须考虑的**正常边界**，结构化约束仍需 Prompt 与 Validator 共同承担。

### 2.4 校验与修复策略

Validator 在 `Analyze()` 内部执行，形成单一校验入口。`Analyze()` 只保留 Agent Loop 的最后一个有效 assistant 输出（中间轮次可能是 Tool Calling 内容），随后交给 `parseContext`：

```go
func parseContext(raw string) (*Context, error) {
	raw = strings.TrimSpace(raw)

	if raw == "" {
		return nil, errors.New("market context output is empty")
	}

	var result Context

	if err := json.Unmarshal([]byte(raw), &result); err != nil {
		return nil, fmt.Errorf("invalid market context JSON: %w: output=%q", err, raw)
	}

	if err := Validate(&result); err != nil {
		return nil, fmt.Errorf("invalid market context: %w", err)
	}

	return &result, nil
}
```

完整输出边界：Agent 最终 assistant 输出 → `TrimSpace` → `json.Unmarshal`（失败返回 `invalid market context JSON`）→ `Validate`（失败返回 `invalid market context`）→ `*Context`（可信的内部对象）。

校验失败的处理方式按层次划分，优先级从高到低：

1. **Prompt 层约束**：明确声明字段类型（`string[]`）、枚举取值与数值范围，并给出正确示例。成本最低的第一道防线。
2. **模型层约束**：启用 `ResponseFormatTypeJSONObject`，保证输出是 JSON 对象而非"自然语言 + JSON"。
3. **Go 边界层校验**：`json.Unmarshal` 加 `Validate`；失败即返回 error，调用方不得消费结果。

当前实现中，校验失败**直接返回 error，不做自动修复**。设计上曾考虑一次性 Repair：把"不符合 schema"的反馈回传给模型，要求**仅修正 JSON 结构、不改变分析结论与内容**（例如把 `"risk": "风险A；风险B"` 改为 `"risk": ["风险A", "风险B"]`），最多修复 1 次，再失败即报错，且 Repair 不重新执行数据获取与研究。该策略尚未在代码中实现，属于已确定方向的后续加固项。无论是否引入 Repair，边界不变：**LLM 可以犯格式错误，Aegis 绝不接受不符合契约的结果。**
