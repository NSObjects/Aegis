>
> **权威约束**：[10-多Agent架构与职责边界.md](10-多Agent架构与职责边界.md) 优先于本文件；当前功能收尾沿用 [MULTI_AGENT_ROADMAP.md](MULTI_AGENT_ROADMAP.md) 的 F0～F4；具体实现由后续 Issue/ADR 决定。本路线图是产品方向、依赖、范围、验收和优先级的统一索引，不是实时完成状态。

## 0. 本次讨论确定的需求（不得在开发中遗失）

1. **先完成已有多 Agent 内核的 V1 水准**：在真实数据、真实模型下跑通从研究、辩论到 Risk/Portfolio 的闭环；不要重复写已有 Analyst 或因非阻塞细节无限延后交付。
2. **实际使用入口是 Web，不是 CLI**：CLI 留给开发/测试；最终用户在页面操作任务、阅读报告、研究组合。
3. **对话是 Web 的一等交互方式**：用户可以自然语言发起研究、追问多空争议、比较历史结论、分析仓位；不是等整个 Dashboard 完工才「再加聊天页」。
4. **仓位管理重要，但不是一套写死的三三制**：底线采用确定性风控，基础计算随市场风险与账户预算变化，后续通过同口径回测比较三三制、固定比例、波动率等政策。
5. **研究需要连续性，不只是记住聊天**：行情/财报/新闻由独立数据流程写入；Memory 重点保存 Agent 曾做出的判断、假设、错误、反思与后续验证，能长期跟踪一个标的。
6. **不仅被动回答，还能主动发现机会**：策略选股、观察池、异动/公告监控、增量复查、定期报告。
7. **研究结果必须可证伪**：同一数据、信号与费用假设下比较策略，不因模型自称有信心就提高仓位，也不因为某次预测碰巧对就宣称策略有效。
8. **面向持续开发**：每个阶段有清晰用户场景、最小可运行交付物、正反例验收与回退边界；开发时核对最新 main，不按过期的路线图盲目造轮子。

## 1. 产品最终形态：研究工作台，而非「带图表的 CLI」

### 1.1 主要用户操作闭环

~~~text
用户打开 Aegis Web
    │
    ├─ 对话：「研究 600519.SH，最近有什么变化？」
    │          ↓
    │    Conversation / Tool Router
    │          ↓
    │    Research Task → Existing Multi-Agent Workflow
    │          ↓
    │    事实与证据 → 多空辩论 → ResearchPlan → TradeIntent
    │          ↓
    │    Risk / Portfolio → 研究性仓位情景（数据足够时）
    │          ↓
    │    页面展示实时进度、引用、结构化研究报告
    │
    ├─ 页面：股票详情、市场、组合、观察池、历史报告
    ├─ 追问：「空头的证据是什么？与上周相比呢？」
    ├─ 管理：研究任务、观察条件、风险配置、策略假设
    └─ 持续：新数据 → 触发复查 → 比较新旧研究 → 结果验证
                                            ↓
                                     研究记忆/策略验证
~~~

每条研究都需有独立标识、研究截止时间、来源、产物版本。**会话只是操作和解释方式，研究记录才是事实与结果载体**。

### 1.2 典型场景与系统动作

| 用户动作 | 正确行为 | 不允许的行为 |
| --- | --- | --- |
| 「分析贵州茅台现在适合参与吗？」 | 明确时点；提交或查询有效研究任务；按真实来源研究并给出论点/风险 | 只凭聊天记忆编今天的行情 |
| 「刚才为什么偏空？」 | 从同一 run 的 Bear/Manager 与证据引用回答 | 再造一个未验证的空头理由 |
| 「和上周相比有什么变化？」 | 对齐两个研究快照的日期、数据口径，标记新证据/失效结论 | 直接比较两个无来源的自然语言摘要 |
| 「市场变弱，我的仓位应该怎样？」 | 调用组合风控与情景计算；确认账户快照/预算/止损假设 | LLM 凭感觉报 60% 或批准交易 |
| 「扫描上升趋势回踩股票」 | 用确定性规则先形成候选，再调用深度研究 | 全市场逐只调用 LLM 筛选 |
| 「之前哪些判断错了？」 | 从历史论断及后续观察得出有出处的归因 | 在没有后验数据时写虚构复盘 |

### 1.3 一致的交互理念

- **聊天和可视化共用一份研究状态**：聊天里产生的 ResearchRun 应出现在研究列表；页面选中的 symbol/run 可成为对话上下文；两种入口不产生不同结论。
- **用户可以深入查看过程，也能只看结果**：支持摘要、市场/技术/基本面/事件、多空辩论、证据链、风险、组合情景逐层展开。
- **相同的动作既能通过按钮触发也能经工具路由触发**。自然语言只是可选快捷入口，不取消明确的结构化控制。
- **失败/数据不足是正常的产品状态**：必须解释缺失哪些输入、能重试什么、哪些结论尚不可计算。

## 3. 实施方法：核心依赖与可并行工作

不再把功能硬排成 18 个必须串行执行的 PR。采用 **短期主交付线 + 小范围并行的独立能力线**。

| 里程碑 | 用户可得到什么 | 必须依赖 | 是否允许与其他阶段并行 |
| --- | --- | --- | --- |
| **M0 核心研究收口** | 完整多 Agent 研究、风险审查有可复现真实结果 | 现有 F0～F4 | 当前唯一主线 |
| **M1 可用 Web + 基础对话** | 不用 CLI 发起研究、实时查看、追问、回看结果 | M0 + 最小服务/任务 API | 与 M2 的独立领域计算可并行 |
| **M2 组合仓位 V1** | 有账户/预算时获得确定性目标仓位与风险解释；未知时明确不计算 | M0 + 现有 Portfolio 契约 | 可与 M1 前端/API 并行；不阻塞最小 Web |
| **M3 研究历史与发现入口** | 自选池、历史对照、单策略候选筛选、列表转研究任务 | M1 + 可查询运行记录 | 与 M2 后续优化可并行 |
| **M4 主动研究与假设跟踪** | 价格/公告变化触发复查，能判断原假设是否仍成立 | M3 + 可靠数据/任务调度 | 与离线评估基础可并行 |
| **M5 持续研究 Memory/反思** | 追踪过去做过什么判断、错在哪里、哪些经验值得保留 | 历史产物 + 可验证假设/后验观察 | 可与 M4 增量演进 |
| **M6 策略与仓位验证进化** | 离线回测、样本外验证、不同仓位政策比较 | 可版本化策略、历史 PIT 数据、研究输出 | **最小回放/校验在 M2 就开始**，复杂验证不必等所有 Memory 做完 |

阶段编号表达**交付目标**，不是仓库 Go 模块版本号，也不预示具体日期。M1、M2 可以在 M0 完成后双线推进；基础仓位功能未完全扩展时，Web 可先展示现有 Risk/Portfolio 和 What-if，不虚构目标仓位。

## 5. M1 — Web 研究工作台 + 基础 Conversation Agent（P0）

### 5.1 先做一条真实的纵向用户路径

不先造复杂页面和独立聊天平台。先完成：

~~~text
Web 输入：「研究 600519.SH」
      ↓
Go API 创建 ResearchRun（run_id）
      ↓
统一 Application Service 调用现有 Aegis Workflow
      ↓
任务阶段事件（存储 + SSE）和 Artifact
      ↓
Web 展示运行情况、研究结论、证据和失败原因
      ↓
对话追问：「刚才空头的三个核心理由是什么？」
      ↓
Conversation Tool 读取同一 run_id / Debate Artifact
      ↓
回答附结构化来源，不重新完整运行研究
~~~

达到这条端到端路径后再扩展其它页面和工具。

### 5.2 最小 API/任务基础

- Go Application Service 是唯一研究调用入口；CLI / REST / Conversation / 未来 Scheduler 共用此接口，不复制编排逻辑。Eino Workflow 保持在既有核心层。
- 基础对象：ResearchRun（run_id、symbol、requested_as_of、状态、配置/版本、错误阶段）；StepEvent（角色/状态/序号）；Artifact（结构化结果与来源）；ConversationMessage（session_id、role、run_id/引用）。
- 最小操作：创建研究任务、查询任务/报告、按序读取阶段事件、列出历史、读取研究产物、读取组合情景。实现接口前再定具体 URL/Schema，不在路线图里冻结未经评审的 API 路径。
- 长时间研究与 HTTP 请求解耦；支持异步执行、超时、取消、SSE 重连、幂等性、错误状态和服务重启后的历史访问。
- 数据存储应有最小持久化和迁移；M1 不要求分布式队列、完整多租户平台或大型基础设施。具体选型经 ADR 验证再定。
- 模型与数据源密钥仅在服务端；合理鉴权、账户隔离、输入校验与日志脱敏。单人部署不等于公开端点没有安全风险。

### 5.3 Web 第一版信息架构

**主要工作区（优先上线）**：左侧导航/会话列表，中间聊天与结构化研究面板，右侧（可折叠）展示 Agent 阶段、证据与当前标的/运行。手机或小屏改为切换视图，不强制三栏。

逐步补齐：

| 页面/视图 | 可用能力 | 首期优先级 |
| --- | --- | --- |
| Research Workspace + Chat | 触发研究、实时阶段、报告、证据引用、在同一 run 上追问 | 必须 |
| Research History | 已完成/失败任务列表、按股票/时间打开、研究版本和来源 | 必须（可以很简洁） |
| Portfolio | 显示现有组合 Risk / What-if；M2 完成后增强目标仓位与差额 | 简版先行 |
| Dashboard | 最近研究、待关注股票、关键风险和数据新鲜度 | 后续增强 |
| Settings | 模型/数据源服务状态、研究参数、风险策略配置 | 后续增强 |

**最小对话工具**（先少后多）：

1. \`ReadCurrentResearch\`：查看当前 run 的结构化研究结果与多空证据。
2. \`StartResearch\`：经应用服务启动真实研究任务；明确标的与时点。
3. \`ListAndCompareResearch\`：选择同一标的两次研究并比较结论/证据的差异。
4. \`QueryPortfolioScenario\`：读取/评估已有明确账户与政策的情景；未来接 M2 的 sizing。

对话本身不创造研究事实：普通解释直接回答；需要最新数据时调用现有 Capability；需要全量研究时启动现有 Workflow；数据不足时要求必要输入或说明无法计算。多轮指代将「它/刚才/上周」解析到明确 symbol / run_id / as_of；历史事实不能假冒当日现值。M1 不要求完整长期 Memory/RAG。

**M1 Exit Gate**：用户完全不打开 CLI，就能在浏览器完成「提问/启动研究 → 实时进度 → 结构化报告 → 追问证据 → 刷新后恢复并打开历史」；同一 run 在 UI/API/CLI 的核心产物一致；包括失败、账户未知、工具无权限、超时和页面重连测试。

## 6. M2 — 组合仓位管理 V1（P0，可与 M1 并行）

### 6.1 选择设计：固定硬风控 + 可配置动态计算

三三制是未来**可供比较的一类仓位政策**，不是默认全仓 1/3 + 1/3 + 1/3。核心目标是根据 **市场环境、单笔亏损预算、已有持仓、价格/止损假设与组合限制** 给出研究性目标比例，且可复算。

~~~text
TradeIntent + Market/Risk Context
                +
可信 Portfolio Snapshot（账户 / 估值 / 现有仓位 / 可用资金）
                +
明确 Risk Policy（单笔亏损预算、总仓位/单股上限等）
                +
研究性价格与失效/止损假设（有来源/时点）
                ↓
Deterministic SizingPolicy
                ↓
Portfolio Risk Gate / 可解释约束
                ↓
Research-only SizingAssessment
（当前比例、建议比例、差额、约束原因、无法计算原因）
~~~

- **观测值 vs 策略配置**：真实/用户显式给定的账户状态与用户设置的风险参数分开来源记录；永远不将 NOT_PROVIDED 解释为零持仓或零现金。
- **最简政策**：风险预算 ÷ 预设止损距离得到理论仓位，再取现金、单股、总敞口、现有仓位等限制下的较小值；市场 regime 只施加明确版本化的风险上限，不使用未经校准的 LLM confidence 直接乘比例。
- **多标的一致性**：同一组合共享账户预算；多个独立 Agent 候选不可重复占用同一现金或忽略相关性/行业集中风险，缺乏必要数据时声明限制。
- **模型职责**：Agent 能解释偏多/偏空、风险和假设；输入/计算/裁决由确定性代码与验证器完成。若止损条件或价格缺失，则可以给风险定性描述，但不能制造精确目标仓位。
- **契约兼容**：不要直接把现有非执行 PortfolioDecision 改造成下单意图；扩展独立的 SizingAssessment/AllocationScenario 并版本化；无 BUY/SELL 委托、无真实订单数量授权。
- **A 股特殊性**：研究/模拟中逐步建模交易单位、停牌、涨跌停、T+1、交易费用与流动性等；标注假设，不暗示可保证按目标比例成交。
- **验证先行**：同样的输入必须得到一致输出；至少用固定仓位 baseline 与基础动态规则做小规模历史重放/情景比较，明确无前视数据、费用和模拟假设。**这只是正确性与初步对照，不等于证明动态策略有超额收益**。

策略分层：V1 一个确定性动态规则；后续才添加三三制、ATR/波动率、等权、分批建仓等独立 SizingPolicy，使用相同信号与成本模型比较，经过样本外验证再决定默认策略。

**M2 Exit Gate**：给定真实且完整的账户+政策+研究条件时输出可复算的当前/目标/差额/命中上限；未知账户、过期估值、资金不足、无效止损、风险阻断、多标的争用时安全返回不足或拒绝；全部有确定性测试、Workflow 回归，Web 只显示研究建议而非执行按钮。

## 7. M3 — 研究历史、观察池与机会发现（P1）

### 7.1 研究资产化

保存原始输入/输出、研究截止时间、引用、策略/模型/政策版本、耗时、失败阶段及事件轨迹；支持同一标的多次研究的结构化 diff，不以聊天摘要替代证据。

### 7.2 策略扫描与 Watchlist

- 第一类扫描可采用「上升趋势回踩」，从可配置股票池按确定性规则筛选候选。股票板块、交易范围、停牌/风险警示、流动性要求作为策略配置，不固定为所有用户的默认偏好。
- 扫描有 universe、研究时点、规则版本、指标数值、入选/淘汰原因。先筛选，再为少数候选启动多 Agent。
- 观察池保存关注理由、假设有效期、参考证据与下次研究建议；比较多只股票时统一数据时点与指标口径。
- 日/周报告基于真实已完成研究记录生成；可先手动触发，监控调度后续进入 M4。

**M3 Exit Gate**：历史记录可追踪，新旧研究差异可解释；规则扫描可重跑得到同一结果；候选能直接触发研究；不会用未来成分或后来公布的财报污染过去筛选结果。

## 8. M4 — 主动研究与 Thesis Tracker（P1）

**从「用户每次点研究」进化为「条件变化时主动提醒和复查」**。

- 触发源：预设支撑/失效条件、价格/量能异常、公告/事件更新、账户风险变化、定期回看；下层 Provider 可由 API/WebSearch/爬虫/本地数据库供给，不能因为数据来源不同就多造 Agent。
- 每条触发带 symbol、观察时间、触发规则/原始事件、唯一去重键、来源健康状态；限流/冷却/重试/费用预算，避免重复全量研究。
- 判断「仅刷新一个数据维度」「局部复查」「重新执行完整研究」；不能把旧研究自动当成今天仍成立。
- 跟踪结构化研究假设：假设主张、证据、反方证据、适用时间窗口、失效条件、验证方法、状态（OPEN/SUPPORTED/REFUTED/INCONCLUSIVE/EXPIRED）。
- 保留提出假设当时的快照、后续真实观察与验证版本；证据不足时 INCONCLUSIVE，不将未证伪等同于正确。
- 对话可以追问「这次重大公告如何改变上次研究」「原来的空头假设还成立吗？」。

**M4 Exit Gate**：至少一种真实外部变化触发受控复查，并生成前后证据差异；假设状态可复现，重复事件不重复造成任务风暴；失败可见且不会宣称无事发生。

## 9. M5 — 持续研究 Memory、错误归因与反思（P2）

Memory 的目标不是建立聊天机器人长期偏好库，而是**累计有证据的研究经验**。每日行情、新闻、交易所/财务数据由独立数据管线更新；研究 Memory 只存 Agent 的判断过程、错误、归因、假设与待验证经验。

三层职责：

| 层次 | 记录对象 | 可否被模型直接改写 |
| --- | --- | --- |
| 历史事实与运行 | 当时的输入、来源、证据、Agent 输出、策略/版本、组合背景 | 不可覆盖；版本化追加 |
| 研究假设与后验评估 | 原假设、预期窗口、实际观察、预测偏差、失败类型 | 规则计算/受控评估，保留原版本 |
| Research Memory | 从多次研究形成的经验候选、反例、失效市场环境、后续建议 | 可提议，需带证据/版本/可撤销状态 |

- 需要能回答「上次为什么偏多」「现在什么新事实推翻了上次判断」「过去十次哪些错误是同一类型」。
- 检索同时带支持与反例；Memory/摘要不能替代最新市场数据，不允许越过确定性风控。
- 反思应针对错误类型：数据缺失、错误引用、市场条件改变、假设失效、参数过拟合、风险预算超限等；不要仅以涨跌结果贴对错标签。
- RAG/向量索引仅在研究记录规模与检索效果需要时选用；避免为了使用新库而创建没有增益的 Memory Agent。
- 记忆提出的策略修改进入离线候选，未经验证不能自动启用。

**M5 Exit Gate**：至少能跨多个日期检索同一标的的历史判断、已证伪假设与来源；能回溯反思建议对应的运行和后验数据；检索失败、版本冲突、不足证据有明确状态。

## 10. M6 — 独立回测、仓位策略对照与持续进化（P2）

严格沿用 [权威架构](10-多Agent架构与职责边界.md) 的 **Online Research Loop / Offline Strategy+Validation Loop** 分离：

~~~text
历史 PIT 数据 → StrategyCandidate（版本、规则）
                         ↓
              Independent Backtest
                         ↓
       ValidationReport（成本、回撤、OOS、鲁棒性）
                         ↓
             REJECT / REVISE / APPROVE
                         ↓
              ApprovedStrategy Set
                         ↓
                 在线按 regime 选择
~~~

最小要求：

- 回测收益、持仓、费用、滑点、T+1、交易日历、停牌/涨跌停、交易单位为**确定性模拟**，每条运行可用固定数据与参数复现。
- 明确训练/样本外与 walk-forward；验证信号时点、退市样本、生存者偏差、分红复权泄漏、选择性汇报和交易成本。
- **评估研究和评估仓位是两个问题**：同样股票池/入退场信号/费用，比较固定仓位、风险预算、三三制、波动率/ATR 与分批建仓，不因样本内收益最高自动上线。
- 持续研究结果可以提出 StrategyCandidate vN+1，但由独立验证产出 ValidationReport；旧版本和对应历史结果不可被覆盖。
- 扩展主题/产业链、资金流、Sentiment、Agent 分歧验证、反事实情景等时，需先证明有新增信息价值，避免只增加 Agent 数量。

**M6 Exit Gate**：同样数据与版本重跑一致；包含真实费用、样本外与压力情景；新仓位政策与 baseline 对比可审计；不通过验证的候选不进入在线默认策略。回测交易永远是离线模拟。

## 11. 跨阶段工程约束

### 11.1 角色与服务边界

~~~text
Interface: Web UI / Chat / CLI / Scheduler
                  ↓
Application Service: Run / Query / Compare / Scenario
                  ↓
Existing Aegis Eino Graph + typed Context/Artifact
                  ↓
Research / Risk / Portfolio domains (deterministic limits)
                  ↓
Versioned Storage + Provenance + Run Events

Separate capabilities: Screening / Monitoring / Memory / Backtest
接入同一任务/产物基础设施，但不重写 Existing Workflow。
~~~

- Role 按研究职责、Capability 按数据/执行能力、Provider 按数据源；不要创建 Tushare Agent/MCP Agent/超级 Trading Agent。
- 当前优先纵向用户场景，不创建 TeamRegistry、AgentFactory、ProviderRegistry 等泛化组织框架。
- Agent 的 prompt/model/profile、运行参数与关键规则版本化，可回溯；外部来源不可用时区分降级、不完整与明确失败，不伪造结果。
- 各端状态一致：Web/Chat/CLI 获取同一 run_id 的结果，不能因为换入口重跑又得不一致的「同次研究」。
- 适度可观测性：阶段成功率、数据源失败率、p50/p95 延迟、成本、失败原因和用户可见的恢复路径；性能优化以真实瓶颈驱动。
- 涉及用户账户/日志/来源的隐私与权限需在 API 层处理；网页不得直连模型密钥或数据商私钥。

### 11.2 DoD：完成不等于合并

一个里程碑完成至少具备：可复现路径、输入/输出契约、正常/不足/失败测试、必要真实数据验证（或明确未完成）、证据及 PR/commit/CI/Hosted run 链接、文档更新、已知边界。不得把模拟测试说成真实市场表现已验证。

### 11.3 技术选型仅为候选，不提前当做决定

保留现有 Go + Eino 主体。Web 候选 Next.js/TypeScript；通讯 REST + SSE；存储使用适合持久化 run/event/artifact 的数据库；研究图表使用成熟图表库。具体选型经最小技术验证与 ADR 后确定，避免在路线图里硬写多余的技术栈迁移。

## 12. 可操作的 Epic / Issue 拆分（不伪造固定 PR 数量）

| Epic | 下一条最小纵向交付 | 通过标准 | 状态（本次核查） |
| --- | --- | --- | --- |
| **E0 Core Closure** | 复核 PR #123、main 的完整 Hosted F4 风控/研究输出 | SHA + 真机/Hosted 记录 + 正反路径 | IN_PROGRESS |
| **E1 Run Service** | 从 CLI 装配提取统一 RunResearch；持久化 run/event/artifact，最小查询 API | 任务创建、进度、重启后查询 | PLANNED |
| **E2 Web+Chat Slice** | 一个研究输入页 + Agent 进度 + 报告 + 追问工具 | 不开 CLI 完成一条真实路径 | PLANNED |
| **E3 Portfolio Sizing** | 输入合同 → 简单动态 SizingPolicy → Portfolio Gate → 报告 | 可复算 + 缺失/超限测试 | PLANNED，可与 E2 并行 |
| **E4 History / Compare** | 多次研究版本化查询、证据差异和引用 | 明确时间/来源、可复原对照 | PLANNED |
| **E5 Screening / Watchlist** | 上升趋势回踩规则候选 + 一键研究 | 同条件重跑一致，PIT 严格 | PLANNED |
| **E6 Monitoring / Thesis** | 一个真实触发事件与一个可验证假设 | 可观察触发/去重/结果评价 | PLANNED |
| **E7 Research Memory** | 研究判断→后验验证→错误归因→经验候选 | 证据引用、反例、可撤销 | PLANNED |
| **E8 Independent Validation** | 策略回放、仓位比较、样本外验证 | 可复现、独立审批，未通过不晋升 | PLANNED |

Epic 不等于单个 PR。每个开发 Issue 使用以下简约模板：

~~~markdown
## 用户可感知目标
## 当前 main SHA / 已有实现和真实缺口
## 最小输入/输出契约与复用对象
## 实现范围 / 明确不做
## 验收：正常场景、缺失/失败场景、可复现命令
## 证据：测试/CI/Hosted Run、PR、最终合并 SHA
## 依赖/剩余风险
~~~

对已实现能力只做验收，不为了匹配路线图另造同名模块。每个 PR 聚焦可验证的用户路径或明确的领域约束，优先功能正确再优化细节。

## 13. 下一步执行顺序与路线维护

### 立即（只推进一个主线）

1. 查最新 main、PR #123 与 CI/Hosted 证据；按 F4 Gate 收尾当前多 Agent 内核。若已足够，直接结束 E0，不继续叠加研究角色。
2. 准备 **E1+E2 的最小产品化纵向切片**：固定一个「输入股票 → 真实研究 → 页面查看 → 对话追问」用户故事，确认 Run/Artifact 和观察事件从核心复用。
3. 在不阻塞上述 Web 切片的前提下，准备 **E3 的最小仓位输入契约**：账户预算、止损假设、风险限制、拒绝条件；先可复算，后比较多策略。
4. 之后按实际使用问题补历史/比较、观察池、主动研究、记忆与回测。基本回放/风控正确性随 E3 开始，独立完整回测在 E8 扩展。

### 路线维护规约

- 每次开始 Epic，先核对 main、开放 PR、已有代码与真实测试；历史 SHA 只作溯源，不代表当前状态。
- 状态统一使用 PLANNED / IN_PROGRESS / IN_REVIEW / DONE / BLOCKED / DEFERRED；DONE 必须附合并 SHA 和验收证据。路线图不通过「猜测完成度百分比」推进。
- 产品需求变动时，更新此文件的用户故事、范围、Gate 与 Epic 依赖；具体协议、数据库表、接口实现细节写在 Issue 或 ADR，避免把总路线图变成巨型代码规范。
- 当前只允许 E0 为研发主线；完成后优先首个 Web+Chat 纵向路径，同时允许独立 E3 动态仓位研究。**最终目标不是运行一条 CLI，而是用户能在网页中发起、理解、追踪和持续改进研究。**
