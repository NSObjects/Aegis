# Aegis 开发路线图（Development Roadmap）

> **用途**：本文件是开发导航。V1 做完后，开发者打开本页顶部「当前阶段 / 下一项任务」，就能直接决定下一个 Issue/PR；每个任务都有交付、验收和完成记录要求。**不是产品愿景文档，也不是架构重写方案。**
>
> 初始盘点：2026-10-10；`main` 最近查到 `0ed06de9bdc1f079530cc9b0f901c9d6847aef8e`（PR #123 已合并）。这是核查时点而非永久最新状态；验收未通过的事项不会因 PR 合并而自动标记完成。
>
> **约束优先级**：已存在的 [Multi-Agent F0～F4 收尾清单](MULTI_AGENT_ROADMAP.md) 和 [权威职责与研究边界](10-多Agent架构与职责边界.md) 仍有效。Aegis 仅做投资研究与决策辅助；没有券商下单、资金划拨、订单审批或自动调仓。仓位建议、交易计划和回测「成交」均不可执行。
>
> **版本口径**：「V1」在本页指**当前多 Agent 研究内核可完整运行的交付目标**，不代表把仓库已经使用的工程版本 `V2.13` 改名。后续统一用 **R0～R8 阶段编号**来指导开发，避免产品版本与 Git 工程版本混淆。

**顺序规则**：只要有当前阶段未通过验收，默认不跳到下阶段；同阶段任务按编号推进。确有必要并行时，允许 R1 的页面/服务与 R2 的**独立纯计算库**并行，但以已通过的接口契约为前提，并在状态区注明；绝不拿复杂优化拖住可运行主路径。

### 阶段完成后如何找到下一任务

1. 打开本节，查看「当前主线」；进入对应 Rn 小节，找到**第一条未勾选的任务**。
2. 创建或复用该任务的 GitHub Issue：先核对最新 main 是否已实现；已具备则做验收，不重复开发。
3. 一个 PR 做一个可验证的纵向切片，完成代码 + 必需测试 + 文档；CI/Hosted 结果要对应**固定 commit SHA**。
4. 将已完成任务勾选为 `[x]`，填入 PR / 合并 SHA / 测试链接；**只有阶段 Exit Gate 真正通过**，才将阶段状态改为 DONE，并把顶部「当前主线/下一项任务」指向下一阶段的 **Rn-01**。
5. 遇到真实阻塞标为 BLOCKED，写原因与解除条件；非阻塞细节记入「延后项」，不得停工打磨无关能力。

**状态定义**：PLANNED / IN_PROGRESS / IN_REVIEW / DONE / BLOCKED / DEFERRED。下面的任务勾选是待开发列表；不等于对现有代码一概判断为缺失。

## R0 — 当前：V1 多 Agent 研究内核收尾（完成再做 R1）

**目标**：一次实际运行从真实市场/公司研究出发，走完 Analyst → Synthesis → Bull/Bear → Research Manager → TradeIntent → Risk Analyst → Portfolio Manager，生成结构化结论；有真实来源时可成功，无数据时有受控不足/失败结果。不要求此阶段有 Web、Memory、复杂动态仓位或多策略平台。

**当前基础（查到的真实代码与提交）**：

- 既有 `internal/research/workflow.go`、`internal/research/full_portfolio_workflow.go`、`internal/research/portfolio_review.go` 与 `cmd/aegis`；现有 Market/Technical/Event 研究链、Fundamental 增量能力、Debate/Manager/Trading/Risk/Portfolio。
- PR #117、#118 加强 Bull/Bear 交接；PR #120 保护风险/组合阶段的可信输入；PR #122 增强终态风险门禁。
- **PR #123 已合并**，新增 F4 真实 CLI JSON 风险门禁验证；**合并 ≠ 已确认当前所有 Hosted 场景通过**。

### 按顺序执行

- [ ] **R0-01　冻结基线和验收真实 Hosted E2E**
  - 核对当前 `main` SHA；执行 `go test ./... -count=1`、`go vet ./...`；使用 `.github/workflows/integration.yml` 的真实 `run_production_cli`、适用时的 `run_fundamental`；附可打开的运行 URL、固定 SHA、真实/缺失来源说明。
  - 观察输出中同一次 run 的 `research_artifact`、辩论、研究计划、`trade_intent`、`risk_context`、`portfolio_decision` 及终态风险门禁。不可只因 workflow 文件存在或 PR 合并而勾选。
  - **验收**：一条实际成功路径 + 一条受控缺失/失败路径，可复现且不伪造行情/账户。
- [ ] **R0-02　修复 R0-01 明确暴露的阻塞缺陷（如有）**
  - 只修调用链、真实数据契约或核心风控阻塞；每个缺陷另 Issue/PR、附最小复现与回归测试。若无阻塞缺陷，明确记录「无阻塞项」后跳过。
  - **验收**：对同一实际输入重新执行 R0-01，失败被解释或验证消除。
- [ ] **R0-03　V1 交付冻结**
  - 记录正式启动命令、所需服务端凭证/Provider、样例 JSON、已知边界、对应提交和测试证据；更新原 F0～F4 状态。区分「账户 NOT_PROVIDED」与真实空仓。
  - **验收**：另一开发者仅凭文档即可运行/判断失败类型；主链路不需要手动拼接多个 Agent。

**R0 Exit Gate**：以上均有证据，现有多 Agent Graph/契约可以作为稳定可复用内核；此时将 R0 改 DONE，**下一项马上做 R1-01**。非阻塞的高级风控、多智能体数量、Memory/RAG、性能微调不作为 R0 阻塞项。

## R1 — V1 后第一个开发阶段：API + 可操作 Web + 基础对话

**为什么紧接着做**：你明确最终使用 Web，而不是 CLI。因此 V1 一完成，不应继续沉迷 CLI 或不断加新 Agent；先让现有研究能力可被页面和自然语言使用。

**阶段完成时的实际体验**：打开 Web → 输入股票代码或说「研究 600519.SH」→ 后端启动现有多 Agent 研究 → 页面实时显示 Agent 进度 → 阅读证据与报告 → 追问「刚才空头为什么这样说？」→ 重开页面还能找到该研究。

### 按顺序执行（建议一个任务一张 Issue，必要时进一步拆 PR）

- [ ] **R1-01　提取应用层研究入口（第一项）**
  - 将 `cmd/aegis/main.go` 中通用的装配/启动逻辑整理为可被 CLI 和服务调用的 Application Service（建议 `RunResearch(ctx, request)` 风格，确切包名在 Issue 里定）。
  - **复用**现有 Eino Graph、PortfolioReview、Agent/Capability，CLI 成为适配器；不重写研究逻辑、不提前造通用 Agent Registry。
  - **验收**：Go 集成测试直接调用服务可得到与原 CLI 等价的 typed Artifact；现有 CLI 完整回归。
- [ ] **R1-02　实现 ResearchRun 任务生命周期和持久化**
  - 结构化 RunID、symbol/as_of、版本、PENDING/RUNNING/COMPLETED/FAILED/CANCELLED、失败阶段；保存事件、研究产物、源/时间、输入 digest。
  - 首版可用单机 Worker + 持久化数据库；存储技术通过小 ADR 选，不必预先引入 Kafka/分布式调度。
  - **验收**：运行/失败均能查询；进程重启后历史可读；重复请求、超时/取消不导致无界重复运行。
- [ ] **R1-03　Go HTTP API 与进度 SSE**
  - 最小 API：启动 Run、查询 Run、列出/读取 Artifact、订阅阶段事件、查询历史；鉴权、输入校验、请求限流及凭证隔离。
  - **验收**：curl/集成测试完整跑通「启动 → 查询 → 事件 → 结果」，客户端断线重连不丢最终状态；错误信息能定位阶段。
- [ ] **R1-04　Web 最小研究工作区**
  - Next.js/TS 可作为首选候选（技术选型在本任务定），优先实现股票输入、开始研究、Agent 时间线、ResearchArtifact/辩论/风险/结论报告以及历史入口。
  - **验收**：不启动 CLI，仅使用 Web 完成一次真实研究；加载中、无数据、失败、刷新后继续查看均正常。
- [ ] **R1-05　Conversation Agent 最小 Tool 调用**
  - 只提供 `StartResearch`、`ReadResearch`、`ReadDebate`、`ListResearchRuns` 等必要 typed tools；短期 session 上下文明确指向 symbol、run_id、as_of。
  - 不依赖长期 Memory，不允许凭对话编行情/财报或绕开现有 Risk Gate；简单问题不必启动整个 Graph。
  - **验收**：页面对话「分析它 → 为什么看空 → 给出处」能够读取同一 Run 的验证过的 Artifact；工具错误受控，不重复付费跑全链。
- [ ] **R1-06　Web + Chat 端到端与部署收口**
  - 提供最小单机部署、API 连接/鉴权、配置与数据库迁移说明；浏览器 E2E 覆盖正常、研究失败、缺来源、刷新/重连、会话切换。
  - **验收**：通过 Web/Chat 连续完成同一研究的发起、进度、证据追问与历史检索，CI/浏览器真实结果可复现。

**R1 Exit Gate**：Web/Chat 已经成为日常可用入口，而非 CLI 展示页；**接下来做 R2-01**，用已有组合研究输入实现仓位计算。若只有 Web 还没有基础对话或历史恢复，R1 仍未完成。

## R2 — 组合级动态仓位管理 V1（高优先级）

**阶段成果**：页面/对话能查看当前持仓风险、输入可验证的组合与预算参数，获得**研究性目标仓位与理由**。不是照抄「三三制」，更不是通过 AI 下单。

- [ ] **R2-01　明确组合/账户/风险预算输入契约**
  - 复用 `internal/portfolio` 的已观察账户状态、估值/风险限额与现有 What-if；明确净值、现金、现有持仓、预算、组合暴露、时效、数据来源。
  - 风险参数与观察到的资金事实分开；NOT_PROVIDED 永远不默认为零持仓。缺失价格、止损研究假设、资金预算时明确无法精确计算。
  - **验收**：单测覆盖完整、账户未知、过期、金额不一致、参数非法。
- [ ] **R2-02　确定性基础 SizingPolicy**
  - 固定风控硬上限 + 市场风险约束 + 单笔风险预算/止损距离 + 现金/总敞口/单股限制；输出可复算的基础目标仓位、差额和限制理由。
  - Agent 给的是研究论点和失效条件，不是绕过风控的仓位数值；所有参数与计算版本化。
  - **验收**：表驱动正常/极端值/不足输入测试，同样输入结果一致。
- [ ] **R2-03　组合级 Risk Gate**
  - 同一账户多股票/多策略必须共享一个预算；不能分散到各 Agent 后重复使用现金；现有 Risk/Portfolio 最终审查仍具备否决权。
  - **验收**：资金不足、集中度超限、现有仓位冲突、候选被拒绝等场景不会输出合规假象。
- [ ] **R2-04　接入 Workflow、API 和 Web/Chat**
  - 新增独立研究性 SizingAssessment（建议契约），包含 target/current/delta、风险预算、约束命中、insufficient reason；不改变已有不可执行的 PortfolioDecision 含义。
  - **验收**：一次 Run 可追溯研究、风险与仓位情景；Web 和 Chat 都能展示相同结果。
- [ ] **R2-05　最小历史回放与策略基准对照**
  - 使用冻结的信号与 PIT 数据验证基础政策在不同价格/风险情况下是否稳定，和固定比例 baseline 做初步模拟对照；记录成本/交易限制假设。
  - **验收**：计算正确且可复现；不宣称初步测试证明超额收益。完整 OOS/Walk-forward 后续在 R7。

**R2 Exit Gate**：真实完整输入下可计算，数据不足时安全退出，组合限制不能绕过，Web 可理解结果。然后 **R3-01**。

## R3 — 完整可用的 Web 研究工作台

在 R1 的最小页面和对话基础上补日常使用必需功能，而不回头重复开发研究 Graph。

- [ ] **R3-01　研究报告与 Agent 工作过程视图**：Market/Technical/Fundamental/Event、Bull/Bear 引用和反驳、Manager/TradeIntent、Risk/Sizing，按证据链展开；验收能查每条结论的来源、日期与失败原因。
- [ ] **R3-02　历史记录与两次研究比较**：按股票/日期筛选运行，diff 同一标的两次 typed Artifact，明确新增/失效证据；验收不把旧行情当现价。
- [ ] **R3-03　组合/What-if 页面**：组合快照、当前敞口、风险限制、模拟仓位建议及冲突诊断；验收未知账户不显示虚假零仓位。
- [ ] **R3-04　Settings 与基础 Dashboard**：模型/数据源健康、研究任务参数、风险政策、最近研究与关键异常；验收敏感密钥不出浏览器。
- [ ] **R3-05　Web 使用体验验收**：异常/空数据/移动端、检索与列表、必要权限、主要用户路径浏览器 E2E；验收无须工程师帮忙输入 CLI 命令。

**R3 Exit Gate**：Web 能独立完成日常研究、报告、历史和组合情景；接下来 **R4-01**。

## R4 — 智能选股、观察池与横向比较

- [ ] **R4-01　第一套确定性扫描策略**：以上升趋势回踩为最初候选，定义股票池、有效交易日、量价条件、排除规则与版本。扫描在确定性代码进行，而非为全市场每只股票调用 LLM。
- [ ] **R4-02　候选结果与研究联动**：筛选原因、数据时点与评分依据可见；从候选一键触发已有 Multi-Agent Run。
- [ ] **R4-03　Watchlist/观察池**：自选、研究理由、触发/失效条件、最新研究关联；支持手动优先级。
- [ ] **R4-04　多标的比较**：同一时间点、统一指标口径比较几只候选股票，提示数据覆盖缺口；不能单凭未经校准的 LLM 信心值硬排序。
- [ ] **R4-05　数据回放验收**：冻结股票池、复权/数据源、时间点与规则，同输入同结果；历史扫描不能使用未来数据。

**R4 Exit Gate**：系统能够主动**筛出值得研究的候选**，但不会把候选直接变成真实交易；然后 **R5-01**。

## R5 — 自动监控、事件触发与定期研究

- [ ] **R5-01　定时任务与数据更新接入**：接入现有行情/新闻数据管线或已验证数据源，定义交易日调度、幂等与失败重试；不重复造新的采集系统。
- [ ] **R5-02　观察池规则监控**：价格/量能、支撑失效、财报/新闻、研究过期或组合风险变化；同一事件去重，限流/冷却，设置模型费用上限。
- [ ] **R5-03　按需增量/完整研究调度**：能判断是否仅刷新一类事实、重新评价假设或执行完整 Graph；保留触发事件 → run_id 关联。
- [ ] **R5-04　通知与定期报告**：每日/每周总结、异常提醒、已有结论变化；引用真实证据、不夸大无数据的结论。
- [ ] **R5-05　运行验收**：至少一类真实事件触发研究与可解释提醒；外部来源宕机显示不确定性，而不是「未发生事件」。

**R5 Exit Gate**：系统无需每次用户手动提问，也能有界、可靠地发起并追踪研究；接下来 **R6-01**。

## R6 — 研究假设、持续研究 Memory、错误反思

**区分数据仓库与 Memory**：每天的交易行情、公告和新闻交由已有数据采集/数据库管理；Memory 专门积累**Agent 研究过什么、判断什么、为什么出错、哪些假设仍待验证**，不只是保存聊天记录。

- [ ] **R6-01　研究假设结构化**：保存 hypothesis_id、研究标的/时点、主张、正反证据、失效/验证条件、有效期与 run_id。
- [ ] **R6-02　后验验证**：新数据到来后按预定义规则判断 SUPPORTED/REFUTED/INCONCLUSIVE/EXPIRED；保留原判断不覆盖，无法验证就标未知。
- [ ] **R6-03　错误归因与反思记录**：区分原始数据质量、研究推理错误、市场环境变化、假设失效和仓位控制问题；每条反思可回溯证据与对照结果。
- [ ] **R6-04　研究记忆检索**：按标的、市场环境、错误类型、假设相似度检索；同时提供反例。向量索引/RAG 按真实检索需求评估，不为框架而框架。
- [ ] **R6-05　嵌入对话与研究任务**：如「今天与昨天的空头判断区别」「过去三次失误是什么」能引用历史决策与后验事实；历史记忆不能覆盖实时行情或强制风控。

**R6 Exit Gate**：同一标的跨多个研究日形成能查、能验证、能解释错误的连续研究档案；接下来 **R7-01**。

## R7 — 独立回测、策略及仓位管理评估

- [ ] **R7-01　PIT 历史数据与回放引擎**：固定市场数据、股票池、复权和交易日；确定性模拟交易成本、滑点、停牌、涨跌停、A 股 T+1 和交易单位，不接真实券商。
- [ ] **R7-02　StrategyCandidate 版本化**：先落地已在 R4 有用的策略规则/参数版本，再增加新候选，记录适用市场 regime 和失效条件。
- [ ] **R7-03　独立验证流程**：回测与策略提出分开；包含样本内/样本外/滚动或 Walk-forward、交易成本和鲁棒性，不让策略 Agent 自判合格。
- [ ] **R7-04　仓位政策对照**：同样选股、入退信号和成本条件下比较 R2 基础动态策略、固定比例、三三制、ATR/波动率/分批建仓；用指标和不同市场情景分析差异。
- [ ] **R7-05　报告与晋升**：可复现 ValidationReport、策略/模型/数据版本、收益、最大回撤、风险与失败原因；未经验证的策略不能默认进入在线研究。

**R7 Exit Gate**：策略、仓位调整与事后经验有明确验证方法；同输入能复现结果；接下来 **R8-01**。

## R8 — 以真实数据驱动的持续改进

- [ ] **R8-01　Agent 研究质量评估**：数据覆盖、证据与引用正确性、Bull/Bear 信息增益、模型错误、真实后验验证，不只统计回答是否流畅。
- [ ] **R8-02　成本/延迟/可靠性**：根据运行 telemetry 分析外部源成功率、p95 延迟、模型费用；再做缓存、路由、并发或降级，而不是先上复杂平台。
- [ ] **R8-03　高级研究能力评估**：Capital Flow / Sentiment / Sector / Theme、Risk Debate、多策略组合、反事实分析等先写独立增益假设，评估是否真的必要后才建 Agent。
- [ ] **R8-04　策略演进闭环**：反思生成策略候选，经 R7 独立验证后人工批准；保证版本化、可回滚、旧结果不可变。
- [ ] **R8-05　下一轮路线盘点**：根据真实用户操作频率、研究质量和投资场景，将新项目排成具体 R9+ 任务，而不是预先无限扩充框架。

**R8 Exit Gate**：下一阶段开发依据真实使用和验证结果，不靠版本号或 Agent 数量驱动。

## 横向约束：每一阶段必须遵守

| 事项 | 检查标准 |
| --- | --- |
| 研究来源 | 真实数据/出处、PIT、观察与解释分离；不可把缺失源按 0 补全 |
| 组织架构 | Role / Agent / Context / Capability / Provider / Graph 分层，不创建「数据源 Agent」 |
| 交付节奏 | 优先跑通真实用户路径；每个 PR 聚焦一个功能缺口；阻塞与非阻塞分开 |
| 风控 | 确定性限制优先，缺数据 fail-closed；Web/对话不可以覆盖已通过的 Risk Gate |
| 安全 | 本系统永不实际下单或授权交易；模型和数据源密钥服务端管理；账户数据鉴权隔离 |
| 验证 | Go tests、vet、契约/工作流测试；需要真实模型/来源的功能提供 Hosted E2E 证据 |
| 前后端 | CLI / Web / Chat / 定时任务共用同一 Application Service 和 typed Artifacts |
| 可追踪 | RunID、提交 SHA、来源/时点、配置版本、Artifact/证据、失败原因、PR/CI 记录 |
| 技术选择 | Go/Eino 继续为研究内核；数据库/前端/API 框架在对应任务做最小决策，不提前大规模重构 |

## 文档维护规则

- **入口只有这一份**：`docs/DEVELOPMENT_ROADMAP.md` 回答「现在在哪，下一步做什么」。`MULTI_AGENT_ROADMAP.md` 是 R0 的下钻任务清单，历史架构/ADR 是约束而不是另一份进度真源。
- **每次合并后**：检查本路线图的「当前下一项任务」是否改变；若改变则更新同一个 PR 或独立小型 docs PR。勾选需要实际验收证据。
- **完成阶段**：写明退出验收证据，并把顶部「当前主线」指向下一阶段，不能让读者猜测还要做什么。
- **计划变动**：记录变更原因、受影响依赖与替代顺序，保留完成记录，不把未来能力误标为已完成。
- **不伪造进度**：GitHub 的 merged、CI success、Hosted E2E、真实研究质量、策略收益验证分别表述，不互相等价。
