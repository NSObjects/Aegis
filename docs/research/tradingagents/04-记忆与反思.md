# TradingAgents 记忆、反思与结构化输出可靠性

本章基于 TradingAgents v0.5.0（commit `2d17df8`）源码，拆解记忆（memory）、反思（reflection）、
检查点（checkpointer）与结构化输出（structured output）四套机制。结论以源码行为为准，
做不到的部分同样如实标注。

## 1. 记忆的类型与分层

### 1.1 只有一种记忆，没有层级

与「短期 / 长期 / 按角色 / 按 ticker」的多层架构不同，v0.5.0 只有**一种**实现：
`TradingMemoryLog`（`agents/utils/memory.py:9`），append-only 的 markdown 决策日志，
docstring 自述为 "Append-only markdown log of trading decisions and reflections"（`memory.py:10`）。
没有短期/长期分层，不按角色分，不用向量库。v0.4.0 之前按角色划分的 BM25 记忆
（`FinancialSituationMemory`）与 `reflect_and_remember()` 管线已整体删除，测试用否定断言锁死
（`tests/test_memory_log.py:879-891` 的 `assert not hasattr(...)`）；
`test_portfolio_manager_no_memory_param`（同文件 `:893-898`）进一步要求
`create_portfolio_manager(llm)` 不再接受 `memory=`。

**设计意图与代价**：用单一可审计、可人工阅读的日志替换「按角色语义记忆 + 相似度检索」，
代价是放弃语义泛化——检索退化为纯 ticker 精确匹配（第 2 节）。

### 1.2 实际的「分层」是三个正交分区

分区均在读取端实现，没有层级结构：

| 维度 | 行为 | 依据 |
|---|---|---|
| 按 ticker 相关性 | same-ticker 注全文 / cross-ticker 仅注反思 | `memory.py:104-109` |
| 按结算状态 | pending 不注入 / resolved 可注入 | `memory.py:85` |
| 按时间点可知性 | `resolved <= as_of` 过滤（历史跑）/ 不过滤（实盘跑） | `memory.py:86-87` |

跨 ticker 条目只保留反思；无反思时退回截断到 300 字符的决策原文（`memory.py:331-337`）
——`300` 硬编码、未参数化，是上下文预算的保守取舍。

### 1.3 方法签名：按「时序阶段」组织

Phase A 写入与读取，Phase B 用结果回填——这是理解整套机制的主轴：

```text
# tradingagents/agents/utils/memory.py
__init__(self, config=None)                                              # :18
store_decision(self, ticker, trade_date, final_trade_decision)           # :30  写
load_entries(self) / get_pending_entries(self)                           # :56 / :69 读
get_past_context(self, ticker, n_same=5, n_cross=3, as_of=None) -> str   # :73  读
update_with_outcome(...) / batch_update_with_outcomes(updates)           # :114 / :180 回填
```

### 1.4 何时写、何时读

| 时机 | 调用 | 依据 |
|---|---|---|
| 图执行成功结束 | `record_decision()` → `store_decision()`，写 pending 条目 | `trading_graph.py:620`、`:569-577` |
| 新一次同 ticker 跑开始前 | `create_run_state()` → `_resolve_pending_entries()` 结算旧条目 | `trading_graph.py:547` |
| 构建初始 state | `get_past_context(..., as_of=...)` 注入 `past_context` | `trading_graph.py:552-554` |
| 图执行中 | PM 节点读取 `state["past_context"]` | `portfolio_manager.py:38-43` |

**结算先于注入**：`create_run_state` 先解析 pending（`:547`）再取 past context（`:552`），
故本次结算出的教训可在同一次跑中立刻读到。读取范围极窄：全仓库消费点只有
`portfolio_manager.py:38-43`，即**只有 Portfolio Manager 一个节点能看到历史教训**
（字段定义见 `agent_states.py:76`）。这是判断闭环程度的关键约束。

## 2. 记忆的存储与检索

### 2.1 单文件 markdown，无数据库、无向量库

`__init__`（`memory.py:18-26`）从 `config["memory_log_path"]` 取路径并 `mkdir(parents=True)`，
默认落盘 `~/.tradingagents/memory/trading_memory.md`（`default_config.py:76`），
同时读入 `memory_log_max_entries` 作为轮转上限。配置缺失时整个记忆层是**静默 no-op**：
`store_decision` 直接 return、`load_entries` 返回空表（`memory.py:37-38`、`:58-59`）。

### 2.2 存储格式：硬分隔符 + 定长 tag 行

分隔符刻意选 HTML 注释，理由写在注释里（`memory.py:12-13`）：
"HTML comment: cannot appear in LLM prose output, safe as a hard delimiter"，
取值为 `"\n\n<!-- ENTRY_END -->\n\n"`；`memory.py:15-16` 另有两条预编译正则分别抓
`DECISION:` 与 `REFLECTION:` 段。条目两态：pending 条目只有 `DECISION:`，
resolved 条目的 tag 追加收益字段并多出 `REFLECTION:` 段。

tag 行是竖线分隔的定长字段，由 `_resolved_tag`（`memory.py:246-249`）生成，形如
`[date | ticker | rating | raw% | alpha% | Nd | resolved:YYYY-MM-DD]`（`resolved:` 可选）。
解析端 `_parse_entry`（`memory.py:288-319`）做字段数下限校验，不足 4 个即判损坏并丢弃。
`resolved:` 缺失是**向后兼容的迁移设计**：v0.4.0 之前写入的条目解析后为 `None`，
在历史跑中被保守排除（见 2.5）。

### 2.3 检索：确定性分区 + 倒序取最近 N

```python
# tradingagents/agents/utils/memory.py:91-98
same, cross = [], []
for e in reversed(entries):
    if len(same) >= n_same and len(cross) >= n_cross:
        break
    if e["ticker"] == ticker and len(same) < n_same:
        same.append(e)
    elif e["ticker"] != ticker and len(cross) < n_cross:
        cross.append(e)
```

单遍扫描同时填两桶、`reversed` 保证最近优先、命中配额即 `break`；
`n_same=5` / `n_cross=3` 为默认参数（`memory.py:74`），生产调用点未覆盖
（`trading_graph.py:552-554`）；因为是 `elif`，同 ticker 条目不进 cross 桶。
**没有相似度、没有 embedding、没有 BM25**——这是 v0.4.0 删除旧记忆架构的直接结果。

⚠️ 检索靠字符串相等，**没有 ticker 归一化**：写入键与查询键都是 `company_name` 原样
（`trading_graph.py:576`、`:552`），而 `_fetch_returns` 内部确有 `normalize_symbol`（`:317`）。
同一标的的不同写法（`600519.SH` / `600519.SS`）会成为两条独立记忆。

### 2.4 膨胀控制：只有条数轮转，且默认关闭

唯一手段是 `memory_log_max_entries`，默认 `None` 即不轮转（`default_config.py:80`）。
`_apply_rotation`（`memory.py:251-286`）的契约是只丢最旧的已结算块
（"Pending blocks are always kept"）：先数 `resolved_count`，不超上限即原样返回，超出则按序
遍历递减 `to_drop`；`is_resolved` 完全依赖 tag 行文本形态（`:268-272`）。
**没有**摘要压缩、时间衰减、按 ticker 配额或按价值淘汰；轮转只在 Phase B 写回时触发
（`:174`、`:228`），不结算就永不轮转，读取端每轮全量读文件 + 全量正则解析。

### 2.5 三个可靠性与语义细节

**（a）幂等守卫，对已结算条目同样生效。** `memory.py:39-47` 的注释说明动机：
guard 用「快速原始文本扫描而非全量解析」，且*任何*同 (date, ticker) 条目都阻断新写入
（"pending or settled"），否则已结算后重跑会把同一决策在 past context 与所有聚合里算两次。
实现为按行匹配 tag 前缀与 `]` 后缀即 return；不解析 rating，故 O(行数) 且不依赖条目合法性
（边界见 `tests/test_memory_log.py:139-154`）。

**（b）原子写。** 追加用普通 append（`memory.py:51-52`）；Phase B 需重写整个文件，
故用 temp + `Path.replace`（`memory.py:176-178`，验证见 `tests/test_memory_log.py:453-464`）。

**（c）point-in-time 门禁。** 历史跑只允许看到「当时已发生」的结果：

```python
# tradingagents/agents/utils/memory.py:85-87
entries = [e for e in self.load_entries() if not e.get("pending")]
if as_of is not None:
    entries = [e for e in entries if e.get("resolved") and e["resolved"] <= as_of]
```

`as_of` 由 `_memory_as_of`（`trading_graph.py:409-418`）给出：
`return td if td < datetime.now().strftime("%Y-%m-%d") else None`，
即**交易日期在过去就过滤，是今天或未来则不过滤**。无 `resolved` 字段的遗留条目在历史跑中排除、
实盘跑中可见（`tests/test_memory_pointintime.py:57-69` 同时断言两侧）。

⚠️ 缺口：`get_past_context` **没有排除 `rating == "REVIEW"` 的条目**，无法解析评级的决策
其反思仍会被当作教训注入下次 PM prompt；而回测评分侧显式排除了 REVIEW
（`backtest.py` 的 `summarize()`）。两处策略不一致。

⚠️ 缺口：`get_past_context` **没有排除 `rating == "REVIEW"` 的条目**，无法解析评级的决策
其反思仍会被当作教训注入下次 PM prompt；而回测评分侧显式排除了 REVIEW

## 3. 反思机制（reflection）

### 3.1 触发时机：延后到下一次同 ticker 跑的开头

`_resolve_pending_entries`（`trading_graph.py:346-358`）只处理
`[e for e in self.memory_log.get_pending_entries() if e["ticker"] == ticker]`，docstring 自述
trade-off：其他 ticker 的条目会一直累积到该 ticker 被再次跑。调用链为 `propagate()` →
`_run_graph()` → `create_run_state()` → `_resolve_pending_entries()`（`:455-459`、`:582`、`:547`）。
**设计意图**是把「取真实价格 + 调 LLM」这两件可能失败的事从产出决策的关键路径上挪走；
**代价**是反思及时性取决于该 ticker 被再次跑到的频率——只跑过一次的 ticker 其决策永远 pending。

### 3.2 第一步：取已实现收益与超额收益

`_fetch_returns`（`trading_graph.py:291-344`）要求**完整持有窗口**都已成交，否则拒绝结算
而非用部分收益凑数：`if len(stock) <= holding_days or len(bench) <= holding_days:
return None, None, None, None`（`trading_graph.py:323-324`，注释标明 #1169）。
窗口足够时取 `raw = (Close[holding_days] - Close[0]) / Close[0]`、同样算法得 `bench_ret`、
`alpha = raw - bench_ret`，并把 `resolution_date = stock.index[holding_days]` 格式化为
`%Y-%m-%d` 返回（`trading_graph.py:326-338`）。窗口长度由 `default_config.py:159` 决定
（默认 5 个交易日）；基准按后缀映射到区域指数（`.T → ^N225`、`.SS/.SH → 000001.SS` 等，
`trading_graph.py:280-289`）。`resolution_date` 取**最后一根被使用的价格 bar 日期**，
正是 2.5(c) 门禁所依赖的时间点。

### 3.3 第二步：Reflector 生成 2–4 句反思

签名见 `reflection.py:36-43`：`reflect_on_final_decision(final_decision, raw_return,
alpha_return, benchmark_name="SPY", holding_days=5) -> str`。
system prompt（`reflection.py:22-34`）是本章最值得借鉴的工程设计，
因为它**显式声明评估窗口**并要求窗口不足时明说：

```python
# tradingagents/graph/reflection.py:24-31（节选）
    f"The outcome covers {holding_days} trading days after the analysis date, "
    "which may be shorter than the horizon the decision was written for.\n"
    "Write exactly 2-4 sentences of plain prose (no bullets, no headers, no markdown).\n\n"
    f"1. What the {holding_days}-day alpha shows about the directional call (cite the figure), "
    "and say so plainly if the window is too short to judge the thesis.\n"
    "2. Which part of the investment thesis this window supports or undercuts.\n"
    "3. One concrete lesson to apply to the next similar analysis.\n\n"
```

动机写在 `_system_prompt` 的 docstring（`reflection.py:14-21`）：为「几个月」写的论点不该被
「一周」证伪；忽略这个差异的教训会被后续跑读成「已被证实的失败」。
`tests/test_memory_log.py:1009-1016` 锁定 prompt 必须出现 `5` 与 `trading day`。
user message 只给数字与最终决策、不给市场上下文，理由是 `final_trade_decision` 已综合所有
分析师结论（`reflection.py:44-63`）；用 `quick_thinking_llm`（`trading_graph.py:165`）是**成本取舍**。

### 3.4 第三步：批量原子写回

`_resolve_pending_entries`（`trading_graph.py:360-394`）逐条取收益、逐条调 Reflector，
再把 `updates` 一次性交给 `batch_update_with_outcomes`。三处容错：价格未到 → `continue`
留 pending；Reflector 抛异常 → `logger.warning` 后 `continue`（注释：a transient failure
leaves the entry pending for the next one rather than stopping the analysis，`:377-382`）；
只有 `updates` 非空才写盘。写回把 tag 行换成含收益数字的 resolved 形态并追加
`REFLECTION:` 段（`memory.py:216-220`）；批处理用 `(trade_date, ticker)` 建 O(1) 分发表，
匹配后立即 `del` 以防同一 update 应用到多条（`memory.py:192-193`、`:221-223`）。

### 3.5 完整流程

```text
  create_run_state()  (第 N 次跑，trade_date = D)
   ├─(1) _resolve_pending_entries(ticker)   ← 只留 ticker == 本次 ticker
   │       _fetch_returns(ticker, entry.date, holding_days)
   │         ├─ raw is None ──> continue（价格未到，下轮再试）
   │         └─ 有效 ──> Reflector.reflect_on_final_decision()
   │                       ├─ 抛异常 ──> continue（留 pending，不中断本次跑）
   │                       └─ 反思 ──> updates ──> batch_update_with_outcomes
   │                              （temp 写入 + Path.replace → _apply_rotation）
   ├─(2) get_past_context(ticker, n_same=5, n_cross=3, as_of=D)
   │       排除 pending；as_of 门禁；同 ticker 5 条全文 / 跨 ticker 3 条仅反思
   ├─(3) 图执行 …… PM prompt += "Lessons from prior decisions and outcomes:" + past_context
   └─ 成功 ──> record_decision() ──> store_decision() 写 [D | ticker | rating | pending]
```

## 4. 这是否构成闭环学习

**结论：它构成「结果 → 下次上下文」的闭环，但只到「上下文注入」为止。它不调整任何参数、策略或
prompt，也不对学到的教训做任何评估或门禁。称为「自我进化」是夸大；
称为「带反思的历史决策日志」是准确的。**

### 4.1 支持「是闭环」的依据

`tests/test_memory_log.py:857-870` 端到端验证：store pending → `get_past_context` 为空 →
`update_with_outcome` 结算 → 返回含 `"Correct call."` 与 `"REFLECTION:"` 的文本。
且该 `past_context` 确实进入 LLM 输入（`portfolio_manager.py:39-43`、`:81-87`），
由 `:762-769` 捕获真实 prompt 字符串断言。

### 4.2 支持「只到上下文为止」的依据

1. **唯一消费者是 PM 的一个 prompt 段落**：全仓库对 `past_context` 的读取点只有
   `portfolio_manager.py:38` 一处。
2. **不存在任何写回 prompt / 配置 / 策略的代码路径**：穷举 `tradingagents/` 的写入点，
   只有 `memory.py` 日志写、`trading_graph.py:668` state JSON 写、`reporting.py` 报告写与数据层缓存写。
   没有任何文件把反思结论转成对 prompt 模板、`DEFAULT_CONFIG`、schema 或 agent 组成的修改。
3. **反思不携带结构化归因**：`reflection.py:63` 直接返回 `...invoke(messages).content`，
   纯字符串；存储时不解析、不打标签（`memory.py:219`），下游无法按维度检索或程序化比较。
4. **没有 Evaluation 与 Promotion**：反思一经生成即被采纳，没有「这条教训是否更好」的样本检验。

### 4.3 与 Aegis 六阶段的对照

| Aegis 阶段 | TradingAgents 是否具备 | 依据 |
|---|---|---|
| Execution | 具备 | `trading_graph.py:579-625` |
| Outcome | 具备（已实现收益 + 区域基准 alpha） | `trading_graph.py:291-344` |
| Reflection | 具备（2–4 句自然语言） | `reflection.py:36-63` |
| Proposal | **不具备** | 无提案生成路径 |
| Evaluation | **部分**：回测对 rating 分组打分，但不评估教训 | `backtest.py` 的 `summarize()` |
| Promotion | **不具备** | 无版本化、无采纳门禁 |
| 下一轮 Execution | 具备，但仅通过 prompt 上下文 | `portfolio_manager.py:38-43` |

`summarize()` 是 Evaluation 的雏形（按 rating 分组统计命中率与平均 alpha、排除 `REVIEW`），
但它评估的是**决策质量**而非**反思质量**，也没有把结果回流到任何东西上；
`backtest.py:10-17` 主动划界："this evaluates decision quality. It is not a portfolio simulator." 

### 4.4 四个能力上限

1. **无归因，只有叙述**：教训是自由文本，无法程序化消费；且只有 PM 读到。
2. **无参数更新**：`holding_period_days`、`n_same`、`n_cross`、评级阈值、prompt 模板全为静态配置。
3. **无采纳门禁，可能把噪声当教训**：5 个交易日的单股 alpha 信噪比极低，而反思 prompt 明确要求
   「one concrete lesson」（`reflection.py:31`）——结构性地推动在噪声上总结规律，又被无条件注入下一轮。
4. **结算调度与记忆耦合**：只有同 ticker 的 pending 在下次跑时结算（`trading_graph.py:353-354`），
   记忆新鲜度取决于 ticker 跑动频率而非结果可得时间。另有 2.5(c) 的 REVIEW 条目未排除问题。

## 5. Checkpointer

### 5.1 定位：断点续跑，不保存会话状态

`checkpointer.py:1-4` 的 docstring 给出定位与存储选择："LangGraph checkpoint support for
resumable analysis runs. Per-ticker SQLite databases so concurrent tickers don't contend."
保存的是**一次图的执行进度**；跨跑的多轮状态由 `TradingMemoryLog` 承担（见 5.5）。

### 5.2 存储布局与路径安全

`_db_path`（`checkpointer.py:19-25`）先过 `safe_ticker_component(ticker).upper()`，
再返回 `<data_cache_dir>/checkpoints/<TICKER>.db`（默认
`~/.tradingagents/cache/checkpoints/`，`default_config.py:75` + README:308）。
该 sanitizer 拦截路径穿越——docstring（`dataflows/utils.py:14-34`）指出来源风险：
CLI 输入与 LLM 工具调用，后者可被新闻中的 prompt injection 影响。
**per-ticker 分库**是为避免并发跑不同 ticker 时的写竞争。

### 5.3 thread_id：把「图形态」折进身份

```python
# tradingagents/graph/checkpointer.py:28-38（节选）
def thread_id(ticker: str, date: str, signature: str = "") -> str:
    """... ``signature`` folds in graph-shape-affecting run choices so a resume
    under a different graph can't reuse this checkpoint (#1089)."""
    base = f"{ticker.upper()}:{date}"
    return hashlib.sha256((f"{base}:{signature}" if signature else base).encode()).hexdigest()[:16]
```

signature 由 `_run_signature`（`trading_graph.py:420-434`）拼出，含 `analysts=`、`debate=`、
`risk=`、`asset=`、`portfolio=`（`portfolio.fingerprint()` 或 `'none'`，
注释说明 "None, an empty book and a changed book are three different runs"）。
这是**正确性防护而非优化**：分析师选择或辩论轮数变了却复用旧检查点，会在形状不匹配的图上续跑，
产生静默错误状态。代价是「改了配置就丢失可续跑性」，属安全侧的合理取舍。

### 5.4 生命周期与图执行集成

`begin_checkpoint`（`trading_graph.py:461-488`）在 `checkpoint_enabled` 为假时返回 `None`
（默认 `False`，`default_config.py:111`）；否则取 signature、进入 `get_checkpointer` 上下文、
`self.graph = self.workflow.compile(checkpointer=saver)`，再查 `checkpoint_step` 设置
`self._resuming`。**续跑时必须传 `None`**（`checkpoint_input` 即
`None if self._resuming else init_state`，`:490-498`），否则初始 state 会经消息 reducer
追加导致重复消息。生命周期被 CLI 与 `propagate()` 共用（`:508-514` 的 `checkpoint_scope`），
修复了 `--checkpoint` 在 CLI 上曾为 no-op 的 bug。CLI 路径（`cli/main.py:1293-1299`）先
`record_decision` 再 `clear_checkpoint_on_success`，即只有跑成功才清理。
`clear_all_checkpoints`（`checkpointer.py:73-87`）必须连同 SQLite 的 `-wal` / `-shm` 一起删；
单条清理走参数绑定的 SQL `DELETE`（`:96-104`）。

### 5.5 与记忆层的对照

| 维度 | `TradingMemoryLog` | Checkpointer |
|---|---|---|
| 目的 / 存储 | 跨跑经验累积；单 markdown 文件 | 单次跑进度恢复；每 ticker 一个 SQLite |
| 生命周期 | 永久（受轮转限制） | 成功后即删 |
| 键 | `(date, ticker)` 文本行 | `sha256(ticker:date:signature)[:16]` |
| 失败语义 | 留 pending，下轮重试 | 保留检查点，下次续跑 |
| 是否影响 LLM 输入 | 是（PM prompt） | 否 |

## 6. Signal Processing

### 6.1 它做什么：从 markdown 决策解析 5 档评级

`signal_processing.py:1-11` 的 docstring 说明它为何不再调用 LLM：PM 的 `PortfolioDecision`
渲染成 markdown 后 "always carries a `**Rating**: X` header"，因此确定性启发式
"is more than sufficient to extract that rating; no extra LLM call is needed"；本模块存在只为
兼容 `process_signal(text)` 接口。`__init__`（`:23-27`）保留 `quick_thinking_llm` 参数但
不存储（"accepted for backwards compatibility but ignored"）。核心只有三行：

```python
# tradingagents/graph/signal_processing.py:29-38（节选）
def process_signal(self, full_signal: str) -> str:
    """Return one of Buy / Overweight / Hold / Underweight / Sell, or REVIEW."""
    rating = extract_rating(full_signal)
    return rating if rating is not None else RATING_REVIEW
```

即**这个类现在是一个兼容层**：曾经「用 LLM 从自由文本抽信号」被「结构化输出保证格式 +
确定性正则抽取」替代，省掉一次 LLM 调用，也消除了抽取环节自身的失败模式（锁定见
`tests/test_signal_processing.py:85-92` 的两处 `assert_not_called()`）。

### 6.2 解决的核心问题：不可判定 ≠ 中性

词汇表与哨兵值集中定义在 `rating.py:23-31`：
`RATINGS_5_TIER = ("Buy", "Overweight", "Hold", "Underweight", "Sell")`，以及
`RATING_REVIEW = "REVIEW"`——其注释说明它不是可交易仓位、"flags output that needs a
human/re-run rather than silently degrading to Hold"；`parse_rating`（`rating.py:81-88`）
的默认值即该哨兵，docstring 强调 "The default is the review sentinel, never a tradeable rating."

```python
# tradingagents/agents/utils/rating.py:59-78（节选，中文为注释转述）
norm = unicodedata.normalize("NFKC", text)   # 全角冒号也能解析
for line in norm.splitlines():
    if _RATING_SCALE_RE.search(line): continue    # 量表行是回显图例，不是结论
    if (m := _RATING_LABEL_RE.search(line)) and m.group(1).lower() in _RATING_SET:
        labelled = m.group(1).capitalize()        # 取最后一个带标签的评级
if labelled: return labelled
named = {m.group(1).capitalize() for m in _RATING_WORD_RE.finditer(norm)}
return named.pop() if len(named) == 1 else None   # 多候选即放弃
```

四个防护点：**NFKC 归一化**（`rating.py:59`）使全角冒号 `Rating：Overweight` 也能解析，
否则会静默降级为 Hold（即 #1170）；**跳过「评级量表」行**（`rating.py:41`、`:66-67`）；
**取最后一个带标签的评级**，因为决策总是先论证后下结论；
**多个不同的裸评级词即返回 `None`**（`rating.py:74-78`），反例是先否定 Buy 再得出
Underweight 的散文会被读成 Buy。失败时**没有任何编造路径**：不可判定就显式暴露为 `REVIEW`，
且它不属于 5 档词汇表，任何 `PortfolioRating(signal)` 映射都必须先判 `is_review`
（`rating.py:91-93`），否则抛错——把静默错误变成显式错误。

## 7. 结构化输出的可靠性工程

共 **6 层防护 + 1 层事后兜底**，每层针对一类有 issue 编号的具体故障模式。

| 层 | 机制 | 失败模式 | 位置 |
|---|---|---|---|
| L1 | `bind_structured` 能力探测 | provider 不支持 structured output | `structured.py:42-56` |
| L2 | `with_structured_output(Schema)` + Pydantic | 输出不合法 JSON / 枚举越界 | `schemas.py` |
| L3 | `invoke_structured_or_freetext` 整体降级 | structured 调用抛错 / 返回 None | `structured.py:59-89` |
| L4 | `_coerce_optional_float` 字段级降级 | 单字段类型错误 | `schemas.py:33-58` |
| L5 | render 期显式命名缺失字段 | 下游无法区分「没给」与「没问」 | `schemas.py:205-208` |
| L6 | `NO_EXTERNAL_TOOLS` 提示 | schema-only 模式下模型误调工具 | `structured.py:36-39` |
| L7 | `extract_rating` + `REVIEW` 哨兵 | 事后解析不出版级 | `rating.py:49-78` |

### 7.1 L1 + L2：绑定与探测

```python
# tradingagents/agents/utils/structured.py:48-56（节选）
    try:
        return llm.with_structured_output(schema)
    except (NotImplementedError, AttributeError) as exc:
        logger.warning("... falling back to free-text generation", agent_name, exc)
        return None
```

关键点是**探测发生在 agent 创建期而非调用期**（`portfolio_manager.py:27`、`trader.py:23`、
`research_manager.py:18`、`sentiment_analyst.py:63`）：一次探测决定该 agent 整段生命周期走结构化
还是纯自由文本。`schemas.py:9-16` 的 docstring 说明选择理由：让每个 provider 走各自原生模式
（`json_schema` / `response_schema` / tool-use），并把 **schema 字段描述当作模型的输出指令**。

### 7.2 L3：整体降级，只降一次，不重试结构化

```python
# tradingagents/agents/utils/structured.py:73-89（节选）
        try:
            result = structured_llm.invoke(prompt)
            if result is None:      # 模型用纯文本作答，parser 拿到 None
                raise ValueError("structured output returned no parsed result")
            return render(result)
        except Exception as exc:
            logger.warning("... retrying once as free text", agent_name, exc)
    return plain_llm.invoke(prompt).content          # 降级路径
```

三个取舍：**`except Exception` 全捕获**，理由是 "malformed JSON from a weak model,
transient provider issue" 都要降级以保证管线不阻塞（`structured.py:10-13`）；
**`result is None` 被显式转成异常**，为「thinking 模型用纯文本作答而不走 tool call」准备，
否则 `render(None)` 会崩（`tests/test_structured_agents.py:196-211` 锁定）；
**只降级一次，不重试结构化**——降级目标就是自由文本。代价：降级只有 `logger.warning`，
调用方无法从返回值区分「结构化成功」与「自由文本降级」，下游只能靠 L7 尽力解析。

### 7.3 L4：字段级降级——最值得移植的一层

触发背景是两个具体 issue：弱模型把 `"None"`/`"N/A"` 写进可空数值字段（#1058），
把百分比写进价格字段导致整份提案校验失败（#1288）。`schemas.py:30` 定义占位符集合
`_NULLISH_FLOAT = {"", "none", "n/a", "na", "null", "nil", "-", "tbd", "unknown"}`；
核心逻辑（`schemas.py:49-58`）是：命中占位符或以 `%` 结尾 → `None`；
否则去掉千分位与货币符号后 `float()`，转换失败（区间、约数）→ `None`。
docstring 给出两条关键判据：百分比**不可救**（把 "15%" 读成 15 会把 $600 股票的止损放到
$15），因此与占位符同样丢弃，让**一个坏字段置空而不是整份提案失败**；非单个数一律丢弃，
因为区间（"150-160"）与约数（"around 150"）会让 pydantic 校验失败并丢掉整份决策。

| 输入形态 | 处理 | 理由 |
|---|---|---|
| `"None"` / `"N/A"` / `"TBD"` | → `None` | 等同「模型没给」 |
| `"15%"` / `" 7.5% "` / `"-10%"` | → `None` | **不可救**：15% 绝不能变成 $15 止损价 |
| `"$1,234.50"` / `"1,180"` | → `1234.5` / `1180.0` | 去千分位与货币符号后可还原 |
| `"150-160"` / `"around 150"` / `"~150"` | → `None` | 不是单个数，宁缺勿错 |

校验器以 `mode="before"` 挂在 `entry_price`/`stop_loss`（`schemas.py:185-188`）
与 `price_target`（`:262-265`）上。测试覆盖 `tests/test_structured_agents.py:103-115`
（三种百分比写法都得到 `None`）、`:127-138`（`entry_price="612.40"`、`stop_loss="15%"` 时
前者保留、后者置空，即**一个字段坏掉不再拖垮整份提案**）与 `:509-519`（parametrize 覆盖
五种区间/约数写法，说明规则按**「能否还原为单个数」这一统一判据**处理）。
它把「整份输出作废 → 降级为自由文本 → 所有字段失去结构保证」这条雪崩路径，
切断为「单个字段置空 → 其余字段保留结构化」。关键边界：该规则**只用于 `float | None`
的可选字段**；必填枚举（`rating`、`action`、`overall_band`）与必填字符串**没有**降级路径——
枚举越界或字段缺失仍是硬失败并触发 L3。

### 7.4 L5：render 期显式命名缺失字段

`render_trader_proposal`（`schemas.py:203-208`）在可选字段为空时写入固定字面量
`'not provided'`，注释说明动机："Named even when absent, so a reader can tell a level the
trader chose not to give from one the schema never asked for."；`render_pm_decision`
（`:285-287`）同理处理 `Price Target` 与 `Time Horizon`；测试断言
`count("not provided") == 3`（`tests/test_structured_agents.py:541-548`）。
**设计意图**：`**Stop Loss**: not provided` 与「根本没有这一行」在文本层几乎不可区分，
但对阅读者与审计者是完全不同的信息——让**缺失本身成为可观测信号**。

### 7.5 L6：schema-only 模式下的工具调用防护

`structured.py:31-39` 的注释解释了这个非直觉约束：schema-only 结构化输出只绑定一个 tool
（即 schema 本身），模型若去调搜索工具就产生未知 tool call，整个结构化尝试被丢弃并转为
自由文本重试（#1130）。解法是在 prompt 里用 `NO_EXTERNAL_TOOLS` 显式声明约束
（`portfolio_manager.py:79`、`research_manager.py:52`），而不是只依赖绑定本身。

### 7.6 L7 与尚未做到的

L7 是 `extract_rating` / `REVIEW`（第 6 节）：即使 L1–L6 全部降级为自由文本，
系统仍要么抽出一个可信评级，要么显式产出 `REVIEW`。**没有任何路径会编造一个评级。**
由此得到一条完整原则：

> 引擎侧用 schema 收窄输出空间，字段侧用降级保住可信部分，渲染侧把缺失显式化，
> 解析侧把不可判定显式化；**每层失败都不会向上扩散为静默错误**。

尚未做到：**没有「修复重试」**（结构化失败即放弃本次结构化收益）；**降级不可观测**
（调用方无法从返回值判断走哪条路径）；**L4 只覆盖数值字段**；`llm_max_retries`
（`trading_graph.py:209-213`）是 SDK 级网络重试，与输出不合规无关。

## 8. 对 Aegis 的可移植结论

Aegis 用 Go + Eino，长期目标是 `Execution → Outcome → Reflection → Proposal → Evaluation → Promotion`
（`docs/08-演进路线与现状.md:239-250`）。以下按机制而非 Python 细节给出判断。

### 8.1 值得吸收

1. **字段级降级优先于整条失败——对应 Aegis 的 Repair 议题。** `docs/06:370` 已明确校验失败当前
   **直接返回 error，不做自动修复**，并计划「最多 1 次 Repair」。`_coerce_optional_float`
   （`schemas.py:33-58`）是更省成本的路径：**可空字段先尝试无损还原，无法还原就置空并保留其余
   字段**，只在必填字段失败时才走 Repair。判据应照搬——**「能否还原为单个数」**；`"15%"` 必须
   置空而不是变成 15。
2. **「缺失」必须显式命名，不能靠省略。** `not provided`（`schemas.py:203-208`）在 Aegis 的 JSON
   契约里的落法是：区分 `"field": null` 与 key 缺省，并让 `Validate` 拒绝二者混用。
3. **不可判定必须是独立状态，不是中性值。** `RATING_REVIEW`（`rating.py:31`）与 `is_review`
   守卫（`:91-93`）应进入 Aegis 的 `Decision`：解析失败时产出 `"unknown"` / `"review"` 这类
   **不可交易状态**，而非退化成中性 Action。Aegis 已把 `Decision` 定位为 Strategy / Risk /
   Backtest / Memory 共同消费的对象（`docs/01:51`），一旦中性值承载「解析失败」，所有下游统计
   都会把失败计入中性样本。`extract_rating` 的**多候选即放弃**规则（`rating.py:77-78`）同理。
4. **反思的 prompt 必须声明评估窗口，并允许「窗口不足以判断」。** `reflection.py:22-34` 与
   `tests/test_memory_log.py:1009-1016` 解决的是：Reflection 拿到的 Outcome 窗口长度可能与
   Decision 声称的时间视野不匹配。若不声明，Reflection 会把「短期内没兑现」写成「判断错误」，
   而这条伪教训会被下一轮当作既定事实。Aegis 的 `as_of` 已解决数据的时间点问题，
   但**尚未解决「结果窗口 vs 判断视野」的语义匹配**。
5. **记忆条目自带「可知时间」，检索按可知时间门禁。** `resolved:YYYY-MM-DD`
   （`memory.py:246-249`）+ `as_of` 过滤（`:86-87`）+ 遗留条目保守排除
   （`tests/test_memory_pointintime.py:57-69`）是 point-in-time 纪律在记忆层的落地。建议 Memory
   条目从第一天就带 `outcome_known_at`，检索强制按它过滤，缺失该字段的条目在历史模式下排除。
6. **Append-only + 原子写 + 幂等键，三件套一起做。** `memory.py:39-47` 的幂等守卫、`:176-178`
   的 temp + `replace` 原子写、只追加不改写的形态，共同保证「同一决策永不重复计数」；
   `tests/test_memory_log.py:139-154` 覆盖了「已结算条目仍须阻断重复写入」这个易漏边界。
   Aegis 若用 SQLite/JSONL 存记忆，应把 `(as_of, ticker, decision_version)` 设为唯一键。
7. **记忆检索从确定性分区起步，不急于上向量检索。** `get_past_context`（`memory.py:91-98`）
   用「同 ticker 最近 5 条全文 + 跨 ticker 最近 3 条反思」即达到可用效果，零额外依赖、
   零额外 LLM 调用、结果完全可复现。建议 Aegis 在 V5（`docs/08:49`）引入 memory 时按同一顺序
   推进，把「结果回流 → 上下文注入」跑通并验证后再考虑 embedding。TradingAgents 甚至删掉了
   原有的 BM25 记忆（`tests/test_memory_log.py:877-891`），说明按角色的语义记忆被证明是过度设计。
8. **膨胀控制：轮转只删已结算，pending 永不删。** `_apply_rotation`（`memory.py:251-286`）的规则
   是「pending 代表未处理工作，必须保留」。注意 TradingAgents 这一项**默认关闭**
   （`default_config.py:80` 为 `None`），导致长期日志无界增长；Aegis 应默认开启上限。
9. **Checkpoint 与 Memory 是两层，不要合并。** 二者正交（见 5.5），值得在 Aegis 目录设计中保持
   分离。另两个细节：**恢复时必须传空输入**，否则初始 state 会被 reducer 重复追加
   （`trading_graph.py:490-498`）；**清理必须删除 WAL/SHM**（`checkpointer.py:73-87`）。
10. **反思失败不得阻断主流程。** `trading_graph.py:377-382` 的 `except` 让 Reflection 失败时条目
    保持 pending 而本次跑照常进行（`tests/test_memory_log.py:949-979` 锁定）。Aegis 的成长闭环里
    Reflection 必然调用 LLM，这条纪律应作为硬约束写进设计。

### 8.2 不该照搬

1. **单文件 markdown + 正则解析的存储形态。** `memory.py` 用 `_SEPARATOR` 切分、用正则解析 tag
   与正文（`memory.py:13-16`、`:288-319`），并用 `[:300]` 硬编码截断（`:335`）。这是「以人为可读
   产物为主」路线的产物。Aegis 的 `Decision` 已是 JSON 契约（`docs/06` 第 2 节），记忆应直接存
   结构化记录（SQLite 表或 JSONL）。退回文本正则会重新引入字段顺序耦合、硬编码截断，以及
   `get_past_context` 未排除 `REVIEW` 这类无法用类型系统防住的缺口。
2. **「同 ticker 才结算」的调度耦合。** `_resolve_pending_entries` 只处理本次 ticker 的 pending
   （`trading_graph.py:353-356` 自述），还需要额外的 `settle_pending()`（`:559-567`）在回测扫尾时
   手动补结算。Aegis 应把 Outcome 结算做成**独立于分析跑的定时任务**：结果何时可得由市场决定，
   不该由「这个 ticker 是否被再次分析」决定。
3. **把「教训注入 prompt」当作学习方法——本节最重要的一条。** TradingAgents 反思闭环的终点是
   **一个 prompt 段落**（`portfolio_manager.py:38-43`），只被一个节点读取。对 TradingAgents 这是
   恰当设计——它的目标是一次性研究质量。但 Aegis 的目标是六阶段自成长，若把 memory 直接接到
   Prompt 上就停下，得到的是「每轮多读几段历史文本」而不是「Agent 能力版本发生变化」——
   **Reflection → Proposal → Evaluation → Promotion 四步全部缺失**。Aegis 若要吸收 memory，
   应明确它是六阶段的前半段（Outcome → Reflection），**并从第一天就设计 Reflection 的结构化
   输出**，使其可被 Proposal 阶段程序化消费。
4. **无评估门禁的自动采纳。** 反思一经生成立即注入，没有任何「这条教训是否成立」的检验。单股
   5 个交易日的 alpha 是极低信噪比信号，而反思 prompt 明确要求产出「一条具体教训」
   （`reflection.py:31`）——这在结构上鼓励在噪声上总结规律。建议区分**「观察」（outcome 数据）
   与「结论」（reflection 文本）**：前者可直接采信，后者在 Promotion 前只作为候选信号。
5. **用区域指数 alpha 做唯一的结果度量。** `_fetch_returns` 的 alpha 是「标的收益 − 基准收益」
   （`trading_graph.py:326-334`）。A 股场景下这套度量的隐含假设不成立：涨跌停导致的成交不可得、
   T+1 限制、行业 beta 远大于大盘 beta，且 `holding_period_days` 默认 5 天
   （`default_config.py:159`）对 A 股短线波动噪声尤其不利。Aegis 应把「结果度量」本身作为可替换
   契约（对应 Capability 思路），而非沿用单一 alpha 定义。
6. **LangGraph `SqliteSaver` 的具体实现细节。** `sha256[:16]`、`saver.setup()`、
   `writes`/`checkpoints` 表名、`get_tuple(config).metadata.get("step")`（`checkpointer.py:59-70`）
   都是 LangGraph 特有形态。可移植的是**判据**而非实现：把影响图形态的配置折入续跑身份
   （`_run_signature`，`trading_graph.py:420-434`）。
7. **反思走廉价模型的固定选择。** `Reflector(self.quick_thinking_llm)`（`trading_graph.py:165`）
   是成本优先的固定绑定。Aegis 明确要求 **per-agent 选供应商**（`docs/05:25` 列出 Reflection
   Agent → 更强模型），且 `configs/config.yaml` 已有 `reflection → claude` 配置（`docs/05:322`）。
   反思质量直接决定长期记忆质量，其成本应单独优化而非默认走最便宜模型。

## 10. 一句话总结

TradingAgents v0.5.0 的记忆是一个**单文件、append-only、文本形态的决策日志**，
反思是**延后到下次同 ticker 跑时、由廉价模型生成的 2–4 句自然语言教训**，
其唯一去向是 **Portfolio Manager prompt 的一个段落**。它完成了「Outcome → 下次 context」
的闭环，但**没有** Proposal / Evaluation / Promotion，**不调整任何 prompt、参数或策略**，
也**不对教训做任何采纳门禁**——称为自我进化是夸大，把它当作可靠的
「结果回流 + 点时间门禁 + 字段级降级」机制来学习是恰当的。最值得 Aegis 优先吸收的是
第 7 节的分层防护与 8.1 的十项机制，尤其是**字段级降级**、**不可判定哨兵**、
**反思窗口声明**与**记忆的可知时间门禁**。
