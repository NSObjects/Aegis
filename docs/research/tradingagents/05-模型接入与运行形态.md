# TradingAgents 模型接入、配置体系与运行形态

本章只讨论 TradingAgents v0.5.0（commit `2d17df8`）的三件事：`tradingagents/llm_clients/` 的多供应商抽象、
`default_config.py` 与 `cli/` 的配置分层、CLI / Docker / 包入口体现的运行形态。Agent 图结构与 Prompt 不在范围内。

> 结论以源码为唯一依据，标注 `路径:行号`；源码未声明的属性（如各模型真实上下文窗口）显式标注「未确认」。

## 1. 多供应商抽象

### 1.1 基类与统一构造入口

`tradingagents/llm_clients/base_client.py:25` 定义唯一抽象基类，抽象面只有两个方法：

```python
class BaseLLMClient(ABC):
    def __init__(self, model: str, base_url: str | None = None, **kwargs):
        self.model = model; self.base_url = base_url; self.kwargs = kwargs   # base_client.py:28-31
    def get_provider_name(self) -> str: ...          # base_client.py:33，取 self.provider，否则由类名推导
    def warn_if_unknown_model(self) -> None: ...      # base_client.py:40
    @abstractmethod
    def get_llm(self) -> Any: ...                     # base_client.py:54，返回类型是 Any
    @abstractmethod
    def validate_model(self) -> bool: ...              # base_client.py:59
```

同文件的自由函数 `normalize_content(response)`（`base_client.py:6-22`）把 OpenAI Responses API、
Gemini 3、Claude extended thinking 返回的"类型化内容块列表"压平成字符串，丢弃 reasoning/metadata 块。

`factory.py:5` 是唯一构造入口：手写 if 链先匹配原生 API（`anthropic`/`google`/`azure`/`bedrock`，
`factory.py:34-48`），其余交给 OpenAI 兼容注册表（`factory.py:50-52`），未知 Provider 抛
`ValueError(f"Unsupported LLM provider: {provider}")`（`factory.py:54`）。Provider 模块惰性 import，
目的是"单独 import factory 不拖入重型 LLM SDK、也不因缺 key 失败"（`factory.py:13-15`）。

### 1.3 各 Provider 客户端

| 客户端 | 底层类 | `get_llm()` 关键行为 | `validate_model()` |
|---|---|---|---|
| `OpenAIClient`（`openai_client.py:258`） | `NormalizedChatOpenAI` / `DeepSeekChatOpenAI` / `MinimaxChatOpenAI` / `LocalCompatibleChatOpenAI` | 注册表驱动 base_url / key / Responses | 查目录（`:338`） |
| `AnthropicClient`（`anthropic_client.py:53`） | `NormalizedChatAnthropic` | 透传白名单含 `effort`，按 `_supports_effort` 门控 | 查目录（`:78`） |

| `BedrockClient`（`bedrock_client.py:41`） | 惰性构造的 `NormalizedChatBedrockConverse` | region 取 `AWS_REGION`/`AWS_DEFAULT_REGION`/`us-west-2`；bearer token 走 `api_key` | 恒 `True`（`:76`） |

## 3. 能力探测（capabilities.py）

### 3.1 标志与判定

```python
StructuredMethod = Literal["function_calling", "json_mode", "json_schema", "none"]
    # capabilities.py:21-26；"none" = 无结构化输出，调用方退回自由文本

@dataclass(frozen=True)
class ModelCapabilities:
    supports_tool_choice: bool; supports_json_mode: bool; supports_json_schema: bool
    preferred_structured_method: StructuredMethod
    requires_reasoning_content_roundtrip: bool = False   # capabilities.py:39
    requires_reasoning_split: bool = False               # capabilities.py:45

def get_capabilities(model_name: str) -> ModelCapabilities:
    if model_name.startswith("deepseek/"):                        # OpenRouter 命名空间剥离
        model_name = model_name.removeprefix("deepseek/")         # capabilities.py:127-128
    if model_name in _BY_ID:                                      # :130 精确 ID 优先
        return _BY_ID[model_name]
    for pattern, caps in _BY_PATTERN:                             # :132 正则次之
        if pattern.match(model_name):
            return caps
    return _DEFAULT                                               # :134 兜底
```

三档预置能力为 `_DEEPSEEK_THINKING`（`:54`）、`_DEEPSEEK_CHAT`（`:62`）、
`_MINIMAX_THINKING`（`:77`）、`_DEFAULT`（`:85`）；正向模式（`^deepseek-v\d`、
`^deepseek-reasoner`、`^MiniMax-M\d`，`:112-116`）让未发布的新版本自动继承怪癖，
前提假设是"模型 ID 演进快于发版"。

### 3.2 上层如何降级

```python
def with_structured_output(self, schema, *, method=None, **kwargs):        # openai_client.py:38
    caps = get_capabilities(self.model_name)
    if caps.preferred_structured_method == "none":
        raise NotImplementedError(
            f"{self.model_name} has no structured-output method available; "
            f"agent factories will fall back to free-text generation.")     # :41-44
    method = method or caps.preferred_structured_method
    if method == "function_calling" and not caps.supports_tool_choice:
        kwargs.setdefault("tool_choice", None)     # 不发 tool_choice，schema 仍作为 tool 绑定
    return super().with_structured_output(schema, method=method, **kwargs)
```

三条降级路径：`method == "none"` 抛 `NotImplementedError` 由 Agent 工厂退回自由文本
（`CHANGELOG.md:36`："A provider without structured output still returns a readable decision."）；
不支持 `tool_choice` 时不发该参数（`:49-50`）；本地/泛化端点由 `LocalCompatibleChatOpenAI`
无条件这么做（`:64-68`）。`MiniMaxChatOpenAI` 走另一条查表路径，由 `requires_reasoning_split`
决定是否注入 `extra_body.reasoning_split`（`:153-162`）。

### 3.3 与能力表并存的第二套机制

Anthropic / Google 的"参数是否被接受"没进能力表，而是在客户端里用正则做版本比较：
`_supports_effort` 用 `claude-(opus|sonnet|fable)-(\d+)(?:-(\d+))?` 配
`_EFFORT_MIN_VERSION = {"opus": (4,5), "sonnet": (4,6), "fable": (5,0)}`（`anthropic_client.py:14-38`）；
`_accepts_minimal_thinking` 判 `gemini-(\d+)\.(\d+)` 且非 pro 且版本 `< (3,8)`（`google_client.py:12-20`）。
同一类知识因此分散在三个文件、两种表达方式里（数据 vs 代码）。另有一个**无消费者**的字段：
`requires_reasoning_content_roundtrip`（全仓 grep 只命中定义处 `capabilities.py:39`），
因为 `DeepSeekChatOpenAI` 是无条件回灌（`openai_client.py:103-129`）。

### 4.3 validators.py：校验是警告而非拒绝

```python
_ANY_MODEL_PROVIDERS = ("ollama", "openrouter", "openai_compatible",
                        "mistral", "kimi", "groq", "nvidia", "bedrock")   # validators.py:8-11
VALID_MODELS = {provider: models for provider, models in get_known_models().items()
                if provider not in _ANY_MODEL_PROVIDERS}                  # :13-17

def validate_model(provider: str, model: str) -> bool:
    provider_lower = provider.lower()
    if provider_lower in _ANY_MODEL_PROVIDERS: return True                # :27
    if provider_lower not in VALID_MODELS:     return True                # :31
    return model in VALID_MODELS[provider_lower]                          # :33
```

规则是"白名单 Provider 才校验，未知 Provider 一律放行"，结果只用于 `warn_if_unknown_model()`
发一条 `RuntimeWarning` 后继续（`base_client.py:40-52`），文案为
`Model '<x>' is not in the known model list for provider '<p>'. Continuing anyway.`
设计意图：Provider 上新模型快于 TradingAgents 发版，硬失败会把"能用"变成"不能用"，
代价是模型名写错只能在第一次 API 调用时暴露；`bedrock` 被列入放行集合与其
"Model ID 由调用方给定"一致（`bedrock_client.py:47-49`）。

## 5. 配置分层

### 5.1 分层结构与环境覆盖

| 层 | 载体 | 生效方式 |
|---|---|---|
| 代码默认 | `default_config.py:72` 的 `DEFAULT_CONFIG` 字面量 | 进程启动时构造 |
| 环境变量 | `_ENV_OVERRIDES`（`default_config.py:10-29`） | **导入时**原地覆盖（`:59-69`） |
| 交互选择 | `cli/main.py:507` 的 8 步问卷 | 覆盖 `DEFAULT_CONFIG` 副本（`cli/main.py:1012-1046`） |
| 上次选择 | `~/.tradingagents/cli_prefs.json`（`cli/prefs.py:27`） | 仅作问卷默认值，从不跳过步骤（`cli/prefs.py:1-15`） |
| 密钥 | 项目 `.env`（`cli/utils.py:665-673`） | 写入后注入当前进程环境 |

覆盖类型由默认值类型推断，非法值抛错而不静默回退：`_coerce` 对 bool 只接受 `true/1/yes/on` 与
`false/0/no/off`，否则 `raise ValueError(f"expected a boolean (...)")`（`default_config.py:36-56`），
`_apply_env_overrides` 再包装成 `Invalid value for {ENV_VAR}: ...`（`:68`），因此

### 5.3 每个 Agent 能否选不同模型？不能，只有两档

`TradingAgentsGraph.__init__` 只创建两个客户端，且共用同一个 `llm_provider` 与 `backend_url`：

```python
deep_client = create_llm_client(provider=self.config["llm_provider"],
    model=self.config["deep_think_llm"],
    base_url=self.config.get("backend_url"), **llm_kwargs)          # trading_graph.py:129-134
quick_client = create_llm_client(provider=self.config["llm_provider"],   # 同一 provider / 同一 base_url
    model=self.config["quick_think_llm"], **llm_kwargs)             # :135-143
```

绑定关系在 `graph/setup.py:76-92`，**12 个 Agent** 全部落在两个实例上（另有 `Reflector` 与 `SignalProcessor` 两个非 Agent 组件）：

| 实例 | 使用者 | 代码位置 |
|---|---|---|
| `quick_thinking_llm` | Market / Sentiment / News / Fundamentals 四个分析师 | `setup.py:76-79` |
| `quick_thinking_llm` | Bull Researcher、Bear Researcher | `setup.py:83-84` |
| `deep_thinking_llm` | Research Manager | `setup.py:85` |
| `quick_thinking_llm` | Trader | `setup.py:86` |
| `quick_thinking_llm` | Aggressive / Neutral / Conservative 三个风险辩手 | `setup.py:89-91` |
| `deep_thinking_llm` | Portfolio Manager | `setup.py:92` |
| `quick_thinking_llm` | Reflector、SignalProcessor | `trading_graph.py:165-166` |

结论：模型是"两档 + 全局 Provider"，没有任何 `agents.<name>.model` 形式的配置项，`llm_provider`
也无 per-agent 变体。设计意图可从绑定结果读出：只有两个"下结论/汇总"角色（Research Manager、
Portfolio Manager）用 deep，其余全部 quick。隐含假设是同一供应商两档的差异足以覆盖所有角色差异——
这意味着"分析师用便宜模型、组合经理用贵模型"可在同供应商内实现，但"分析师用 Qwen、经理用 Claude"做不到。

### 5.4 运行参数的落点

研究深度是唯一的运行参数入口（`cli/utils.py:179-183`）：

```python
DEPTH_OPTIONS = [
    ("Shallow - Quick research, few debate and strategy discussion rounds", 1),
    ("Medium - Middle ground, moderate debate rounds and strategy discussion", 3),
    ("Deep - Comprehensive research, in depth debate and strategy discussion", 5),
]
```

`_build_run_config` 把该值同时写入 `max_debate_rounds` 与 `max_risk_discuss_rounds`，
但环境变量优先：当 `TRADINGAGENTS_MAX_DEBATE_ROUNDS` / `_MAX_RISK_ROUNDS` 存在时保留 env 值
并打印"该半由环境变量设定，所选研究深度对其不生效"，否则才写入问卷结果（`cli/main.py:1022-1032`）。

轮数语义在 `ConditionalLogic`：`should_continue_debate` 用
`state["investment_debate_state"]["count"] >= 2 * self.max_debate_rounds` 作为退出条件
（`graph/conditional_logic.py:52-58`），即"1 轮"= 多空各发言一次；风险辩论同理。
`max_recur_limit` 只透传为 LangGraph `recursion_limit`（`graph/propagation.py:14-16,80`），不在交互流程暴露。

### 5.5 dataflows/config.py 的角色

`tradingagents/dataflows/config.py:6` 维护模块级单例 `_config`：`initialize_config()` 首次
`deepcopy(DEFAULT_CONFIG)`（`:9-13`）；`set_config(config)` 对 dict 值做一层深合并、标量值替换（`:26-30`）；
`get_config()` 返回深拷贝（`:33-37`）。它**不是**第二套配置来源，而是把 `TradingAgentsGraph`
收到的 config 投递给数据层工具的进程内通道：唯一写入点是 `trading_graph.py:116`，
读取点是 9 处数据流模块（如 `dataflows/yfinance_news.py:80` 取 `news_article_limit`、
`dataflows/sec_edgar.py:116` 取 `data_cache_dir`）。代价是配置成为隐式全局状态：同进程先后构造
两个不同 config 的图，后者会覆盖前者的数据层配置（未确认是否有测试覆盖该场景）。

## 8. 对 Aegis 的启示

### 8.1 现状对照

| 维度 | TradingAgents v0.5.0 | Aegis 现状 |
|---|---|---|
| 模型选择粒度 | 全局单 Provider + quick/deep 两档（`setup.py:76-92`） | `default_model` + `agents.<name>.model` override（`internal/config/config.go:40-59`） |
| Provider 声明 | 17 行 `ProviderSpec` 注册表 + 4 个原生客户端（`openai_client.py:212-234`） | `Provider` 枚举 6 个，构造只有 `switch` 一个分支（`internal/llm/manager.go:51-58`） |
| 模型目录 | `MODEL_OPTIONS` + `LEGACY_MODELS` + 校验（`model_catalog.py:96,235`） | 无；只校验 profile 名存在（`config.go:51-57`） |
| 能力表 | `ModelCapabilities` 数据表 + 正则前向兼容（`capabilities.py`） | 无；`ResponseFormatTypeJSONObject` 硬编码（`internal/llm/deepseek.go:35`） |
| 密钥 | Provider→env 名映射表 + `key_optional` + 统一文案（`api_key_env.py`、`openai_client.py:302-315`） | 存 env 名（`ModelConfig.APIKey`），文案在构造处（`deepseek.go:44-57`） |
| 客户端缓存 | 两档实例，构造期创建（`trading_graph.py:129-143`） | `Manager` 按 profile 懒加载 + 互斥锁缓存（`manager.go:27-49`） |
| 运行参数 | `DEFAULT_CONFIG` 字典 + env 覆盖 + 深度问卷 | 无（尚未引入轮数类参数） |

### 8.2 TradingAgents 更强之处

1. **Provider 是数据，不是分支。** 一行 `ProviderSpec` 同时表达 base_url、端点环境变量、是否必须 key、
   用哪个 chat 子类（`openai_client.py:183-234`），新增 Provider = 加一行；而 Aegis 的 `Manager.New`
   是 `switch cfg.Provider`（`manager.go:51-58`），"Provider 元数据"（默认 base_url、env 名、
   是否允许无 key）没有落点。
2. **能力表把模型怪癖从代码变成表格。** `deepseek-v4-pro` 拒收 `tool_choice` 只在
   `capabilities.py:94-98` 出现一次，消费点在 `openai_client.py:49`；Aegis 的同类知识只能写在构造函数里。
3. **密钥环境变量有单一来源。** `PROVIDER_API_KEY_ENV` 同时服务客户端与交互式补 key
   （`api_key_env.py:1-10`）。Aegis 的 `ModelConfig.APIKey` 语义已是"环境变量名"（`deepseek.go:49-57`），
   方向正确，但缺注册表与 `key_optional` 概念。

### 8.3 TradingAgents 更弱之处（Aegis 不应放弃的优势）

1. **没有 per-agent 模型**（5.3 节）：只能两档 + 单 Provider，无法表达"某个 Agent 换供应商"；
   Aegis 的 `ModelProfileForAgent`（`config.go:40-59`）粒度更细，应保留并作为主模型。
2. **配置无 schema、无类型边界**：配置是 `dict`，键名错拼只在读取点变成 `KeyError`；
   `backend_url` 曾跨 Provider 串用产生畸形 URL（`default_config.py:85-90` 注释记录该修复）；
   `dataflows/config.py` 的模块级单例还让配置成为隐式全局状态（5.5）。

### 8.4 可落地的改进建议

1. **增加 Provider 元数据表（对应 `ProviderSpec`）**：登记默认 `BaseURL`、端点覆盖环境变量名、
   是否允许无 key、占位 key、由哪个构造函数处理，让 `Manager.New` 变成"查表 + 调用登记的工厂函数"。
2. **引入 `internal/llm/capabilities` 数据表**：字段对应 `SupportsToolChoice` /
   `PreferredStructuredMethod`（`function_calling` / `json_object` / `none`）/
   `RequiresReasoningContentRoundtrip`，消费点放在 ModelConfig→Eino 构造处，替代 `deepseek.go:35` 的常量。
3. **为 profile 增加可机读属性与启动期校验**：把 `context_window`、`supports_tool_call`、
   `structured_method` 做成结构化字段，加载时校验"Agent 引用的 profile 是否满足其契约要求"，
   把错误从运行期前移到启动期（现有 profile 存在性校验已是雏形）。
4. **保留 per-agent override，叠加"命名档位"作为可选糖**：解析顺序
   `agents.<name>.model` > `agents.<name>.tier: quick|deep` > `default_model`，既保住细粒度，
   又省去重复写同名 profile。
5. **密钥解析统一为"注册表 + 明确语义"**：保留 `api_key_env`（存变量名），补齐 Provider→默认 env 名
   注册表、`key_optional` 标志（本地端点发占位 key 而非报错）、统一缺失文案
   （形如 `openai_client.py:311-315`）。
6. **运行参数进配置结构**：轮数与递归上限应像 `DEFAULT_CONFIG` 一样进 `internal/config` 并支持
   环境覆盖，同时提供"档位→多参数"映射（对应 `research_depth` → 两个轮数键，`cli/main.py:1032`）。
7. **两处不要照搬**：`get_llm() -> Any` 让抽象在运行期泄漏到 langchain（1.3 节），而 Aegis 的
   `Manager` 返回 `model.BaseModel[*schema.AgenticMessage]` 有类型边界；
   `requires_reasoning_content_roundtrip` 这类"声明了但没有消费者"的标志位（3.3 节）要么接线，要么不写。
