# TradingAgents 整体架构：图、状态与运行生命周期

本章基于 TradingAgents **v0.5.0**（commit `2d17df8`，2026-09-17）的源码，描述它的执行模型、状态契约、控制流与一次完整运行的生命周期。
所有结论均标注 `路径:行号`，可回源核对。

---

## 1. 定位与代码规模

TradingAgents 是一个**多 Agent 投研流水线**：给定一个 ticker 与一个交易日期，走完「分析师研究 → 多空辩论 → 交易计划 → 风控辩论 → 最终决策」五段流程，输出一份报告树与一个五档评级。

| 部分 | 行数 | 说明 |
|---|---|---|
| `tradingagents/`（核心包） | ~9,450 | Agent、图、数据层、模型客户端 |
| `cli/` | ~2,420 | 交互式命令行与配置 |
| `tests/` | ~10,400 | 测试占比很高，含大量回归用例 |
| 合计 | ~22,290 | Python |

值得注意的第一印象：**测试体量超过核心包**（10.4k vs 9.5k）。源码里大量 `#1088`、`#1169`、`#1251` 形式的 issue 引用注释，说明这是一个被真实缺陷反复打磨过的工程，而不是 demo。这本身就值得当作研究对象。

---

## 2. 执行模型：StateGraph + 条件边

框架基于 **LangGraph**，核心是一个 `StateGraph`：

- **节点（Node）** = 一个 Agent（或一个 ToolNode，或一个「清空消息」节点）
- **边（Edge）** = 确定性流转
- **条件边（Conditional Edge）** = 由 `ConditionalLogic` 里的纯函数决定下一跳
- **状态（State）** = 在图节点之间传递的 TypedDict

关键判断：**真正控制执行流程的不是 Agent，而是 `ConditionalLogic`。**
Agent 只负责「产生内容」，循环轮数、谁下一个说话、什么时候停止，全部由普通 Python 函数根据 state 字段决定（`tradingagents/graph/conditional_logic.py:52`、`:63`）。这个区分很重要——它意味着整个系统是**可预测、可测试**的，而不是让 LLM 自己决定流程。

```text
                                              │     │                            │
                                              └─────┘  (count >= 3*max_risk_      │ setup.py:154
                                                        discuss_rounds 时转向      ▼

```

三条结构性特征：

1. **分析师是串行流水线**，不是并行 fan-out。每个分析师跑完自己的一轮 tool 循环、清空消息、再交给下一个（`setup.py:133`）。
2. **两段辩论都是「轮流发言 + 计数退出」**，不是让 LLM 决定何时停止。
3. **消息会被主动清空**（`Msg Clear X` 节点，`create_msg_delete()`）：每个分析师结束后清掉 `messages`，避免上下文越滚越长。这是一个务实的成本控制手段，代价是后面的 Agent 拿不到前面的原始对话，只能拿到被写进 state 的**报告字段**。

### 3.1 防御性设计：path_map 必须完整

`setup.py:32` 与 `:37` 定义了两个 `path_map`，**把路由器可能返回的所有目标都列全**：

```python
DEBATE_PATH_MAP = {
    "Bull Researcher": "Bull Researcher",
    "Bear Researcher": "Bear Researcher",
    "Research Manager": "Research Manager",
}
```

注释说明了原因（`setup.py:28-31`）：条件路由器返回的是**字符串标签**，一旦 prompt、多语言或重构导致标签漂移，返回值就会命中一个不存在的 `path_map` 条目，让 LangGraph 在运行中途崩溃（#1088）。

> **这是本框架最值得警惕的脆弱点**：用自然语言前缀（`current_response.startswith("Bull")`，`conditional_logic.py:59`）决定控制流。它的补救方式不是去掉字符串路由，而是把路径表补全。移植到强类型语言时，这个风险应当被彻底消除——用枚举或显式状态位代替字符串前缀匹配。

## 4. 状态契约

状态定义在 `tradingagents/agents/utils/agent_states.py`，根类型继承 LangGraph 的 `MessagesState`（`:47`）：

```python
class AgentState(MessagesState):
    company_of_interest: Annotated[str, "Company that we are interested in trading"]
    asset_type: Annotated[str, "Asset type under analysis such as stock or crypto"]
    instrument_context: Annotated[str, "Deterministic ticker identity resolved at run start"]
    trade_date: Annotated[str, "What date we are trading at"]

    sender: Annotated[str, "Agent that sent this message"]

    # research step
    market_report: Annotated[str, "Report from the Market Analyst"]
    sentiment_report: Annotated[str, "Report from the Sentiment Analyst"]
    news_report: Annotated[str, "Report from the News Researcher of current world affairs"]
    fundamentals_report: Annotated[str, "Report from the Fundamentals Researcher"]

    # researcher team discussion step
    investment_debate_state: Annotated[InvestDebateState, "..."],
    investment_plan: Annotated[str, "Plan generated by the Analyst"],
    trader_investment_plan: Annotated[str, "Plan generated by the Trader"],

    # risk management team discussion step
    risk_debate_state: Annotated[RiskDebateState, "..."],
    final_trade_decision: Annotated[str, "Final decision made by the Risk Analysts"],

    past_context: Annotated[str, "Memory log context injected at run start (...)"],
    portfolio_context: Annotated[str, "Caller-supplied holdings and cash, ..."],
```

两个辩论状态各自带 `count` 与 `judge_decision` 字段（`:8`、`:22`），它们是**控制流的状态载体**——`count` 用于退出判定，`judge_decision` 用于把裁判结论单独留存。

### 4.1 信息传递是「字段」而不是「闲聊」

Agent 之间**不通过自然语言对话传递信息**，而是通过具名 state 字段：

| 生产者 | 字段 | 消费者 |
|---|---|---|
| Market / Sentiment / News / Fundamentals Analyst | `*_report` | Bull / Bear Researcher |
| Bull / Bear Researcher | `investment_debate_state.{bull,bear}_history` | Research Manager |
| Research Manager | `investment_plan` | Trader |
| Trader | `trader_investment_plan` | 三个风控辩手 |
| 三个风控辩手 | `risk_debate_state.*_history` | Portfolio Manager |
| Portfolio Manager | `final_trade_decision` | 外部（signal 解析、报告落盘、记忆日志） |
| 记忆日志 | `past_context` | **所有** Agent（运行开始时注入） |
| 调用方 | `portfolio_context` | 所有 Agent |

这套「字段即接口」的写法是它可测试、可恢复的基础：任意节点崩溃后，只要 state 已持久化，就能从断点续跑。

## 5. 控制流：三种路由

`ConditionalLogic`（`tradingagents/graph/conditional_logic.py`）只有三类逻辑：

### 5.1 分析师 tool 循环

```python
def should_continue_market(self, state: AgentState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools_market"
    return "Msg Clear Market"
```

四个分析师各有一份（`:14`、`:22`、`:36`、`:44`），逻辑完全相同，只是标签不同。**这是典型的 ReAct 循环**：Agent 想调工具 → 去工具节点 → 回到 Agent；不再调工具 → 收尾。

### 5.2 多空辩论

```python
def should_continue_debate(self, state: AgentState) -> str:
    if state["investment_debate_state"]["count"] >= 2 * self.max_debate_rounds:
        return "Research Manager"
    if state["investment_debate_state"]["current_response"].startswith("Bull"):
        return "Bear Researcher"
    return "Bull Researcher"
```

退出条件是**轮数硬上限**（默认 `max_debate_rounds=1` → 2 次发言），交替靠**回复文本前缀**判断上一个说话人。

### 5.3 风控三方辩论

`:63` 结构相同，退出条件为 `count >= 3 * max_risk_discuss_rounds`，三方按 Aggressive → Conservative → Neutral 轮转。

**结论**：所谓「多 Agent 辩论」，在这套实现里就是**有限轮数的轮流调用 + 把对方发言拼进自己的 prompt**。它不包含「是否继续辩论」的智能判断——轮数是配置项，不是决策。这既是它的简单之处，也是它的局限：一个证据已经充分一致的标的，仍然会跑满配置的轮数。

## 6. 动态图：分析师执行计划

被选中的分析师不是硬编码的，而是由一份 dataclass 计划生成（`tradingagents/graph/analyst_execution.py:20`）：

```python
ANALYST_NODE_SPECS: dict[str, AnalystNodeSpec] = {
    "market": AnalystNodeSpec(

    "social": AnalystNodeSpec(   # 线值保持 social 以兼容已保存配置

    ...
}

def build_analyst_execution_plan(selected_analysts) -> AnalystExecutionPlan:
    ...
    if not specs:

```

`setup_graph()` 遍历 `plan.specs` 批量注册 `agent / clear / tool` 三个节点，并按顺序连边（`setup.py:99-101`、`:124-135`）。

**值得吸收的点**：用一张声明式表描述「一个角色需要哪几个节点 + 报告写到哪个字段」，使「增删分析师」变成改数据而不是改流程。这正是 Aegis 想要的「Agent 只是当前版本的 Composition」的具体做法。

同文件还提供 `AnalystWallTimeTracker`（`:76`）用于统计每个分析师的墙钟耗时——纯粹的产品化细节，但说明它把**运行耗时**当作一等观测对象。

## 7. 一次运行的完整生命周期

入口是 `TradingAgentsGraph`（`tradingagents/graph/trading_graph.py:96`）。

### 7.1 构造期（`:96-180`）

```text
读取 config（默认 DEFAULT_CONFIG）
  ↓
set_config(config)                     注入数据层全局配置
  ↓
创建两个 LLM 客户端                     deep_think_llm / quick_think_llm
  ↓
创建 TradingMemoryLog                  决策记忆日志
  ↓
创建四个 ToolNode                      market / social / news / fundamentals
  ↓
创建 ConditionalLogic(max_debate_rounds, max_risk_discuss_rounds)
  ↓
创建 GraphSetup / Propagator / Reflector / SignalProcessor
  ↓
setup_graph(selected_analysts) → compile()
```

### 7.2 运行期：先结算历史，再开始本次分析

这是**整个框架最精巧的设计**。`create_run_state()`（`:539`）：

```python
def create_run_state(self, company_name, trade_date, asset_type="stock", portfolio=None):
    self._resolve_pending_entries(company_name)          # ① 先结算本 ticker 的旧决策
    return self.propagator.create_initial_state(
        company_name, trade_date, asset_type=asset_type,
        past_context=self.memory_log.get_past_context(      # ② 注入历史教训
            company_name, as_of=self._memory_as_of(trade_date)
        ),
        instrument_context=self.resolve_instrument_context(  # ③ 注入确定的标的身
            company_name, asset_type, trade_date
        ),
        portfolio_context=portfolio.render(company_name) if portfolio is not None else "",
    )
```

三步各有明确目的：

**① `_resolve_pending_entries`（`:346`）——把「上次的判断」变成「这次的教训」**

```python
pending = [e for e in self.memory_log.get_pending_entries() if e["ticker"] == ticker]
...
raw, alpha, days, resolution_date = self._fetch_returns(
    ticker, entry["date"], self.config.get("holding_period_days", 5), benchmark=benchmark)
if raw is None:
    continue                      # 价格还没出来，下次再说
reflection = self.reflector.reflect_on_final_decision(
    final_decision=entry.get("decision", ""), raw_return=raw,
    alpha_return=alpha, benchmark_name=benchmark, holding_days=days)
...
self.memory_log.batch_update_with_outcomes(updates)   # 原子批量写
```

要点：
- 只有**同一 ticker** 的待结算条目会在本次运行时结算，其他 ticker 的条目要等它自己被跑（源码在 docstring 里明确承认这个 trade-off）
- 持有窗口没走完（`len(stock) <= holding_days`）就**保持 pending**，绝不用部分数据提前结算（#1169）
- 反思调用失败**不阻断**本次分析，条目留待下次（`:377-382`）

**② `_memory_as_of`（`:409`）——时间点正确性的关键**

```python
def _memory_as_of(self, trade_date) -> str | None:
    td = str(trade_date)
    return td if td < datetime.now().strftime("%Y-%m-%d") else None
```

回测/历史运行时，只注入**在该交易日之前已经结算**的教训；实盘当日运行则关闭过滤。配合 `_fetch_returns` 返回的 `resolution_date`（「最后使用的价格 bar 的日期，即结果已知之时」，#1251），它保证了**不会把未来才知道的教训喂给过去的决策**。

**③ `resolve_instrument_context`（`:396`）——确定性标的身**

运行开始时用一次**确定性的 yfinance 查询**（带缓存、失败开放）把 ticker 解析成真实公司身份，注入 `instrument_context`，让所有 Agent 锚定真实标的，而不是从价格图里幻觉出一家公司（#814）。

### 7.3 执行与收尾（`:579`）

```python
init_agent_state = self.create_run_state(...)
graph_input = self.checkpoint_input(init_agent_state)   # 续跑时传 None
final_state = self.graph.invoke(graph_input, **args)
self.curr_state = final_state
self._log_state(trade_date, final_state)                # 写 full_states_log_<date>.json
self.record_decision(company_name, trade_date, final_state)   # 写入记忆日志（pending）
self.clear_checkpoint_on_success(...)                   # 成功后清 checkpoint
return final_state, self.process_signal(final_state["final_trade_decision"])
```

**闭环在这里合成**：本次运行结束 → 决策写入记忆日志并标记 pending → 下次同 ticker 运行开始时 → 取实现收益 → 生成反思 → 写回日志 → 作为 `past_context` 注入。

## 8. 双层模型（quick / deep）

框架用**两个模型档位**贯穿全图（`:129-143`，默认 `deep_think_llm` / `quick_think_llm`）：

| 档位 | 用在哪些节点 | 依据 |
|---|---|---|
| `quick_thinking_llm` | 四个分析师、Bull/Bear、Trader、三个风控辩手、`Reflector`、`SignalProcessor` | `setup.py:88-96`、`trading_graph.py:165-166` |
| `deep_thinking_llm` | Research Manager、Portfolio Manager | `setup.py:90`、`:93` |

分工逻辑清晰：**产出信息/参与辩论的节点用快模型，做最终判断与仲裁的节点用强模型**。
注意 `Reflector` 用 quick 模型（`trading_graph.py:165`）——反思被当作轻量任务。

`_get_provider_kwargs()`（`:182`）把「供应商特有的思考参数」收敛在一处：

| 配置项 | 适用 Provider | 用途 |
|---|---|---|
| `google_thinking_level` | google | 思考档位 |
| `openai_reasoning_effort` | openai | 推理强度 |
| `anthropic_effort` | anthropic | 推理强度 |
| `temperature` | 跨供应商 | 采样温度 |
| `llm_max_retries` | 跨供应商 | SDK 重试预算（#1091） |
| `max_tokens` | 跨供应商 | 输出上限；Google 下改名 `max_output_tokens`（#1204） |

## 9. Checkpoint 与恢复

`checkpoint_enabled` 打开后，图会被**重新编译并挂上 per-ticker 的 `SqliteSaver`**（`begin_checkpoint`，`:461`）：

```python
saver = self._checkpointer_ctx.__enter__()
self.graph = self.workflow.compile(checkpointer=saver)
step = checkpoint_step(self.config["data_cache_dir"], company_name, str(trade_date), signature)
self._resuming = step is not None
return thread_id(company_name, str(trade_date), signature)
```

三个细节值得注意：

1. **`thread_id` 里编码了「图形状签名」**（`_run_signature`，`:420`）：分析师选择、辩论轮数、风控轮数、资产类型、持仓指纹。任何一个变了就换 thread，**从新开始而不是悄悄续跑一个形状不同的图**（#1089）。
2. **续跑时必须传 `None` 而不是初始 state**（`checkpoint_input`，`:490`）：重传初始 state 会经消息 reducer 追加，导致消息重复（#1249）。
3. **成功后清除 checkpoint**（`:516`），避免下次误用陈旧状态。

## 11. 设计评估

### 值得吸收

| 机制 | 为什么 |
|---|---|
| **字段即接口的 State 契约** | Agent 之间不闲聊，靠具名字段传递；可测试、可恢复、可断言 |
| **控制流外置到纯函数** | 轮数/路由/退出全部是普通函数，可单测，不受 LLM 波动影响 |
| **声明式节点计划** | 增删角色是改数据不是改流程 |
| **运行开始先结算旧决策** | 把「结果」自动转成「下次的上下文」，是自成长闭环的最小可用形态 |
| **`as_of` 过滤 + `resolution_date`** | 严格防止把未来信息注入历史决策 |
| **图形状签名进 thread_id** | 配置变更不会被误当成续跑 |
| **报告树与 state 日志双落盘** | 人读 Markdown，机读 JSON |
| **失败不阻断主流程** | 反思/结算失败只记日志，留待下次 |

### 应当警惕或改造

| 问题 | 说明 |
|---|---|
| **字符串前缀决定控制流** | `current_response.startswith("Bull")` 这类判断极其脆弱，靠补全 `path_map` 兜底。强类型实现应改为枚举/显式状态位 |
| **辩论轮数不可自适应** | 轮数是配置常量，不随证据冲突程度变化；一遍跑满 |
| **分析师串行** | 四个分析师依次执行，端到端延迟是累加的；无并行 fan-out |
| **消息清空后信息降级为文本** | 后续 Agent 只看到报告字符串，原始 tool 结果丢失 |
| **记忆结算的 ticker 局限** | 其他 ticker 的待结算条目会长期堆积，需外部调度 `settle_pending` 补偿 |
| **`Memory`/`Config` 走全局单例** | `set_config` 注入数据层全局状态，不利于并发多实例 |

### 与 Aegis 的关系

TradingAgents 的**图形态**（分析师流水线 → 多空辩论 → 交易计划 → 风控辩论 → 组合决策）不适合直接搬到 A 股短线场景：它以「给定一只股票，产出一份高质量判断」为目标，**没有把「当前市场环境适合什么打法」提升为第一层决策**。Aegis 的第一问必须是「现在是什么市场」，而不是「这只股票怎么样」。

但它的**机制层**几乎全部可移植，尤其是第 7.2 节的「先结算历史、再注入教训」与第 4 节的「字段即接口」——这两点是 Aegis 实现「Agent 自成长」时最直接可用的参考。
