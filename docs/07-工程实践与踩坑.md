# Aegis 工程实践与踩坑记录

本文档整理 Aegis 接入 CloudWeGo Eino 与 DeepSeek 过程中形成的工程结论，涵盖模型组件选型、可观测性（Callback / visual debug plugin）、结构化输出调试、Skill Runtime 实践、Eino API 版本差异，以及确定性测试与真实集成测试的分层策略。文中错误信息、代码与日志均取自实际接入过程，作为后续开发与排障的基线。

## 1. 模型组件选型：agenticdeepseek

`agenticdeepseek` 是 Eino Ext 面向 agentic 场景的 DeepSeek 模型组件，位于 `github.com/cloudwego/eino-ext/components/model/agenticdeepseek`。它是 `model.AgenticModel` 的实现，即 `model.BaseModel[*schema.AgenticMessage]`，不是 Agent，也不是普通 `ChatModel`。职责只有一件事：接收 `[]*schema.AgenticMessage`，调用 DeepSeek，返回 `*schema.AgenticMessage`。

选用它的原因是 AgenticMessage 路径：`schema.AgenticMessage` 用 `ContentBlocks` 表达内容，原生支持 reasoning 内容与更复杂的 tool call 组合，避免以后从 `schema.Message` 迁移时重做 Agent、Runner、Tool 调用链与上下文处理。

| 维度 | ChatModel | AgenticModel |
|---|---|---|
| 消息类型 | `schema.Message` | `schema.AgenticMessage` |
| Tool Calling / ReAct | 支持 | 支持 |
| 多模态 / 结构化内容 | 相对传统 | 更原生 |
| Reasoning 内容 | 普通消息体系 | `AgenticMessage` 原生支持 |
| ADK Agent 配置 | `ChatModelAgentConfig` | `TypedChatModelAgentConfig[*schema.AgenticMessage]` |
| 生态成熟度 | 更成熟 | 相对新，API 仍在演进 |

边界必须分清：AgenticModel 是模型层，ADK Agent 才是 Agent 层。Tool 不属于模型，`agenticdeepseek` 不需要 `WithTools()`；Tool 由 Agent 通过 `ToolsConfig` 持有，调用时经 Eino 的 `model.WithTools` 传入。

```go
func newDeepSeek(ctx context.Context, cfg config.ModelConfig) (model.BaseModel[*schema.AgenticMessage], error) {
	return agenticdeepseek.New(ctx, &agenticdeepseek.Config{
		APIKey:  apiKey,          // 必填，从环境变量读取，不写进代码
		BaseURL: cfg.BaseURL,     // 默认 https://api.deepseek.com
		Model:   cfg.Model,       // 必填
		Timeout: 120 * time.Second,

		ResponseFormatType: agenticdeepseek.ResponseFormatTypeJSONObject,
	})
}
```

`Timeout` 是单次请求最大等待时间；若设置了 `HTTPClient`，`Timeout` 不生效。`ResponseFormatTypeJSONObject` 对应 `json_object`，是结构化输出的第一道保障（见第 6 节）。

## 2. 类型不匹配：`*Model` 不能当作 `model.BaseModel[M]`

### 现象

用非泛型兼容别名创建 Agent 时编译失败：

```text
无法将 dp (类型 *Model) 用作类型 model.BaseModel[M]
类型未实现 model.BaseModel[M]
需要方法: Generate(ctx context.Context, input []*schema.Message, opts ...Option) (*schema.Message, error)
具有方法: Generate(ctx context.Context, in []*schema.AgenticMessage, opts ...model.Option) (*schema.AgenticMessage, error)
```

### 原因

`ChatModelAgentConfig` 是兼容别名，类型参数被固定为 `*schema.Message`：

```text
ChatModelAgentConfig = TypedChatModelAgentConfig[*schema.Message]
```

而 `agenticdeepseek.Model` 实现的是 `BaseModel[*schema.AgenticMessage]`。两者是不同的 Go 泛型实例，不能互相赋值；错误信息已指明差异在 `Generate` 的输入输出类型。

### 解决

显式指定类型参数为 `*schema.AgenticMessage`：

```go
agent, err := adk.NewTypedChatModelAgent[*schema.AgenticMessage](
	ctx,
	&adk.TypedChatModelAgentConfig[*schema.AgenticMessage]{
		Name:        "aegis",
		Description: "Aegis trading research agent",
		Instruction: instruction,
		Model:       dp,
		ToolsConfig: adk.ToolsConfig{
			ToolsNodeConfig: compose.ToolsNodeConfig{Tools: tls},
		},
	},
)

runner := adk.NewTypedRunner[*schema.AgenticMessage](
	adk.TypedRunnerConfig[*schema.AgenticMessage]{
		Agent:           agent,
		EnableStreaming: true,
	},
)
```

完整类型链路：`agenticdeepseek.Model → BaseModel[*schema.AgenticMessage] → NewTypedChatModelAgent[*schema.AgenticMessage] → TypedChatModelAgentConfig[*schema.AgenticMessage] → NewTypedRunner[*schema.AgenticMessage]`。不要为绕过该错误退回普通 `deepseek.ChatModel`，那只是绕开问题，并未验证 agentic 路径。

## 3. `TypedRunnerConfig` 没有 `handler` 字段

### 现象

把 Callback 放进 Runner 配置时编译失败，提示 `unknown field Handler`：

```go
adk.TypedRunnerConfig[*schema.AgenticMessage]{
	Agent:           agent,
	EnableStreaming: true,
	Handler:         handler, // 编译失败
}
```

### 原因

`adk.TypedRunnerConfig[M]` 只有 `Agent`、`EnableStreaming`、`CheckPointStore` 三个字段。Callback 属于**单次运行**的选项，不是 Runner 的静态配置。

### 解决

通过 `Run()` 的 `adk.WithCallbacks(...)` 传入：

```go
events := runner.Run(
	ctx,
	[]*schema.AgenticMessage{schema.UserAgenticMessage("分析 600519 当前短线状态。")},
	adk.WithCallbacks(handler),
)
```

同时区分两套机制：`adk.WithCallbacks(...)` 注册 Callback handler，用于观测 `OnStart / OnEnd / OnError`；Agent Config 上的 `Handlers` 注册 `TypedChatModelAgentMiddleware`，用于改写 Instruction、注入 Tool（Skill / Filesystem middleware 走这条）。

## 4. 可观测性 / Callback

Eino Callback 覆盖 Agent、Agentic Agent、Agentic Model、Tool、ToolsNode、ChatModel、Graph / Chain / Lambda，每个组件都有 `OnStart / OnEnd / OnError` 生命周期并支持 streaming 输入输出，是 logging / tracing / metrics 的统一接入点。注册 Tool 回调无需自行实现 `CallbackHandler`，用 `callbacksHelper.NewHandlerHelper()`：

```go
handler := callbacksHelper.NewHandlerHelper().
	Tool(&callbacksHelper.ToolCallbackHandler{
		OnStart: func(ctx context.Context, info *callbacks.RunInfo, input *tool.CallbackInput) context.Context {
			log.Printf("[tool:start] %s input=%s", info.Name, input.ArgumentsInJSON)
			return ctx
		},
		OnEnd: func(ctx context.Context, info *callbacks.RunInfo, output *tool.CallbackOutput) context.Context {
			if output.ToolOutput != nil {
				log.Printf("[tool:end] %s tool_output=%+v", info.Name, output.ToolOutput)
			} else {
				log.Printf("[tool:end] %s output=%q", info.Name, output.Response)
			}
			return ctx
		},
		OnError: func(ctx context.Context, info *callbacks.RunInfo, err error) context.Context {
			log.Printf("[tool:error] %s: %v", info.Name, err)
			return ctx
		},
	}).
	Handler()
```

第一版只监听 Tool，确认生命周期正常后再加入 Agent / AgenticModel、token 与 latency。典型日志：

```text
2026/09/21 10:21:56 [tool:start] market_snapshot
2026/09/21 10:21:56 [tool:start] technical_indicators
2026/09/21 10:21:56 [tool:end] market_snapshot
2026/09/21 10:21:56 [tool:end] technical_indicators
2026/09/21 10:21:56 [tool:start] news_search
2026/09/21 10:21:56 [tool:end] news_search
```

这套日志的价值在于判断「Agent 是否真的自主选择了工具」：`market_snapshot` 与 `technical_indicators` 几乎同时 start，说明 Tool 调用可以并发、交叉，并非固定流水线；不同问题产生不同调用集合；后续 `news_search`、`market_overview` 的出现说明模型基于已有结果继续推进；同时可确认是否出现重复调用、信息足够后是否停止。

层次要分清：Eino Callback 负责「什么时候、什么组件、什么数据被触发」，`log.Printf` 只是当前阶段的输出方式；以后接 tracing / metrics / Langfuse / OpenTelemetry 只替换输出层，不改 Agent。另外 `AgenticAgentCallbackHandler.OnEnd` 中的 Events iterator 需异步消费以避免阻塞，早期刻意不在 `OnEnd` 内处理 Events。

## 5. Eino 官方 visual debug plugin

接入方式：插件以编排产物为调试对象，生命周期为 `devops.Init()` → 编排产物注册 → 至少 `Compile()` 一次。当前 `cmd/aegis/main.go` 保留：

```go
if err := devops.Init(ctx); err != nil {
	log.Fatal(err)
}
```

解决的问题：以节点级视图展示 Graph / Chain 的结构与数据流，用于观察编排层（节点、边、输入输出），而不是 Agent 内部的 ReAct 循环。

暂缓接入的取舍：

- 现象：插件已接入，但当时 Aegis 的初始化、Tool 创建、Agent 创建与 Run 全部堆在单一 `main.go`，且 Agent 路径是 `AgenticModel → TypedChatModelAgent → Runner`，与插件擅长的 Graph / Chain / StateGraph 调试对象不一致。
- 原因：插件的调试目标是 Graph / Chain 编排产物，而 V1 的主体价值在 Agent Loop 与 Tool Selection；为了「让插件看得到东西」把 Agent Loop 拆成 Graph Node，等于迁就调试工具改架构。
- 解决：V1 暂缓可视化，只把「组装」与「运行」从 `main.go` 中拿出来，让 `internal/agent/trading` 成为 Agent 入口，`main.go` 只负责初始化与运行。结构调整为 Agent Layer（ADK Agent + Agent Loop + Tools）先行，Orchestration Layer（Graph：Market Context / Strategy / Research / Decision / Risk）在确实需要确定性流程时再引入。不要为可视化提前把 Agent 改造成 Graph。

## 6. 结构化输出与 JSON 失败排查

### 现象

```text
invalid decision JSON: unexpected end of JSON input
output:

invalid decision JSON: invalid character 'I' looking for beginning of value
output: I'll gather the necessary data for 600519.{"symbol":"600519", ...}
```

### 原因

1. **输出被自然语言包裹**：模型在 JSON 前输出过渡文字，`json.Unmarshal` 从首字符 `I` 开始解析而失败。
2. **Prompt 不是可靠的协议约束**：Instruction 已写明「最终输出必须是合法 JSON，不要在 JSON 前后添加其他文字」，模型仍可能先输出说明再输出 JSON。
3. **中间文本混入最终输出**：Agent Loop 中间轮次可能带少量 assistant text；若用 `output += text` 聚合，得到「中间文字 + 中间文字 + JSON」，必然解析失败。
4. **Tool 失败导致本轮终止、输出为空**：`tushareMcp_rt_k` 返回权限错误（原始错误 `tushare API 错误 [40203]: 没有 rt_k 访问权限`）→ Tool 返回 error → Agent 本轮终止 → 没有 final message → `output == ""` → 对空字符串 `json.Unmarshal` → `unexpected end of JSON input`。报错指向 Decision，真实错误在 Tool。
5. **约束不足导致字段类型漂移**：`evidence` / `risk` 输出单个字符串而非数组，或 `action` 取契约外值。

### 解决

第一，开启 DeepSeek JSON 模式：

```go
ResponseFormatType: agenticdeepseek.ResponseFormatTypeJSONObject,
```

拿到的是合法 JSON 字符串，不再需要 `strings.Index("{")` / `strings.LastIndex("}")` 这类截取作为正式方案。

第二，在 Prompt 中强化结构约束：

```text
最终输出必须是合法 JSON，不要使用 Markdown 代码块，不要在 JSON 前后添加其他文字。

evidence 和 risk 必须始终输出为 JSON 字符串数组。
即使只有一条，也必须使用数组，不能输出为单个字符串。

action 只能使用：WATCH / AVOID / CANDIDATE
confidence 必须是 0 到 1 之间的小数。
不要输出 BUY 或 SELL。

正确示例：
{
"symbol": "600519",
"market_view": "当前短线状态判断",
"evidence": ["证据1", "证据2"],
"risk": ["风险1", "风险2"],
"action": "WATCH",
"confidence": 0.6
}
```

第三，只取最后一个非空 assistant text，不做拼接；结构化最终结果使用非流式 Runner（`EnableStreaming: false`）：

```go
text := strings.TrimSpace(assistantText(event.Output.MessageOutput.Message))
if text != "" {
	// Agent Loop 中间可能发生多轮 Tool Calling，
	// 最后一个有效 assistant 输出才是需要的 JSON。
	output = text
}
```

若 UI 需要实时进度，应通过 Agent Event / Callback 实现，而不是依赖 token streaming。

第四，在 Go 边界防御：运行 event 时优先检查 Agent error，解析前检查空输出。

```go
for {
	event, ok := events.Next()
	if !ok {
		break
	}
	if event == nil {
		continue
	}
	if event.Err != nil {
		return nil, fmt.Errorf("market agent run failed: %w", event.Err)
	}
	// 原来的 event output 处理
}

if output == "" {
	return nil, errors.New("market agent returned empty output")
}
```

否则所有 Tool 错误都会被伪装成 `invalid decision JSON`。

第五，用确定性 Validator 兜住业务约束，原则是 **LLM 负责判断，Go 负责约束**：

```go
func Validate(v *Context) error {
	if v == nil {
		return errors.New("market context is nil")
	}
	if v.AsOf == "" {
		return errors.New("as_of is required")
	}
	switch v.Regime {
	case RegimeRiskOn, RegimeMixed, RegimeRiskOff:
	default:
		return fmt.Errorf("invalid regime: %s", v.Regime)
	}
	if v.Confidence < 0 || v.Confidence > 1 {
		return fmt.Errorf("confidence out of range: %f", v.Confidence)
	}
	if len(v.Evidence) == 0 {
		return errors.New("evidence is empty")
	}
	return nil
}
```

Validator 只判断「是否合法」，不判断「结论对不对」：`action = WATCH` 是否应改为 `CANDIDATE` 属于 Agent 的研究判断，Go 不介入。边界分层为 `Prompt 约束 → Go 防御性解析 → Validator 业务约束`，三层职责不可互相替代；`strings.Index("{")` 只能作兜底。

## 7. Skill 相关实践

### 7.1 Skill 发现日志

Skill Root 由 Runtime 统一决定，Agent 不参与路径选择。Eino filesystem Skill Backend 只扫描 `BaseDir` 下一级子目录中的 `SKILL.md`。当前仓库的 Skill Root 落在项目根的 `./skills`（早期实现使用 `~/.aegis/skills`），规则只有一份。在 `skillBackend` 创建后立即打印：

```go
skillBackend, err := skill.NewBackendFromFilesystem(ctx, &skill.BackendFromFilesystemConfig{
	Backend: backend,
	BaseDir: root,
})
if err != nil {
	return nil, fmt.Errorf("create skill backend: %w", err)
}

skills, err := skillBackend.List(ctx)
if err != nil {
	return nil, fmt.Errorf("list skills: %w", err)
}

for _, s := range skills {
	log.Printf("[skill:discovered] name=%s description=%s", s.Name, s.Description)
}
```

实际输出：

```text
2026/09/22 15:09:48 [skill:discovered] name=test-script description=用于验证 Aegis 是否能够加载 Skill 并执行 Skill 自带脚本。
2026/09/22 15:09:48 [skill:discovered] name=tushare-data description=面向中文自然语言的 Tushare 数据研究技能。……
```

该日志用于区分两类问题：列表里没有目标 Skill，说明目录 / FrontMatter / Backend 层有问题；列表里有但模型未优先激活，属于模型路由层问题。

### 7.2 最小可执行 Skill：test-script

目录 `skills/test-script/SKILL.md`：

```markdown
---
name: test-script
description: 用于验证 Aegis 是否能够加载 Skill 并执行 Skill 自带脚本。
---

# Test Script

执行当前 Skill 目录下的：

`scripts/hello.py`

使用 python3 运行，并返回脚本输出。
```

`skills/test-script/scripts/hello.py`：

```python
print("hello from aegis skill")
```

Skill Runtime 的 middleware 组合，同一个 `local.Backend` 同时作为文件系统 Backend 与 Shell：

```go
backend, err := local.NewBackend(ctx, &local.Config{})

skillBackend, err := skill.NewBackendFromFilesystem(ctx, &skill.BackendFromFilesystemConfig{
	Backend: backend,
	BaseDir: root,
})

skillMW, err := skill.NewTyped[*schema.AgenticMessage](ctx,
	&skill.TypedConfig[*schema.AgenticMessage]{
		Backend:            skillBackend,
		CustomSystemPrompt: skillRuntimePrompt,
	})

fsMW, err := filesystem.NewTyped[*schema.AgenticMessage](ctx, &filesystem.MiddlewareConfig{
	Backend: backend,
	Shell:   backend, // execute 依赖 Shell

	// 当前 Skill 只需要读取资源和执行脚本。
	WriteFileToolConfig: &filesystem.ToolConfig{Disable: true},
	EditFileToolConfig:  &filesystem.ToolConfig{Disable: true},
})

return []adk.TypedChatModelAgentMiddleware[*schema.AgenticMessage]{
	skillMW,
	fsMW,
}, nil
```

挂到 Agent 上（`adk.TypedChatModelAgentConfig[*schema.AgenticMessage]` 的 `Handlers: middlewares`）。验证链路：

```text
测试一下 test-script skill
    ↓
skill（加载 SKILL.md，并把 Skill BaseDirectory 返回给模型）
    ↓
execute
    ↓
python3 .../skills/test-script/scripts/hello.py
    ↓
hello from aegis skill
```

期望日志 `[tool:start] skill / [tool:end] skill / [tool:start] execute / [tool:end] execute`。验收标准三条：Skill 能被动态发现；Agent 能通过 `skill` 加载对应 `SKILL.md`；Skill 引用 `scripts/` 时，Agent 能通过 `execute` 真正执行并拿到 stdout / stderr。

### 7.3 常见问题

**问题一：Skill 有脚本但无法执行。**

- 现象：Skill 目录存在 `scripts/*.py`，`SKILL.md` 能加载，但脚本从未运行。
- 原因：Skill Middleware 只负责发现 Skill、加载 `SKILL.md`、把 `BaseDirectory` 告知模型，**不会自己执行** `scripts/*.py`。Eino 的 filesystem middleware 虽提供 `execute`，但必须配置 `Shell` 或 `StreamingShell`。只接 Skill Middleware 时，缺的是执行能力，不是 Skill 内容。
- 解决：把 Skill Runtime 补成四块——Skill Middleware（发现 / 加载）、Filesystem（读取 `references` / `scripts`）、Execute（运行脚本）、Skill Installer（安装完整目录并检查依赖），对应 `SKILL.md → instruction`、`scripts/ → executable resources`、`execute → execution capability`。始终由 Agent 决定是否执行，由 Execute Tool 真正执行，不让 Skill Middleware 自动执行脚本。依赖处理遵循「模型决策、execute 执行」：普通运行依赖（包安装、chmod、临时目录）由 Agent 自行安装并重新验证；凭证、账号权限、付费权限、系统权限等无法自行获得的条件才视为外部阻塞。不要引入 `DependencyManager` 之类额外 Runtime 抽象。

**问题二：同一能力出现两套实现导致 Skill 不执行。**

- 现象：`tushare-data` Skill 已加载，随后仍直接调用 `tushareMcp_daily` / `tushareMcp_moneyflow`，未走 Skill 自己的脚本路径。
- 原因：「能力有两套实现」不能直接当作 Skill 不执行的原因；真实原因是三件事叠加：`skill` Tool 的强约束主要写在 Tool description 里，注入 Agent Instruction 的 Skill system prompt 只有「识别 → 加载 → 遵循」，缺少同样强的阻塞语义；旁边 MCP Tool 的名称已足够表意，模型有更直接的捷径；官方 Skill 要求先做本地环境检查（`python` / `tushare` 包 / `TUSHARE_TOKEN`），而 MCP 不需要这一步。
- 解决：在 Skill Middleware 上用 `CustomSystemPrompt` 增加通用 Skill-first 规则，不针对单个 Skill 写特殊规则：

```go
CustomSystemPrompt: func(ctx context.Context, toolName string) string {
	return fmt.Sprintf(`
# Skill Runtime

在执行任务前，先检查可用 Skill 是否与当前任务匹配。

规则：
1. 如果存在明显匹配当前任务的 Skill，必须首先调用 %q 加载该 Skill。
2. 在相关 Skill 加载完成之前，不要直接使用其他领域工具绕过该 Skill。
3. Skill 加载后，按照 Skill 中定义的工作流、前置检查、脚本、参考资料和执行要求完成任务。
4. Skill 可以使用 filesystem、execute 以及其他可用工具完成任务。
5. 不要重复加载已经加载过的 Skill。
`, toolName)
},
```

单独验证 Skill 自身执行路径时，smoke test 只给 Agent：`skill`、`ls`、`read_file`、`glob`、`grep`、`execute`，暂时不注册 `tushareMcp_*` 与 Mock Tool。这是隔离测试条件，不是长期方案：有 MCP 捷径时，模型大概率不会走本地脚本路径。`Skill = 怎么做，MCP / scripts = 用什么能力做`，两者不冲突，但验证阶段必须分开。

**问题三：Skill 安装 / 创建应由模型决策还是人工操作。**

分层处理：

- 普通运行依赖缺失：由模型决策、由 `execute` 执行。把安装步骤甩给人工，等于绕过了正在验证的 Agent 能力。
- 凭证、Token、账号权限、付费权限：模型无法自行获得，不得伪造；只有这类情况才明确说明阻塞原因。
- Skill 本身的安装与创建：`skill_install` / `skill_create` 属于 Skill Lifecycle Management，不属于 Skill Runtime。安装位置必须由 Runtime 控制，不由模型传 `path`；`skill_install` 应复制完整 Skill 目录并校验 `credentials` / `requirements` / `environment_variables` / `network_access`，而不是只复制 `SKILL.md`。

主流 Agent（Pi / Codex / Claude Code）都没有在 Runtime 层硬性保证「Skill 必须先执行」，普遍是「渐进式披露 + 模型自行匹配 + 显式调用兜底」，也没有依赖解析器。Aegis 起步阶段应保持一致，不急于引入 `SkillRouter`，否则「为什么调用这个 Skill」的答案会变成「Router 规定的」，反而绕开最有价值的 Agent Decision 部分。

## 8. Eino API 版本差异的教训

- 现象：接入 Skill Runtime 时引用 `github.com/cloudwego/eino-ext/adk/backend/local`，被判断为「这个包不存在」。
- 原因：该路径确实存在，但它是**独立 Go module**，有自己的模块声明与版本标签（例如 `v0.2.6`），不属于 `github.com/cloudwego/eino-ext` 根 module 下的普通 package。因此 `go get github.com/cloudwego/eino-ext` 不会自然带上它，必须单独 `go get github.com/cloudwego/eino-ext/adk/backend/local`。更根本的问题是判断依据：依赖了对 API 的文档记忆与搜索索引结果，没有先核对当前仓库目录结构与本地 `go.mod` 可解析的依赖。
- 解决：接入任何 Eino 能力前，先核对当前版本的实际 API：看源码目录、看 `go.mod` 版本、确认是否为独立 module，不按旧版示例猜 API。最后核对到的正确 API：

| 能力 | 正确 API |
|---|---|
| MCP Tool 装载 | `officialmcp.GetTools(ctx, &officialmcp.Config{...})`，返回 `[]tool.BaseTool`，可直接放入 `ToolsNodeConfig.Tools` |
| MCP 连接 | `mcpsession.Connect(ctx, mcpsession.ServerConfig{...})`；`session` 包支持 SSE、stdio、Streamable HTTP |
| MCP 断线 | `session.Session` 在连接级错误时重建 session 并重试一次，单 Server 临时断线无需自行实现 reconnect |
| MCP 分页 | `ListToolsMode: officialmcp.ListToolsAllPages` |
| MCP 工具改名 | `officialmcp.ToolNameMapper`，用于 `server_tool` 归一化，避免多 Server 同名冲突 |
| filesystem 执行 | `filesystem.MiddlewareConfig{ Backend, Shell }`，`execute` 必须配置 `Shell` 或 `StreamingShell` 才可用 |
| skill Backend | `skill.NewBackendFromFilesystem(ctx, &skill.BackendFromFilesystemConfig{ Backend, BaseDir })` |
| Skill 激活 | `skill` Tool 激活后会把 `Skill.BaseDirectory` 一并返回给模型，相对路径无需自行处理基准目录 |

已验证的版本组合（`go.mod`）：

```text
github.com/cloudwego/eino                                         v0.9.19
github.com/cloudwego/eino-ext/adk/backend/local                   v0.2.6
github.com/cloudwego/eino-ext/components/model/agenticdeepseek    v0.1.0
github.com/cloudwego/eino-ext/components/tool/mcp/officialmcp     v0.1.1
github.com/cloudwego/eino-ext/devops                              v0.1.9
```

```go
	replacer := strings.NewReplacer("-", "_", ".", "_", ":", "_", "/", "_")
	return replacer.Replace(name)
}
```

### 9.1 确定性单元测试

用实现 `model.BaseModel[*schema.AgenticMessage]` 的 fake model 代替 DeepSeek，其 `Generate` 把预设字符串包成 `AssistantGenText` 返回，`Stream` 直接返回错误以确保测试路径不依赖 streaming：

```go
type fakeModel struct {
	output string
	err    error
}

func (m *fakeModel) Generate(
	_ context.Context,
	_ []*schema.AgenticMessage,
	_ ...model.Option,
) (*schema.AgenticMessage, error) {
	if m.err != nil {
		return nil, m.err
	}
	return &schema.AgenticMessage{
		Role:          schema.AgenticRoleTypeAssistant,
		ContentBlocks: []*schema.ContentBlock{schema.NewContentBlock(&schema.AssistantGenText{Text: m.output})},
	}, nil
}

func (m *fakeModel) Stream(
	_ context.Context,
	_ []*schema.AgenticMessage,
	_ ...model.Option,
) (*schema.StreamReader[*schema.AgenticMessage], error) {
	return nil, errors.New("stream should not be called")
}
```

table-driven 覆盖 Validator 全部分支，断言采用 testify 风格的「首个失败即终止」（等价 `require`），每个 case 独立构造输入，避免 subtest 之间共享状态造成污染：

```go
func TestValidate(t *testing.T) {
	tests := []struct {
		name    string
		input   *Context
		wantErr bool
	}{
		{name: "valid", input: &Context{
			AsOf: "20260922", Regime: RegimeMixed,
			Evidence: []string{"市场存在分化"}, Risk: []string{}, Confidence: 0.72,
		}},
		{name: "nil", input: nil, wantErr: true},
		{name: "missing as_of", input: &Context{
			Regime: RegimeMixed, Evidence: []string{"test"}, Confidence: 0.5,
		}, wantErr: true},
		{name: "invalid regime", input: &Context{
			AsOf: "20260922", Regime: "BULL",
			Evidence: []string{"test"}, Confidence: 0.5,
		}, wantErr: true},
		{name: "confidence too high", input: &Context{
			AsOf: "20260922", Regime: RegimeRiskOff,
			Evidence: []string{"test"}, Confidence: 1.1,
		}, wantErr: true},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			err := Validate(tt.input)
			if tt.wantErr && err == nil {
				t.Fatal("expected error")
			}
			if !tt.wantErr && err != nil {
				t.Fatalf("unexpected error: %v", err)
			}
		})
	}
}
```

配置解析同样用 table-driven 覆盖分支：Agent override 有值 → 用 override；无 override → 用 default；引用不存在的 profile → error；default 不存在或为空 → error。这类测试不花 API 费用，直接跑 `go test ./internal/agent/market -v`。

### 9.2 真实集成测试骨架

用环境变量开关跳过，需要 `DEEPSEEK_API_KEY` 与 `TUSHARE_TOKEN`，设置超时并输出结果便于人工检查。

> **实现状态提示（截至 2026-09-23）**：下面这段是 **Runtime 落地后的目标形态**，不能原样编译。
> 其中 `config.Config` / `ModelConfig` / `ModelProfileForAgent` / `llm.NewManager` / `Manager.Get` / `market.New` **已经实现**；
> 而 `runtime.New(...)` 与 `rt.Handlers()` **尚未实现**（`internal/runtime/runtime.go` 只有 `Config` 与 `Runtime` 两个类型声明）。
> 在 Runtime 实现之前，需要用现有的 `internal/skillruntime.New(ctx)` 取得 handlers：
>
> ```go
> handlers, err := skillruntime.New(ctx)
> // ...
> a, err := market.New(ctx, market.Config{
>     Model:         marketModel,
>     Handlers:      handlers,
>     MaxIterations: 30,
> })
> ```
>
> 按 9.4 的纪律，**测试只应引用已经存在的 API**；把它写成 `rt.Handlers()` 的形态会让测试在实现完成前一直编译失败。

```go
func TestMarketAgent_Analyze_Integration(t *testing.T) {
	if os.Getenv("AEGIS_INTEGRATION") != "1" {
		t.Skip("set AEGIS_INTEGRATION=1 to run integration test")
	}

	requireEnv(t, "DEEPSEEK_API_KEY")
	requireEnv(t, "TUSHARE_TOKEN")

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Minute)
	defer cancel()

	skillsDir := findSkillsDir(t)

	// 1. Market Agent 故意不配置专属模型，必须继承 default_model
	appCfg := config.Config{
		DefaultModel: "default",
		Models: map[string]config.ModelConfig{
			"default": {
				Provider: config.ProviderDeepSeek,
				Model:    envOrDefault("DEEPSEEK_MODEL", "deepseek-chat"),
				APIKey:   "DEEPSEEK_API_KEY",
				BaseURL:  os.Getenv("DEEPSEEK_BASE_URL"),
			},
		},
	}

	// 2. 解析 Agent 的 model profile
	profile, err := appCfg.ModelProfileForAgent("market")
	if err != nil {
		t.Fatalf("resolve market model profile: %v", err)
	}
	if profile != "default" {
		t.Fatalf("market model profile = %q, want %q", profile, "default")
	}

	// 3. 通过 LLM Manager 创建 / 复用模型
	models := llm.NewManager(appCfg.Models)
	marketModel, err := models.Get(ctx, profile)
	if err != nil {
		t.Fatalf("create market model: %v", err)
	}

	// 4. 创建共享 Runtime（Skill + Filesystem / execute）
	rt, err := runtime.New(ctx, runtime.Config{SkillsDir: skillsDir, TimeZone: "Asia/Shanghai"})
	if err != nil {
		t.Fatalf("create runtime: %v", err)
	}

	// 5. 组装 Market Agent
	a, err := New(ctx, Config{Model: marketModel, Handlers: rt.Handlers(), MaxIterations: 30})
	if err != nil {
		t.Fatalf("create market agent: %v", err)
	}

	// 6. 执行真实市场研究
	result, err := a.Analyze(ctx, "分析当前 A 股市场环境。")
	if err != nil {
		t.Fatalf("analyze market: %v", err)
	}

	// 7. 只做基本断言
	if result == nil || result.AsOf == "" || len(result.Evidence) == 0 {
		t.Fatalf("invalid market context: %+v", result)
	}

	// 8. 输出结果便于人工检查
	data, _ := json.MarshalIndent(result, "", "  ")
	t.Logf("market context:\n%s", data)
}

func requireEnv(t *testing.T, name string) string {
	t.Helper()

	value := os.Getenv(name)
	if value == "" {
		t.Skipf("%s is required for integration test", name)
	}
	return value
}
```

Skills 根目录不能假设 `BaseDir: "skills"` 一定可解析，因为测试进程工作目录通常是 package 目录；需支持 `AEGIS_SKILLS_DIR` 覆盖，并向上查找 `go.mod`：

```go
func findSkillsDir(t *testing.T) string {
	t.Helper()

	if dir := os.Getenv("AEGIS_SKILLS_DIR"); dir != "" {
		return dir
	}

	dir, err := os.Getwd()
	if err != nil {
		t.Fatalf("get working directory: %v", err)
	}

	for {
		if _, err := os.Stat(filepath.Join(dir, "go.mod")); err == nil {
			return filepath.Join(dir, "skills")
		}

		parent := filepath.Dir(dir)
		if parent == dir {
			t.Fatal("repository root containing go.mod not found")
		}
		dir = parent
	}
}
```

### 9.3 集成测试的断言原则

只做基本断言，不做不确定的数值断言：

```go
result != nil
result.AsOf != ""
len(result.Evidence) > 0
```

不要断言 `as_of == "20260922"`：当天是否交易日、盘中数据是否完整、数据源更新时间都会变化。`Analyze()` 本身已完成 JSON parse 与结构校验，集成测试的职责是验证「分析当前 A 股市场环境 → Runtime Context → Agent 时间语义理解 → Skill 自行寻找合适数据」这条链，而不是替 Agent 决定 `as_of`。真正要观察的是执行轨迹：

```text
Market Agent → skill("tushare-data") → SKILL.md → 环境检查
  → references / scripts → execute → Tushare API → 市场数据
  → 综合判断 → 结构化 Context → Validate
```

### 9.4 重要纪律

**不要写引用尚未实现 API 的测试。** 曾出现过把「目标架构」直接写成「当前代码」的情况，集成测试引用了当时并不存在的接口：

```text
config.Config / config.ModelConfig / config.ProviderDeepSeek / ModelProfileForAgent()
llm.NewManager() / Manager.Get()
runtime.New() / runtime.Config / Runtime.AgentHandlers()
newTestCallback()
```

这类测试既不能编译，也无法定位真实问题。正确顺序是：当前能工作的集成测试 → 先实现 `internal/runtime` → 测试 runtime → 实现 config 的 model profile → 测试 config → 实现 `internal/llm` 的 DeepSeek 路径 → 测试 llm → 最后再改 Market integration test。

先把能跑的链路跑通，再逐步把 bootstrap 抽出去。每一步只改一小块并验证「原本能跑、改完还能跑」。抽 `internal/runtime` 之前，先在 `market` 包里放临时 bootstrap，把 `main` 中已跑通的 Model + Skill + Filesystem 组合搬过来验证一次；等 Trading Agent 与 Market Agent 出现真实重复依赖，再抽共享 Runtime——抽象来自真实重复，而不是预先设计。

同样，集成测试不应重复初始化底层 Provider 与 middleware：

```go
agenticdeepseek.New(...)          // 属于 internal/llm
local.NewBackend(...)             // 属于 internal/runtime
skill.NewBackendFromFilesystem(...)
skill.NewTyped(...)
filesystem.NewTyped(...)
```

集成测试只应看到「模型配置 → 解析 profile → 创建模型 → 共享 Runtime → Agent → 真实结果」这条业务链路。
