# Aegis 数据能力层：Capability / Binding 与 MCP 运行时

本文档说明 Aegis 如何获取外部数据：为什么数据源不能写死在代码里，Capability / Binding 如何表达「一个能力、多个实现」，数据契约与失败判定如何划分边界，以及 MCP 运行时的结构与职责。范围限于数据获取的抽象与运行时；Agent 判断逻辑、Skill 方法论、Decision 契约不在本文内。

## 1. 问题背景：数据源无法预先确定

A 股研究所需数据的来源在项目早期没有确定答案：可能是 MCP、Skill，也可能是本地数据库或第三方 API，并且可以同时存在。

```text
Aegis
│
├── 本地数据库
│   └── DuckDB / MySQL
│
├── MCP
│   └── 行情 / 财经数据服务
│
├── Skill
│   └── 板块复盘 / 情绪分析 / 选股
│
└── API
    └── Tushare / 其他数据源
```

因此设计约束只有一条：**业务代码不关心数据源是什么，只关心当前需要什么能力。**

```text
MarketData
├── GetMarketOverview()
├── GetStockSnapshot(symbol)
├── GetTechnicalIndicators(symbol)
├── GetCapitalFlow(symbol)
└── GetSectorPerformance()
```

「我要市场概览」这一请求最终由 `DuckDB 查询`、`MCP Call`，还是 `本地数据库 → 数据过期 → MCP → 写回数据库` 完成，上层都不应该知道。

数据库、API、MCP 解决的是「数据从哪里来」，Skill 解决的是「拿到这些能力以后怎么完成任务」，两者不在同一层：

```text
┌───────────────────────────────┐
│          Agent / Skill        │
│  Research / Review / Strategy │
└───────────────┬───────────────┘
                │  Tools
┌───────────────▼───────────────┐
│        Domain Capability      │
│ Market / Stock / News / Flow  │
└───────────────┬───────────────┘
                │
        Data Infrastructure
     ┌──────────┼──────────┐
     ↓          ↓          ↓
   DuckDB      MCP        API
```

因此 Skill 不应被塞成一种 Data Provider：`DatabaseProvider / MCPProvider / SkillProvider` 这种划分不成立，Skill 位于更上层。

MCP 在系统中有两种使用方式，二者可以同时存在：

```text
① 后端确定性调用              ② MCP Tool 直接暴露给 Agent
Graph Node                    Agent
   ↓                            ↓
MarketService                 MCP Tool
   ↓                            ↓
MCP Client → MCP Server       MCP Server
```

前者适合「必须获取」的数据（大盘环境、交易日信息、基础行情），后者适合 Agent 自主追加的数据需求（资金流、板块信息）。

## 2. 早期 Provider 抽象及其不足

第一版抽象是放在 `overview` 包里的一个极窄接口，`Tool` 从持有数据改为持有 Provider：

```go
// OverviewProvider provides market overview data.
type OverviewProvider interface {
	Overview(ctx context.Context) (MarketOverview, error)
}

// StaticProvider provides static market overview data.
type StaticProvider struct {
	Data MarketOverview
}

func (p *StaticProvider) Overview(ctx context.Context) (MarketOverview, error) {
	return p.Data, nil
}
```

```go
type Tool struct {
	Provider OverviewProvider
}

func (t *Tool) InvokableRun(
	ctx context.Context,
	argumentsInJSON string,
	opts ...tool.Option,
) (string, error) {
	overview, err := t.Provider.Overview(ctx)
	if err != nil {
		return "", err
	}
	data, err := json.Marshal(overview)
	if err != nil {
		return "", err
	}
	return string(data), nil
}
```

这一步的价值是建立第一个稳定边界：`Tool` 与未来的 Graph Node 共享同一份数据能力，替换数据源只需替换 Provider 实现。

```text
             OverviewProvider
        ┌───────────┴───────────┐
        ↓                       ↓
StaticProvider             未来真实实现
                    ┌───────────┼───────────┐
                    ↓           ↓           ↓
                  DuckDB       MCP       HTTP API
```

这一阶段**刻意不建**下列类型，理由是没有真实需求支撑，抽象应由真实重复触发：

```text
MCPProvider    DuckDBProvider    TushareProvider
ProviderFactory    ProviderManager
```

同样刻意不做一个万能接口：

```go
type MarketService interface {
	GetOverview()
	GetSnapshot()
	GetKline()
	GetTechnical()
	GetNews()
	GetSector()
	GetCapitalFlow()
	GetNorthbound()
	GetDragonTiger()
	GetLimitUpPool()
	GetSentiment()
	GetTheme()
	// 30 个方法...
}
```

需要多个数据方向时，做法是拆成多个窄接口（`OverviewProvider` / `SnapshotProvider` / `NewsProvider`），而不是合并成一个巨型 Provider。当同一份数据存在多个来源时，`Tool` 也不应该自己管理多个 Provider：

```go
type Tool struct {
	Providers []OverviewProvider // 会把选源、回退、过期、合并、优先级、缓存压进 Tool
}
```

正确边界是：`Tool` 永远只依赖一个接口，组合复杂度隐藏在接口之后。

```text
Agent
  ↓
MarketOverview Tool
  ↓
OverviewProvider
  ↓
CompositeProvider
  ├── DuckDB
  ├── MCP
  └── Tushare
```

`CompositeProvider` / `FallbackProvider` / `AggregatedProvider` 只作为方向记录，未实现。

**不足与结论。** `Provider` 是「单一实现的抽象」：它只能表达「这份数据由一个 Go 类型提供」，无法表达后续被明确提出的三件事——同一能力有多个渠道、单一渠道会失效需要按优先级降级、同一能力可能同时由 MCP 与 Skill 提供。因此 `OverviewProvider` 停止扩展，抽象升级为 Capability / Binding。

## 3. Capability / Binding 模型（核心）

### 3.1 一个能力，N 个实现

```text
market.overview
   ↓
Capability Resolver
   ├── mcp:tushare:market_overview      priority 100
   ├── mcp:eastmoney:market_overview    priority  90
   └── skill:a-share-market-overview    priority  50
```

上层永远只请求能力名，不关心最终是谁执行：

```go
Invoke(ctx, "market.overview", input)
```

最小调用接口：

```go
type CapabilityInvoker interface {
	Invoke(
		ctx context.Context,
		name string,
		input any,
	) (any, error)
}

result, err := invoker.Invoke(ctx, "market.overview", nil)
```

同一机制适用于所有数据方向：

```text
market.snapshot
├── MCP A
├── MCP B
└── Skill A

news.search
├── MCP NewsAPI
├── MCP Eastmoney
└── Skill WebResearch

capital.flow
├── MCP A
└── MCP B
```

### 3.2 Binding 数据结构

核心数据结构是 Binding，不是 Provider：

```go
type CapabilityBinding struct {
	ID         string
	Capability string
	Type       string // mcp | skill | db | builtin
	Priority   int
}
```

同一能力的运行时注册示例：

```text
Capability: market.overview

Binding 1  id = tushare-overview      type = mcp    priority = 100
Binding 2  id = eastmoney-overview    type = mcp    priority = 90
Binding 3  id = market-review-skill   type = skill  priority = 50
```

配置侧只描述「能力由谁提供」，换数据源只改配置，业务代码与 Agent 不变：

```yaml
capabilities:
  market.overview:
    type: mcp
    server: tushare
    tool: market_overview

  news.search:
    type: mcp
    server: finance
    tool: search_news

  market.review:
    type: skill
    name: a-share-market-review
```

### 3.3 优先级降级链

```text
Invoke(ctx, "market.overview", input)
        │
        ▼
  按 priority 取候选 Binding
        │
        ▼
┌────────────────────────────────────────────────┐
│ Binding #1   mcp:tushare:market_overview       │
│                                                │
│   ① 调用是否报错 ──────────────  error ────┐    │
│        │ ok                               │    │
│        ▼                                  │    │
│   ② Adapter 能否转成统一契约 ──── 失败 ────┤    │
│        │ ok                               │    │
│        ▼                                  │    │
│   ③ 契约 Validate 是否通过 ────── 失败 ────┤    │
│        │ ok                               │    │
│        ▼                                  │    │
│      return result                        │    │
└───────────────────────────────────────────┼────┘
                                            │ fallback
┌───────────────────────────────────────────▼────┐
│ Binding #2   mcp:eastmoney:market_overview     │
│ Binding #3   skill:a-share-market-overview     │
│ Binding #N   ...                               │
└───────────────────────────────────────────┬────┘
                                            │ 全部失败
                                            ▼
                              error / Last Known Good
```

### 3.4 同一 Capability 的判定标准

Skill 与 MCP 可以落在同一个 Capability 下，判定标准只有一个：**是否能满足完全相同的输入输出 Contract。**

```text
market.overview   → 获取结构化市场事实
market.review     → 基于数据产生市场分析
```

```text
market.overview
├── MCP Tushare
├── MCP Eastmoney
└── Skill（前提是该 Skill 确实返回相同的结构化 Contract）

market.review
├── Skill A
├── Skill B
└── Agent
```

名字相似但输出形态不同（例如返回自然语言分析而非结构化事实）不属于同一能力，应拆成两个 Capability。

### 3.5 尚未实现的部分

第一版 Capability 机制只计划支持最小集合：

```text
一个 capability
多个 binding
按 priority 顺序尝试
失败 fallback
```

以下能力被明确列为「已设计、未实现」：

```text
health check
circuit breaker
cache / Last Known Good
负载均衡
动态评分
并行 race
```

Last Known Good 用于全部实时实现都失败时返回带时间戳的旧数据，让 Agent 判断数据已过期并降低 confidence：

```json
{
  "data": {},
  "as_of": "2026-09-21T10:55:00+08:00",
  "stale": true
}
```

在交易研究里「旧数据」与「完全没数据」不是一回事。Binding 未来需要逐步具备 `priority` / `enabled` / `timeout` / `health` / `failure_count` / `last_success`，并对连续失败的实现进入 Circuit Open、跳过一段时间后再 Half Open 探测。

> **实现状态**：Capability / Binding / Capability Resolver 在当前代码中**已设计、未实现**；MCP 的动态 Tool 注册由 Eino 承担，因此没有实现自研 `CapabilityRegistry`（见第 7、8 节）。

## 4. 失败判定的完整定义

降级链的第一个判定是「调用有没有报错」，但这远远不够。MCP 可能出现：

```text
HTTP 200
```

却返回：

```text
空数据 / 昨天的数据 / 字段缺失 / 异常价格
```

这些**同样是失败**。因此每个 Capability 必须带一份契约，失败判定有三步：

```text
Invoke market.overview
        ↓
Binding #1  MCP Tushare
        ↓
① 执行成功？
        ↓ yes
② 结果能转换成 MarketOverview？
        ↓ yes
③ MarketOverview.Validate() 通过？
        ↓ yes
      RETURN
```

其中任何一步失败：

```text
↓
next binding
```

判定标准因此是：**能通过 Adapter 转换、且能通过契约 Validate 的结果才算成功**，而不是「没有返回 error」。

## 5. 数据契约流水线

契约是 Adapter 的目标，也是 fallback 的触发条件：

```text
MCP / Skill
    ↓ 原始返回（各渠道字段各不相同）
  Adapter          ← 渠道字段差异在 Adapter 内消化
    ↓
统一契约结构体      ← MarketOverview / IndexSnapshot / SectorPerformance
    ↓
  Validate         ← 只判断结构是否合法
    ↓
成功 / fallback
```

```go
type MarketOverview struct {
	Indexes        []IndexSnapshot     `json:"indexes"`
	AdvanceCount   int                 `json:"advance_count"`
	DeclineCount   int                 `json:"decline_count"`
	LimitUpCount   int                 `json:"limit_up_count"`
	LimitDownCount int                 `json:"limit_down_count"`
	Turnover       float64             `json:"turnover"`
	Sectors        []SectorPerformance `json:"sectors"`
}

type IndexSnapshot struct {
	Name          string  `json:"name"`
	ChangePercent float64 `json:"change_percent"`
}

type SectorPerformance struct {
	Name          string  `json:"name"`
	ChangePercent float64 `json:"change_percent"`
}
```

这一层必须存在，否则动态能力会把整个系统变成 `map[string]any` / `json.RawMessage`，使 Graph、Decision、Backtest 无法维护。

契约中**刻意不放**判断类字段：

```go
MarketRegime string
RiskLevel    string
Sentiment    string
Bullish      bool
```

这些属于判断，不属于原始市场事实。同理，Tool 不应返回：

```json
{ "market_regime": "BULL" }
```

而应只提供事实：

```json
{
  "index_change": 1.82,
  "advance_count": 4210,
  "decline_count": 732,
  "limit_up_count": 85,
  "limit_down_count": 12
}
```

由 Agent 判断「当前市场风险偏好较强」。随着时间语义收紧，市场数据契约在实现中扩展为 `internal/agent/market` 包的 `Context`，在事实字段之外增加 `as_of`、`regime`、`evidence`、`risk`、`confidence`；第 6 节的校验规则即作用于该结构。

## 6. 校验的分寸

`Validate` **只校验「结构是否合法」，不校验「数据是否完整」**：

| 校验 | 不校验（缺失时写入 `risk` 字段） |
|---|---|
| `as_of` 非空 | `Turnover > 0` |
| `regime` 是枚举值之一 | `AdvanceCount > 0` |
| `confidence ∈ [0,1]` | `len(Indexes) > 0` |
| `len(Evidence) > 0` | |

对应的实现形态：

```go
func Validate(v *Context) error {
	if v == nil {
		return errors.New("market context is nil")
	}
	if v.AsOf == "" {
		return errors.New("as_of is required")
	}
	switch v.Regime {
	case RegimeRiskOn, RegimeMixed, RegimeRiskOff:
	default:
		return fmt.Errorf("invalid regime: %s", v.Regime)
	}
	if v.Confidence < 0 || v.Confidence > 1 {
		return fmt.Errorf("confidence out of range: %f", v.Confidence)
	}
	if len(v.Evidence) == 0 {
		return errors.New("evidence is empty")
	}
	return nil
}
```

理由：**拿不到数据应该进入 `risk`，不能逼 Agent 编数据。** 结构性校验失败是 bug，数据缺失是业务事实。二者混同会导致两种坏结果：要么 Agent 为通过校验而编造数值，要么系统在数据缺失时直接崩溃而不是如实报告。

同一原则也适用于 Decision 契约的校验（`symbol` / `market_view` 非空、`action` 属于枚举、`confidence ∈ [0,1]`、`evidence` 非空）。Go 侧判断的是「有没有按协议输出合法结构」，而不是「这个研究结论对不对」：

```text
                 Aegis
          ┌────────┴────────┐
          ↓                 ↓
       LLM Agent          Go
       判断什么？        格式对不对？
       调哪些Tool？      字段是否合法？
       如何解释？        数值是否合法？
          └───────┬─────────┘
                  ↓
             Valid Decision
```

因此 `Validate` 不因更换模型（DeepSeek / Claude / GPT / Gemini）而修改。

## 7. MCP 运行时

MCP 运行时位于 `internal/runtime/mcp`，负责「连接配置中的 MCP Server → 动态发现全部 Tool → 交给 Agent」。它不负责业务等价关系（哪个 MCP 在业务上能替代哪个），那是 Capability Resolver 的问题。

### 7.1 ServerConfig

```go
type ServerConfig struct {
	Name      string            `json:"name"`
	Transport string            `json:"transport"`
	URL       string            `json:"url,omitempty"`
	Command   string            `json:"command,omitempty"`
	Args      []string          `json:"args,omitempty"`
	Env       map[string]string `json:"env,omitempty"`
}
```

| 字段 | 含义 |
|---|---|
| `Name` | Server 唯一名，同时作为 Tool 名前缀用于防重名 |
| `Transport` | 传输类型：`sse` / `stdio` / `streamable-http` |
| `URL` | 网络传输地址，用于 `sse` / `streamable-http` |
| `Command` | stdio 传输启动的进程命令 |
| `Args` | stdio 传输的命令参数 |
| `Env` | 传给子进程的环境变量，用于注入 token 等凭据 |

配置来源可以是多样的：

```text
JSON / YAML / 数据库 / 配置中心 / Web 后台
```

Agent 不关心配置从哪里加载。当前实现为「配置动态」：修改配置后重启生效，**不做热加载**；只有出现不停机增加 MCP 的真实需求后才实现 reload。

```json
[
  {
    "name": "market-primary",
    "transport": "streamable-http",
    "url": "http://127.0.0.1:8081/mcp"
  },
  {
    "name": "market-backup",
    "transport": "streamable-http",
    "url": "http://127.0.0.1:8082/mcp"
  }
]
```

```json
[
  {
    "name": "market",
    "transport": "stdio",
    "command": "python",
    "args": ["./mcp_server.py"]
  }
]
```

当前实现只提供一个很薄的 `LoadConfig(path string) ([]ServerConfig, error)`：读文件 → `json.Unmarshal` 到 `[]ServerConfig`。换成 YAML、数据库或配置中心，只需替换这一个函数，`Connect` 与 Agent 都不受影响。

配置中**不含 Tool 名**。曾短暂设计过 `Tools []string` 白名单（对应 `officialmcp.Config.ToolNameList`），用于只暴露 Server 的部分 Tool（例如隔离 `place_order` 这类高风险能力），最终删除：白名单会提前替 Agent 做能力选择，而「外部有什么能力」不应在 Aegis 代码和配置里提前写死。需要隔离高风险能力时，再加 Agent 级别的 Tool 筛选。

### 7.2 Connect 与 Server

```go
type Server struct {
	name    string
	session *mcpsession.Session
	tools   []tool.BaseTool
}

func Connect(
	ctx context.Context,
	cfg ServerConfig,
) (*Server, error) {
	sess, err := mcpsession.Connect(ctx, mcpsession.ServerConfig{
		Name: cfg.Name,
		Transport: mcpsession.TransportConfig{
			Type:    cfg.Transport,
			URL:     cfg.URL,
			Command: cfg.Command,
			Args:    cfg.Args,
			Env:     cfg.Env,
		},
	})
	if err != nil {
		return nil, fmt.Errorf("connect mcp server %q: %w", cfg.Name, err)
	}

	tools, err := officialmcp.GetTools(ctx, &officialmcp.Config{
		Cli:           sess,
		ServerName:    cfg.Name,
		ListToolsMode: officialmcp.ListToolsAllPages,

		ToolNameMapper: func(
			ctx context.Context,
			input officialmcp.ToolNameMapperInput,
		) (officialmcp.ToolNameMapperOutput, error) {
			return officialmcp.ToolNameMapperOutput{
				ExposedName: normalizeToolName(
					input.ServerName + "_" + input.Tool.Name,
				),
			}, nil
		},
	})
	if err != nil {
		_ = sess.Close()
		return nil, fmt.Errorf(
			"load tools from mcp server %q: %w",
			cfg.Name,
			err,
		)
	}

	return &Server{name: cfg.Name, session: sess, tools: tools}, nil
}

func (s *Server) Tools() []tool.BaseTool { return s.tools }

func (s *Server) Close() error { return s.session.Close() }

func normalizeToolName(name string) string {
	replacer := strings.NewReplacer(
		"-", "_",
		".", "_",
		":", "_",
		"/", "_",
	)
	return replacer.Replace(name)
}
```

职责划分：

- `Connect`：建立 session，通过 `ListTools` 发现全部 Tool，把每个 MCP Tool 映射成 Eino Tool；任一步失败都返回带 Server 名的包装错误，并关闭已建立的 session。
- `Server`：持有 session 与 `[]tool.BaseTool`，对外只暴露 `Tools()` 与 `Close()`。
- `Manager`：批量连接多个 Server，聚合 Tool 与失败信息。

使用 `eino-ext` 的 `officialmcp` 与 `session`，支持 `sse`、`stdio`、`streamable-http` 三种 Transport。`mcpsession.Session` 已提供**连接级自动重连并重试一次**，因此单个 MCP Server 临时断线不需要 Aegis 自己实现 reconnect。**多个 MCP 之间的 fallback 是另一层（Capability Resolver）的问题**，运行时不做。

工具名规范化的必要性：两个 Server 很可能暴露同名 Tool（`tushare` 与 `eastmoney` 都有 `get_stock_quote`）。加 Server 名前缀并规范化分隔符后得到 `tushare_get_stock_quote` / `eastmoney_get_stock_quote`，既不会在 Agent 侧重名冲突，也让后续「同能力多个 MCP」的候选在名字上可区分。

### 7.3 Manager

```go
type Manager struct {
	servers  []*Server
	tools    []tool.BaseTool
	failures map[string]error
}

func ConnectAll(
	ctx context.Context,
	configs []ServerConfig,
) *Manager {
	m := &Manager{failures: make(map[string]error)}
	for _, cfg := range configs {
		server, err := Connect(ctx, cfg)
		if err != nil {
			m.failures[cfg.Name] = err
			continue
		}
		m.servers = append(m.servers, server)
		m.tools = append(m.tools, server.Tools()...)
	}
	return m
}

func (m *Manager) Tools() []tool.BaseTool { return m.tools }

func (m *Manager) Failures() map[string]error { return m.failures }

func (m *Manager) Close() error {
	var errs []error
	for _, server := range m.servers {
		if err := server.Close(); err != nil {
			errs = append(errs, err)
		}
	}
	return errors.Join(errs...)
}
```

`ConnectAll()` 的行为是刻意的：**不因为一个 MCP 连接失败而返回 error，也不让整个 Aegis 启动失败。**

```text
tushare     ✅
eastmoney   ❌  →  Failures: eastmoney → connection refused
news        ✅

最终得到：tushare_xxx / tushare_xxx / news_xxx / news_xxx
```

调用方在启动时打印失败信息即可：

```go
for name, err := range mcpManager.Failures() {
	log.Printf("[mcp:error] server=%s err=%v", name, err)
}
```

```text
configs/mcp.json
       ↓
MCP Manager
   ├── MCP A ✅
   ├── MCP B ❌
   └── MCP C ✅
       ↓
Eino BaseTools
       ↓
Trading Agent
```

## 8. MCP Tool 如何交给 Agent

`officialmcp.GetTools` 返回的就是 `[]tool.BaseTool`，可以直接放进现有的 `ToolsNodeConfig.Tools`：

```go
tools := []tool.BaseTool{
	marketTool,
	technicalTool,
	newsTool,
	overviewTool,
}

tools = append(tools, mcpManager.Tools()...)
```

```go
ToolsConfig: adk.ToolsConfig{
	ToolsNodeConfig: compose.ToolsNodeConfig{
		Tools: tools,
	},
},
```

Agent 侧不需要任何改动：

```text
Trading Agent
      ├── Native Tools（逐步被 MCP 替代）
      └── MCP Dynamic Tools
               ↑
          ListTools()
```

交给 Agent 之前先打印自动发现的 Tool，用于验证链条是否成立：

```go
for _, t := range mcpManager.Tools() {
	info, err := t.Info(ctx)
	if err != nil {
		log.Printf("[mcp:error] read tool info: %v", err)
		continue
	}
	log.Printf("[mcp:tool] name=%s desc=%s", info.Name, info.Desc)
}
```

```text
配置 → MCP Server → ListTools → officialmcp.GetTools
     → []tool.BaseTool → Eino ADK Agent
```

当 Agent 没有调用 MCP Tool 时，排查顺序为：

```text
① 最终传给 Agent 的 tools 里有没有 MCP Tool
        ↓ 有
② MCP Tool 的 name / desc 是否清楚
        ↓ 清楚
③ 用「查询 600519 当前价格」这类只有该 Tool 能回答的问题单独测试
        ↓
④ 看 Callback 是否出现该 MCP Tool
```

Tool 的 `Name` 与 `Description` 直接决定模型能否判断其用途。若 Server 暴露的是 `query` / `query data` 这类名称与描述，模型无法知道它可以查股价。

职责边界：

```text
Runtime 决定：有哪些 MCP Server 可用
Agent   决定：这些 Server 提供的 Tool 现在怎么用
```

Agent 只能决定如何使用已挂载给它的 Tool，不会自行发现任意 MCP Server。当 Server 数量增长到数十、上百个 Tool 时，不应把全部 Tool Schema 塞进模型上下文，此时使用 Eino ADK 的 Dynamic Tool Selection（`adk/middlewares/dynamictool/toolsearch`）按任务检索相关 Tool，再交给 Agent 自主调用。

**当前不做「同能力自动 fallback」。** `market_primary_get_quote` 与 `market_backup_get_quote` 都会暴露给 Agent，选源先由 Agent 与 Skill 承担；只有实践证明不稳定时，才把 fallback 下沉成确定性代码（Capability Resolver）。
