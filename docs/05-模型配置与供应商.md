# Aegis 模型配置与供应商抽象

本文说明 Aegis 如何为不同 Agent 选择与创建 LLM：`Runtime` 与 Model 的边界、`internal/config` 的配置模型与解析规则、`internal/llm` 的 Manager / Factory 形态，以及新增 Provider 需要改动的位置。

> **代码是现状的唯一事实来源**。本文解释「为什么这样定」，并以仓库中已实现的代码为准；设计记录中与实现不一致的形态会被显式标注。

---

## 1. 边界原则：Runtime 不持有 Model

**Runtime 是共享的 Harness 能力，Model 属于每个 Agent 的组装配置。**

`Runtime` 只组装所有 Agent 共用的运行基础设施：Runtime Context、Skill、Filesystem、Execute。它不包含 `Model`，也不包含 `Provider`。模型由 application bootstrap / composition 层创建后注入每个 Agent。

### 1.1 为什么必须这样切

- **一旦 Runtime 持有 Model，就隐含「一个 Runtime = 一个 Model = 所有 Agent 共用一个 Provider」。** 只要 Runtime 上存在 `rt.Model()` 这类入口，模型选择就被固化进共享组件，Market / Trading / Reflection 无法各自选择供应商。
- **模型选择是组装期决策，不是 Harness 能力。** Context / Skill / Filesystem / Execute 对所有 Agent 语义相同、生命周期相同；而「用哪家模型、哪个 model、哪个 API Key」会随配置、成本与效果评估反复调整，属于 Composition。
- **Provider 创建依赖鉴权、BaseURL 与各家能力开关（例如 JSON mode），这些都是组装期信息。** 放进 Runtime 会让共享组件承担 Provider 细节。
- **分离之后 Agent 保持 provider-neutral 与 profile-neutral。** 换模型只改配置，Agent 代码一行不动，Harness 也不需要为「多了一个使用不同模型的 Agent」改结构：

```text
Market Agent      → 便宜快速模型
Trading Agent     → 强推理模型
Reflection Agent  → 更强模型
Evaluator Agent   → 独立模型
```

### 1.2 不放 Runtime，也不做注册表

Provider 创建逻辑独立成 `internal/llm`，不放在 Runtime：

```text
internal/
├── agent/
├── config/
├── llm/        Provider 创建
└── runtime/    Context / Skill / Filesystem / Execute
```

命名为 `internal/llm` 而非 `internal/model`，避免与 `github.com/cloudwego/eino/components/model` 混淆。当前阶段**不做 Provider Registry**：只有一个 `switch`，等真出现第三方动态 Provider 再考虑 registry / plugin。

### 1.3 组装后的依赖关系

```text
                    config.yaml
                        │
        default_model + per-agent override
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
      default         strong         claude
     DeepSeek         OpenAI         Claude
         │              │              │
         ▼              ▼              ▼
   Market Agent   Trading Agent  Reflection Agent
         └──────────────┼──────────────┘
                        ▼
                 Shared Runtime
            Context / Skill / Filesystem / Execute
```

每个 Agent 只接收一个已经确定的 `model.BaseModel[*schema.AgenticMessage]` 与共享的 Runtime handlers：

```go
marketAgent, err := market.New(ctx, market.Config{
	Model:    marketModel,
	Handlers: rt.Handlers(),
})

tradingAgent, err := trading.New(ctx, trading.Config{
	Model:    tradingModel,
	Handlers: rt.Handlers(),
})
```

Agent 不知道这个 Model 是 default 还是 override，也不知道它来自哪家 Provider。

## 2. 配置模型

### 2.1 `Provider` 枚举

```go
type Provider string

const (
	ProviderDeepSeek Provider = "deepseek"
	ProviderOpenAI   Provider = "openai"
	ProviderClaude   Provider = "claude"
	ProviderQwen     Provider = "qwen"
	ProviderGemini   Provider = "gemini"
	ProviderArk      Provider = "ark"
)
```

枚举在配置层先完整列出，让 profile 的 YAML 取值有稳定契约；**枚举中存在不等于已实现**——能否真正创建该 Provider 由 `internal/llm.New` 决定（见第 6 节）。

### 2.2 `ModelConfig`

一个 model profile 就是一份「创建某个模型实例所需的配置」：

```go
type ModelConfig struct {
	Provider Provider `yaml:"provider"`
	Model    string   `yaml:"model"`

	APIKey  string `yaml:"api_key"`
	BaseURL string `yaml:"base_url"`

	MaxTokens *int `yaml:"max_tokens"`
}
```

| 字段 | yaml key | 说明 |
|---|---|---|
| `Provider` | `provider` | 供应商，取值来自 `Provider` 枚举 |
| `Model` | `model` | 该供应商下的模型名，如 `deepseek-chat` |
| `APIKey` | `api_key` | **存放环境变量名，不是密钥本身** |
| `BaseURL` | `base_url` | 可选，覆盖默认 endpoint（代理 / 兼容网关） |
| `MaxTokens` | `max_tokens` | 可选，指针类型；部分 Provider 必填 |

`MaxTokens` 用 `*int` 而非 `int`：`nil` 表示未配置，`0` 表示显式配置了非法值，两者在 Provider 校验中需要区分（例如 Claude 要求 `max_tokens > 0`）。

`ModelConfig` 只放**所有 Provider 的公共字段**；供应商差异不塞进这个结构体，而是留在各自 adapter 内处理。强行做「所有 Provider 参数完全一致」的抽象，会立刻被 Claude 的 `MaxTokens` 这类必填项打破。

### 2.3 `AgentConfig`

```go
type AgentConfig struct {
	Model string `yaml:"model"`
}
```

Agent 侧只有一个字段：它引用的 model profile 名。Agent 配置里**不出现 `provider`**，否则 Agent 就与 Provider 耦合。Agent 引用 profile，profile 再展开为 provider / model / API key / provider options。因此「同一个 Agent 换供应商」只需改 profile 内容，引用关系不变：

```yaml
# 从
market-research: { provider: deepseek, model: deepseek-chat }
# 换成
market-research: { provider: qwen, model: qwen3-... }
```

`agents.market.model` 始终是 `market-research`。

### 2.4 `Config`

```go
type Config struct {
	DefaultModel string `yaml:"default_model"`

	Models map[string]ModelConfig `yaml:"models"`
	Agents map[string]AgentConfig `yaml:"agents"`
}
```

- `DefaultModel`：默认 profile 名，**不是模型名**，而是 `Models` 的 key。它独立成字段而不混在 `Models` 里，是为了让「哪个 profile 是默认」一眼可见。
- `Models`：profile 名 → 模型创建配置。
- `Agents`：Agent 名 → Agent 级覆盖。可以为空甚至为 `nil`，此时所有 Agent 都使用 `default_model`。

### 2.5 约定：`api_key` 是环境变量名

配置文件**不存密钥本身**，只存读取密钥的环境变量名：

```yaml
api_key: DEEPSEEK_API_KEY
```

运行时再解析，这样配置文件可安全提交与分发，密钥只存在于部署环境。`internal/llm/deepseek.go` 的 `apiKey` 负责落地这条约定：

```go
func apiKey(cfg config.ModelConfig) (string, error) {
	if cfg.APIKey == "" {
		return "", errors.New("api_key_env is required")
	}

	value := strings.TrimSpace(os.Getenv(cfg.APIKey))

	if value == "" {
		return "", fmt.Errorf("environment variable %s is not set", cfg.APIKey)
	}

	return value, nil
}
```

两条错误分别对应「没写环境变量名」与「写了名字但环境里没有值」。该函数 Provider 无关，新增 Provider 直接复用。

## 3. default + override 解析规则

### 3.1 规则

```text
Agent 配置了 model（非空）  → 使用该 Agent 指定的 profile
Agent 没配置 model（或整个 agents 段为空） → 使用 default_model

引用不存在的 profile  → error
default_model 为空    → error
```

即 `Default by convention, override by Agent when needed`：最简单的部署只写一个 `default_model` 就能让全部 Agent 运行；需要按 Agent 强化或换供应商时，才补一条 override。

### 3.2 完整实现

`internal/config/config.go`：

```go
func (c *Config) ModelProfileForAgent(agentName string) (string, error) {
	profile := c.DefaultModel

	if agent, ok := c.Agents[agentName]; ok && agent.Model != "" {
		profile = agent.Model
	}

	if profile == "" {
		return "", errors.New("no model profile specified for agent")
	}

	if _, ok := c.Models[profile]; !ok {
		return "", fmt.Errorf(
			"model profile %q not found for agent %q",
			profile,
			agentName,
		)
	}

	return profile, nil
}
```

错误文案：

```text
no model profile specified for agent
model profile %q not found for agent %q
```

第一条覆盖「`default_model` 为空且该 Agent 没有 override」。设计记录中这里曾写作 `default_model is required`，实现采用的是现在的文案。

### 3.3 职责边界：只负责选择 profile

`ModelProfileForAgent(agentName)` 的职责被刻意收窄为**一件事：选出 profile 名**。它**不做**以下事情：

- 不创建任何 model 实例；
- 不检查 `Provider` 是否为空、是否受支持；
- 不检查 `Model` 是否为空；
- 不按 `Provider` 分支做任何判断。

原因是「选择配置」与「创建 Model」是两个职责。**Provider 差异发生在后续创建模型时**（`llm.New` 的 `switch` 与各 adapter 内的必填项校验）；一旦让 resolver 掺入 Provider 判断，换一个供应商就要动配置解析层。

返回 `(string, error)` 而非 `(string, ModelConfig, error)` 也是同一取向：调用方拿到 profile 名后交给 `llm.Manager`，由 Manager 自己从 `Models` 取配置并创建。

## 4. 完整 `config.yaml` 示例

`configs/config.yaml`：

```yaml
default_model: default

models:
  default:
    provider: deepseek
    model: deepseek-chat
    api_key: DEEPSEEK_API_KEY

  strong:
    provider: openai
    model: gpt-5.6
    api_key: OPENAI_API_KEY

  claude:
    provider: claude
    model: claude-sonnet-4-6
    api_key: ANTHROPIC_API_KEY
    max_tokens: 8192

agents:
  trading:
    model: strong

  reflection:
    model: claude
```

### 4.1 `default_model`

```yaml
default_model: default
```

指定默认 profile 为 `default`。凡是 `agents` 段里没有出现、或出现了但没写 `model` 的 Agent，都使用这个 profile。

### 4.2 `models`

三段 profile 各自描述一个可创建的模型实例：

| profile | provider | model | 备注 |
|---|---|---|---|
| `default` | deepseek | `deepseek-chat` | 默认模型，Key 取 `DEEPSEEK_API_KEY` |
| `strong` | openai | `gpt-5.6` | 供需要更强推理的 Agent 覆盖，Key 取 `OPENAI_API_KEY` |
| `claude` | claude | `claude-sonnet-4-6` | 额外提供 `max_tokens: 8192`，因为 Claude 需要该参数 |

`api_key` 三段填的都是**环境变量名**。`claude` 段多出 `max_tokens`，说明 profile 之间字段可以不同：公共字段在 `ModelConfig`，供应商特有参数按需出现在 profile 中，由对应 adapter 消费。

### 4.3 `agents`

```yaml
agents:
  trading:
    model: strong

  reflection:
    model: claude
```

- `trading` → 覆盖为 `strong`（OpenAI / `gpt-5.6`）。
- `reflection` → 覆盖为 `claude`（Claude / `claude-sonnet-4-6`）。
- 其他所有 Agent（如 `market`）**不需要出现在这里**，直接继承 `default_model`。不写 `market: {}` 是刻意的：没有配置就是默认模型，空对象是噪音。

### 4.4 解析结果

| 调用 | 结果 |
|---|---|
| `ModelProfileForAgent("market")` | `default` |
| `ModelProfileForAgent("trading")` | `strong` |
| `ModelProfileForAgent("reflection")` | `claude` |

需要留意：本示例的 `strong` 与 `claude` 分别指向 OpenAI 与 Claude，而当前 `internal/llm.New` 只实现了 DeepSeek（见第 6、8 节）。在第二、第三个 Provider 落地前，这两个 override 会在**创建模型**阶段返回 `unsupported provider` 错误——解析本身是正确的。

## 5. 测试设计

### 5.1 覆盖分支

| # | 场景 | 输入 | 期望 |
|---|---|---|---|
| 1 | Agent 无配置 | `Agents` 为 nil | 用 `default` |
| 2 | Agent 有配置但 `model` 为空 | `Agents{market: {}}` | 用 `default` |
| 3 | Agent 有 model override | `Agents{trading: {strong}}` | 用 `strong` |
| 4 | override 引用的 profile 不存在 | `Agents{trading: {missing}}` | error |
| 5 | `default_model` 为空 | `DefaultModel: ""` | error |
| 6 | `default_model` 指向的 profile 不存在 | `DefaultModel: "missing"` | error |

### 5.2 完整测试代码

### 5.3 为什么必须 table-driven 且每个 case 独立构造输入

- **分支是同一函数上的正交分支。** 六个 case 的差别只在输入形状与期望结果，断言逻辑完全一致。table-driven 让「规则表」直接成为测试代码，新增规则只加一行 case，不必把断言复制六遍。
- **每个 case 自己构造完整的 `Config`，避免 subtest 之间共享状态。** 若所有 subtest 复用同一个外层 `cfg`，再在某个 subtest 里写入 `cfg.Agents["reflection"] = ...`，结果就依赖 subtest 的执行顺序与互相污染：那个 case 想验证「override 引用的 profile 不存在」，却顺带改变了后续 case 的输入。共享可变结构体让失败不可复现，也让「这个 case 到底在测什么」无法从输入直接读出。
- **独立输入让每个 case 可单独运行。** `go test -run 'TestConfig_ModelProfileForAgent/agent_model_overrides_default'` 的语义与全量运行完全一致。
- **不依赖全局变量或 `TestMain` 造共享配置。** 表内每个 `cfg` 都是字面量，测试无赋值副作用，天然可并发。

### 5.4 为什么测试里不出现具体 Provider 的差异

`ModelProfileForAgent` 只负责选 profile，所以它的测试**不能**掺入「`strong` 是 OpenAI」这类事实。因此 case 3 的 `strong` profile 仍使用 `ProviderDeepSeek`（只是换成 `deepseek-reasoner`），测试只关心「profile 名被选中了没有」。

如果测试断言了 `Provider == openai`，等价于要求 resolver 承担 Provider 职责——而 Provider 的正确性属于 `internal/llm`：那里应有独立测试覆盖「支持的 Provider 能被创建」与「不支持的 Provider 返回错误」，例如：

```go
func TestNew_UnsupportedProvider(t *testing.T) {
	_, err := New(
		context.Background(),
		config.ModelConfig{Provider: "unknown", Model: "x"},
	)

	if err == nil {
		t.Fatal("expected error")
	}
}
```

三层测试职责因此保持清晰：

```text
config 测试    → default / override 选择
llm 测试       → Provider → Model 创建
agent 集成测试 → 默认模型 + Runtime + Agent 全链路
```

集成测试同样不应验证 override：它要证明的是「Agent 不配专属模型也能跑通」，因此配置里**故意不写 `Agents`**，并断言 `ModelProfileForAgent("market") == "default"`。

### 5.5 与当前仓库实现的差异

`internal/config/config_test.go` 目前仍是较早的形态：四个 `t.Run` 子测试共享同一个外层 `cfg`，其中 `unknown override model` 一个 case 会写入 `cfg.Agents["reflection"]`；只覆盖 4 个分支，缺少「Agent 有配置但 `model` 为空」与「`default_model` 指向的 profile 不存在」。**本节表格与 5.2 的 table-driven 版本是指定的测试设计**，该文件尚未迁移到这一形态。文件中 `strong` profile 的 `Provider` 写作 `"openai"`，也属于 5.4 描述的 Provider 差异混入。

## 6. Provider 中立

### 6.1 Agent 面对的抽象

所有 Agent 只依赖 Eino 的 agentic model 接口：

```go
model.BaseModel[*schema.AgenticMessage]
```

这意味着：**当前 Aegis 接受支持 Eino Agentic Model 接口的 Provider。** Agent 的 Prompt、契约解析与 Validate 都建立在该接口之上，因此 Agent 层完全不感知 Provider。不为兼容 `*schema.Message` 而把 Agent 泛型化，因为当前没有这个需求。

### 6.2 `llm.Manager`

`Manager` 不是 Provider Registry，它只做一件事：**按 profile 创建一次模型实例并复用**。

```go
type Manager struct {
	mu sync.Mutex

	configs map[string]config.ModelConfig
	models  map[string]model.BaseModel[*schema.AgenticMessage]
}

func NewManager(configs map[string]config.ModelConfig) *Manager {
	return &Manager{
		configs: configs,
		models:  make(map[string]model.BaseModel[*schema.AgenticMessage]),
	}
}

func (m *Manager) Get(ctx context.Context, profile string) (model.BaseModel[*schema.AgenticMessage], error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	if existing, ok := m.models[profile]; ok {
		return existing, nil
	}

	cfg, ok := m.configs[profile]
	if !ok {
		return nil, fmt.Errorf("model profile %q not found", profile)
	}

	instance, err := New(ctx, cfg)

	if err != nil {
		return nil, fmt.Errorf("failed to create model,%s: %w", profile, err)
	}

	m.models[profile] = instance

	return instance, nil
}
```

要点：

- `NewManager(cfg.Models)` 接收整张 profile 表；`Get(ctx, profile)` 按名字惰性创建并缓存，`mu` 保证并发安全。
- 多个 Agent 共用 `default` profile 时只创建**一个** DeepSeek 实例，而不是每个 Agent 各建一个 Client：

```text
default profile → 一个 Model instance → Market / Sector / News Agent 共用
```

- 前提是 Eino 的具体 model 实现本身支持并发使用，这也是模型实例最自然的生命周期。
- 错误文案：`model profile %q not found`、`failed to create model,%s: %w`（后者为当前实现中的原始格式，含一个逗号）。

### 6.3 `llm.New`：唯一的 Provider 分支点

`New` 与 `Manager` 同在 `internal/llm/manager.go`：

```go
func New(ctx context.Context, cfg config.ModelConfig) (model.BaseModel[*schema.AgenticMessage], error) {
	switch cfg.Provider {
	case config.ProviderDeepSeek:
		return newDeepSeek(ctx, cfg)
	default:
		return nil, fmt.Errorf("unsupported provider: %q", cfg.Provider)
	}
}
```

- 这是全仓库唯一按 Provider 分支的位置。
- 设计记录中该分支曾覆盖六个 Provider、错误文案写作 `unsupported model provider: %s`；当前实现只落地 DeepSeek，文案为 `unsupported provider: %q`。
- 用 `switch` 而非 registry：多 Provider 是真实需求，动态插件 Provider 不是。

### 6.4 DeepSeek 的创建路径

```go
func newDeepSeek(
	ctx context.Context,
	cfg config.ModelConfig,
) (
	model.BaseModel[*schema.AgenticMessage],
	error,
) {
	apiKey, err := apiKey(cfg)
	if err != nil {
		return nil, err
	}

	return agenticdeepseek.New(
		ctx,
		&agenticdeepseek.Config{
			APIKey:  apiKey,
			BaseURL: cfg.BaseURL,
			Model:   cfg.Model,

			ResponseFormatType: agenticdeepseek.ResponseFormatTypeJSONObject,
		},
	)
}
```

流程为：profile → `apiKey(cfg)` 从环境变量取值 → `agenticdeepseek.New` → `model.BaseModel[*schema.AgenticMessage]`。`BaseURL` 与 `Model` 直接透传 profile 字段。

`ResponseFormatTypeJSONObject` 属于 **Provider capability**，不是 Agent capability：

```text
Agent Contract                 → provider-neutral
（Prompt + JSON parse + Validate）

Structured Output Optimization → provider-specific
（DeepSeek JSON Mode / OpenAI Structured Output / 各家对应能力）
```

Agent 只声明「我要输出符合 Context contract 的结果」，并通过 Prompt、JSON parse、Validate 保证契约；「用哪个 Provider 的哪种结构化输出机制」写在 adapter 里。当前 JSON Mode 先固定开启以保持既有行为不变；「哪些 Agent 需要 structured output」后续再从 profile / Agent capability 上表达。

## 7. 新增 Provider 的步骤

以接入 OpenAI / Claude 为例，按现有代码结构的改动点如下。

**1. 确认依赖。** `go.mod` 目前只引入 `agenticdeepseek`；新增 Provider 需加入对应的 Eino agentic 组件依赖（设计记录称 Eino 的 agentic 路径已提供 `agenticopenai` / `agenticclaude` / `agenticqwen` / `agenticgemini` / `agenticark`，本仓库尚未逐一引入）。

**2. 在 `internal/llm/` 下新增 adapter 文件**，命名与 Provider 对齐：

```text
internal/llm/
├── manager.go      Manager + New（Factory）
├── deepseek.go     已实现
├── openai.go       待实现
└── claude.go       待实现
```

**3. 每个 adapter 提供一个签名统一的 `newXxx(ctx, cfg)`**：

```go
func newOpenAI(
	ctx context.Context,
	cfg config.ModelConfig,
) (
	model.BaseModel[*schema.AgenticMessage],
	error,
) {
	apiKey, err := apiKey(cfg)
	if err != nil {
		return nil, err
	}

	return agenticopenai.NewChatModel(
		ctx,
		&agenticopenai.ChatConfig{
			APIKey:  apiKey,
			BaseURL: cfg.BaseURL,
			Model:   cfg.Model,
		},
	)
}
```

复用第 2.5 节的 `apiKey(cfg)`，Provider 无关的密钥解析不重复实现。

**4. 供应商特有参数在各自 adapter 内校验**，不要为统一而抹平差异。例如 Claude 的配置要求 `MaxTokens > 0`：

```go
if cfg.MaxTokens == nil || *cfg.MaxTokens <= 0 {
	return nil, errors.New("claude model requires max_tokens")
}
```

对应的 `MaxTokens` 由使用者写在 profile 里（见 `configs/config.yaml` 的 `claude` 段）。

**5. 在 `llm.New` 的 `switch` 中加 case**，其他 case 不动：

```go
case config.ProviderOpenAI:
	return newOpenAI(ctx, cfg)

case config.ProviderClaude:
	return newClaude(ctx, cfg)
```

**6. 补测试。** `internal/llm` 侧覆盖「支持 / 不支持的 Provider 创建」；`internal/config` 侧不需要任何改动——`Provider` 枚举已完整列出，`ModelProfileForAgent` 也不感知 Provider。

**7. 不需要做的事。** 不建 ProviderRegistry / ProviderFactoryRegistry / CapabilityRegistry / DynamicProviderLoader；不改 `internal/config` 的解析规则；不改任何 Agent 代码。

### 7.1 验证方式：不同 Agent 使用不同供应商

Provider 落地后，用一条 override 验证「不同 Agent 用不同供应商」：

```yaml
agents:
  trading:
    model: strong
```

其中 `strong` 指向另一个 Provider（例如 OpenAI）。然后断言：

```text
ModelProfileForAgent("trading") == "strong"
Market 没有 override → default → DeepSeek
Trading 有 override  → strong  → 另一个 Provider
```

两条链路都能创建出模型实例并组装进各自的 Agent，即证明 per-agent 多供应商成立。关键点是 **Agent 代码一行都不用改**：变化全部发生在配置与 `internal/llm` 的 adapter 之后。
