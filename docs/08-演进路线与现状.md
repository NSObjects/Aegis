# Aegis 的演进路线与当前状态

本文档说明 Aegis 从 V1 到 V5 的能力生长路线、各阶段要验证的问题、长期目标（可自成长的 Harness），并给出截至 2026-09-23 的仓库实现状态快照，最后列出推进顺序与已知欠账。

本文档的**状态部分以仓库实际代码为唯一事实来源**；与早期设计记录不一致之处，在文中单独标注差异。

## 1. 总体演进路线

Aegis 不做一次性的大设计，而是让能力逐层生长。每一层都必须是一个**可运行、可验证的闭环**，验证通过后再长出下一层。

```text
V1  验证 Agent 基础架构
    agent / tool / context / decision
    理解问题 → 判断需要什么信息 → 调 Tool → 综合 → Decision → 输出

V2  接真实数据源，验证「外部能力可动态挂载」
    + market / strategy
    MCP 动态发现 Tool；Market Agent 产出结构化 MarketContext

V3  策略与候选
    + candidate / research
    市场状态决定策略，策略决定候选池，研究 Agent 负责解释候选

V4  风控与验证分离
    + risk / backtest
    Agent 负责判断，Backtest Engine 负责验证判断

V5  经验沉淀
    + memory / reflection
    真实结果回流，形成可复用的交易记忆
```

### 1.1 让目录结构本身成为演进的记录

演进策略中有一条硬约束：**不提前铺空目录**。

早期就明确禁止预先创建 `internal/strategy`、`internal/risk`、`internal/portfolio`、`internal/memory`、`internal/reflection`、`internal/debate`、`internal/research`、`internal/backtest`、`internal/candidate`。这些目录大概率会出现，但提前建出来只会得到「空目录 + 预设架构」。

目录随能力一起长：

```text
V1  agent   tool   context   decision

        ↓ 增加能力 = 增加目录

V2  + market     + strategy
V3  + candidate  + research
V4  + risk       + backtest
V5  + memory     + reflection
```

于是目录结构本身就是项目演进的记录：看仓库能看到「能力长到哪一步」，而不是看到一份半年后才会用到的架构草图。

配套的两条组织原则：

- **每个 Agent 在自己的包内完成组装与测试**，共享能力等出现真实重复再抽，不提前抽象；
- **`main` 只作为入口做编排**，Agent 数量与能力变化不应迫使入口层大改。

## 2. V1：验证 Agent 基础架构

### 2.1 V1 的目标

V1 不是完整的选股系统，只验证一个问题：

> Agent Runtime 能否稳定完成「理解问题 → 调用工具 → 综合信息 → 输出结构化判断」。

### 2.2 目标闭环

```text
研究请求
   ↓
Trading Agent（Eino ADK Agent）
   ↓
判断需要什么信息
   ↓
调用 Tool
   ↓
获得结果
   ↓
继续判断 / 再调用 Tool
   ↓
形成 Decision
   ↓
输出
```

关键点：Agent 自己决定「什么时候需要什么数据」，而不是固定调用 A、B、C。Agent 内部的 Tool Loop 交给 ADK，**V1 不引入复杂 Graph**；Agent 自己能完成的事情，不为了「用了 Graph」而强行拆成 Graph。

### 2.3 三个核心件

| 核心件 | 职责 |
|---|---|
| **Context** | 告诉 Agent：标的、分析时间、市场基本上下文、本次分析要求。后续所有交易 Agent 都围绕它工作 |
| **Tools** | 提供 Agent 无法直接知道、但可通过系统获得的信息；换数据源时 Agent 不需要重写 |
| **Decision** | 最终产出结构化的判断，而不是一段自由文本；Decision 是后续 Strategy / Risk / Backtest / Memory 消费的对象 |

Decision 的结构：

```text
MarketView   当前市场 / 短线状态判断
Evidence     支持判断的主要证据
Risk         当前主要风险
Action       当前建议状态
Confidence   置信度（0～1）
```

**V1 的 Action 不做 Buy / Sell，只做观察类取值**（`WATCH` / `AVOID` / `CANDIDATE`）。目的是先验证 Agent 的分析链路，避免一上来就把「交易决策」与「Agent 架构」耦死。

### 2.4 V1 工具集

- `MarketSnapshot`：价格、涨跌幅、成交额等市场快照；
- `TechnicalIndicators`：MA / RSI / MACD 等技术指标；
- `News`：个股相关新闻、公告与事件。

工具的重点不是数量，而是验证「Agent 能不能根据当前信息主动决定取哪些数据」，以及「Tool 返回的数据能不能真正改变推理」。

### 2.5 V1 不做清单

```text
Market Regime / Strategy Selection / Candidate Pool / Bull-Bear Debate /
Risk Debate / Multi-Agent / Supervisor / Memory / Reflection / Checkpoint /
Backtest / 自动交易
```

不是这些能力没用，而是 V1 没有必要证明它们能工作。

### 2.6 V1 验收标准

- Agent 能自己选择 Tool，而不是固定调用顺序；
- Tool 数据能真正影响推理（没有新闻时不编造新闻）；
- Agent 能识别并说明信息冲突（例如技术面强、新闻面弱），而不是机械拼接；
- Decision 能稳定输出结构化结果，而不是不可解析的作文；
- **Runtime 是否值得继续扩展**——这是最重要的验收项。若 ADK + Context + Tools 组合别扭，应先解决基础问题，而不是继续加 Bull/Bear、Risk Agent。

## 3. V2 及其子里程碑

### 3.1 V2：接真实数据源，验证「外部能力可动态挂载」

V2 的核心问题不是「接哪个行情源」，而是验证：

> 业务代码只定义「要完成什么任务」和「结果长什么样」；外部数据具体从哪里拿，由运行时挂载的 MCP / Skill 决定。

由此定下能力归属：**MCP = 外部能力 / 数据访问（数据怎么拿）；Skill = 方法论 / Workflow / Knowledge（任务怎么研究）**。Agent 代码里不出现数据源分支，Graph 只认识业务角色（MarketAgent / StrategyAgent / ResearchAgent / RiskAgent），不认识 Tushare / Eastmoney / NewsAPI。

V2 的实现刻度：

```text
V2.1  单 Agent + Mock Eino Tools                          ✅
V2.2  接入 MCP：动态配置 → 自动发现 Tool → 交给 Agent
V2.3  接入 Skill Middleware，建立第一个 market-review Skill
V2.4  Market Agent 输出结构化 MarketContext
V2.5  Graph：MarketAgent → TradingAgent
```

到 V2.5 才第一次形成完整链路：

```text
外部动态数据
      ↓
     MCP
      ↓
 Market Agent
      ↑
    Skill
      ↓
MarketContext
      ↓
    Graph
      ↓
 Trading Agent
```

### 3.2 V2.2：MCP Server 动态配置 → 自动发现 Tool → 交给 Eino Agent

要验证的行为：

```text
配置 MCP Server
      ↓
动态连接
      ↓
自动发现全部 Tools
      ↓
合并后交给现有 Trading Agent
```

- **不做 Tool 白名单**：不预先声明「这个 Server 只允许暴露哪几个 Tool」，发现即接入；
- **不引入自研 Registry**：MCP 侧使用 Eino 官方的 MCP 工具接入能力；单个 Server 的断线重连由连接层承担，多 Server 之间的业务等价与降级是后面另一层问题；
- **不改 Agent**：MCP Tool 与原生 Tool 在 Agent 看来都是 Tool，由 Agent 自己决定调用哪一个；
- 通过标准：Agent 能自主选择动态发现的 MCP Tool 完成研究，并能识别 MCP 实时数据与本地 Mock 指标之间的冲突。

V2.2 收尾时确认的后续方向是结构化输出契约（Decision schema repair）与外部数据 freshness 意识。

### 3.3 V2.4：Market Agent → MarketContext

Market Agent 只负责市场层面的研究，输出**结构化 MarketContext**，不负责个股分析、不给个股建议、不输出 CANDIDATE / WATCH / AVOID、不选买卖点。

MarketContext 契约：

```text
as_of            实际用于判断的数据日期（YYYYMMDD）
regime           RISK_ON | MIXED | RISK_OFF
indexes          主要指数表现
advance_count    上涨家数
decline_count    下跌家数
limit_up_count   涨停数
limit_down_count 跌停数
turnover         成交额
leading_sectors  强势板块
evidence         证据 string[]
risk             风险 string[]
confidence       置信度 0～1
```

两条配套约束：

- **结构合法性与数据完整性分离**。`Validate` 只校验结构（`as_of` 非空、`regime` 是枚举值、`confidence ∈ [0,1]`、`evidence` 非空）；拿不到数据属于业务事实，写进 `risk`，不能逼 Agent 编数据；
- **时间语义由语义决定，不由测试决定**。先确定本次研究的目标时间，有时间属性的数据尽量使用一致的时间基准；当前交易日数据不完整时使用最近一个数据完整的交易日；`as_of` 填实际用于判断的数据日期，不是请求时间；不得把明显过期的数据当成当前市场状态。

### 3.4 V2.5：Market Agent → Trading Agent

V2.5 开始引入编排：整体市场环境先由 Market Agent 产出，再交给 Trading Agent 作为个股研究的背景。

```text
MarketAgent
     ↓
MarketContext
     ↓
TradingAgent
```

编排原则是：**Graph 只管「什么时候做什么」，Agent 只管「面对当前信息怎么判断」**。流程确定的地方用 Graph，自主判断的地方用 ADK，不把全流程 Graph 化。

## 4. 长期目标：可自成长的 Harness

Aegis 的核心不是「写死几个 Agent」，而是做一个能让 Agent 持续演化的 Harness：能把真实执行结果变成下一版 Agent / Skill / Strategy 的输入。

```text
Execution  ──→  Outcome  ──→  Reflection  ──→  Proposal
                                                   │
                                                   ↓
        新的 Agent / Skill / Strategy 版本  ←──  Promotion  ←──  Evaluation
                                                   │
                                                   └──→（回到 Execution）
```

- **Execution → Outcome**：按当前版本的 Agent / Skill / Strategy 产出结构化 Decision，再由真实市场运行给出可核对的结果；
- **Outcome → Reflection**：结合当时的 Decision 与依据，说明判断为何成立或失效、哪一部分被验证、哪一部分被削弱、下一次应学什么；
- **Reflection → Proposal → Evaluation**：把结论转成对 Prompt / Skill / Strategy / Agent 组成的修改提案，并用历史样本评估提案是否真的更好；
- **Evaluation → Promotion**：通过的提案成为新的可版本化能力，进入下一轮 Execution。

### 实现上遵守的三条原则

1. **Agent 只是 Composition**。每个 Agent 只是当前版本的 Agent Definition / Composition，不把 Runtime 能力写死进 Agent；Agent 数量与组成可以变。
2. **Prompt / Skill / Strategy / Memory / 输出契约可替换、可版本化**。这些是 Harness 的「可进化表面」，必须能独立替换而不牵动其它部分。
3. **`main` / Graph 只做编排**。入口层与编排层不承载 Agent 自身逻辑，能力变化不应迫使入口层大改。

配套边界：**Runtime 是共享的 Harness 能力，不持有 Model**。Model 属于每个 Agent 的组装配置，这样 Market / Trading / Reflection 才能各选各的供应商。

### 5.3 与早期设计记录的差异

核对仓库后，以下几点与早期设计记录不一致，**以仓库为准**：

1. 早期记录称 `internal/runtime/{runtime,context,skill,filesystem}.go` 全部是「空壳，仅 `package` 声明」。实际只有 `context.go`、`skill.go`、`filesystem.go` 是空壳；`runtime.go` 已声明 `Config` 与 `Runtime` 两个类型（但没有构造函数与对外方法），`time_context.go` 已完整实现。
2. 当前真正在使用的 Skill 运行时是 `internal/skillruntime/runtime.go`，不是 `internal/runtime/skill.go`。`internal/runtime` 的目标是把它吸收进来，改为由 `Config{SkillsDir, TimeZone}` 注入。
3. 早期记录称 Market integration test「仍带临时 bootstrap，等待接入 `rt.Handlers()`」。实际工作区的测试体已被整段注释，只保留 helper，链路当前处于「已停用」而非「仍在运行」。
4. 设计中的 `Handlers()` 与 `AgentHandlers()` 命名之争已收敛为 `Handlers()`（Runtime 本来就是给 Agent 使用的）；`runtime.go` 中的字段名也叫 `handlers`，与之保持一致。
5. `internal/config` 的密钥字段名是 `APIKey`（yaml: `api_key`），而设计文本中使用的是 `APIKeyEnv`（yaml: `api_key_env`）；`internal/llm/deepseek.go` 的报错文案仍是 `api_key_env is required`，属改名残留。

## 6. 推进顺序

当前进度正好停在「Runtime 类型已定义、实现未写」这一步。下一步的推进顺序为**严格增量**，每一步都必须保持「原本能跑 → 抽完仍然能跑」：

```text
第 1 步  实现 internal/runtime
         对外只暴露：
             runtime.New(ctx, runtime.Config{SkillsDir, TimeZone})
             rt.Handlers()
         现有 DeepSeek 初始化一行都不动

第 2 步  把 Market integration test 里已经工作的 bootstrap 搬到 Runtime
         测试体只改这一小块，其余不动
         验证：链路没断

第 3 步  实现 config 的 model profile
         default_model + per-agent override，并为 Resolver 补独立测试

第 4 步  实现 internal/llm 的 DeepSeek 路径
         Manager.Get 按 profile 创建并复用实例；Provider 创建逻辑不在 Runtime

第 5 步  最后才改 Market integration test
         换成 default_model → Manager → Market Agent → rt.Handlers() 的最终形态
```

三条约束必须同时遵守：

- **不把目标架构当成当前代码**。测试中不得直接引用尚未实现的 API；每一步只引用该步已经落地的接口；
- **一次只动一小块**。抽 Runtime 时不顺手改 config、llm、Agent；
- **测试去适配语义，不是语义适配测试**。集成测试不硬断言 `as_of` 等于某一天，只断言结果非空、`as_of` 非空、`evidence` 非空。

第 1 步的最小实现范围（只做到这两件事，不发明额外接口）：

```go
rt, err := runtime.New(ctx, runtime.Config{
    SkillsDir: skillsDir,
    TimeZone:  "Asia/Shanghai",
})

handlers := rt.Handlers()
```

`runtime.New` 的职责是把 `internal/skillruntime` 现有的 skill middleware + filesystem middleware 装配逻辑收进来，并把 `./skills` 的硬编码替换为 `Config.SkillsDir`。
