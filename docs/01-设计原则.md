# Aegis 设计原则

本文定义 Aegis 的项目定位、TradingAgents 与 Eino 的使用边界、Graph 与 ADK 的分工，以及 V1 的目标、范围与增量实现纪律。
文中结论都是当前生效的约束；尚未落地的能力只在"演进"语境下出现，不代表已经实现。
技术术语保留英文原词（Agent / Runner / Middleware / Graph / ADK / Tool / State / Harness）。

## 1. 项目定位：交易研究 Agent

**Aegis 是一个交易研究 Agent，不是一个交易执行系统。** 这条边界是项目的第一约束，后续取舍都由它推导：

- 做的是**研究**，职责链路固定为：**判断需要哪些信息 → 获取 → 综合 → 输出结构化判断**
- 做的是 **A 股短线场景**，不是美股基本面流水线的移植
- 最终产出是**结构化判断**，既不是自由文本，也不是下单指令

### 1.1 职责链路

```text
任务输入 → 理解问题 → 判断需要哪些信息 → 调用 Tool 获取
        → 继续判断 / 再调用 Tool → 综合 → 结构化 Decision
```

关键点在"判断需要哪些信息"：Agent 必须自己决定调用什么、按什么顺序调用，而不是由外层固定调用 A → B → C。固定调用序列只能验证函数拼接，验证不了 Agent。

### 1.2 职责边界

Agent 负责研究、推理和判断，不负责数据采集、数据计算、数据存储、回测、下单。Tool 的职责是**把 Agent 无法直接知道、但可以通过系统获得的信息提供给它**；外部能力属于 Tool / Data Layer，Agent 只消费结果。

Agent 侧只应出现能力名，不出现渠道名：

```text
Agent
 ├── get_market_state()      ├── get_stock_quotes()
 ├── get_sector_flow()       ├── get_limit_up_pool()
 ├── get_news()              ├── get_dragon_tiger()
 └── get_policy_news()
```

Agent 不应该知道东方财富 HTTP API、Tushare API、同花顺接口或某个 MCP Server。实时数据通过 MCP / Skills 获取，不自建大量 crawler。这样更换数据源时 Agent 层不需要重写。

### 1.3 Decision 是系统的真实接口

最终结果不能让 LLM 输出一篇分析文章，必须先收敛为明确的 Decision：

```text
Decision = MarketView（短线偏强）
         + Evidence（20MA 向上 / 成交量放大 / 板块活跃 / 有政策催化）
         + Risk（短期涨幅较大 / 需观察次日承接）
         + Action（WATCH） + Confidence
```

Decision 是后续 Strategy / Risk / Backtest / Memory / Portfolio 继续消费的对象，因此必须结构稳定、可解析。

## 2. TradingAgents 的定位：架构研究对象

**TradingAgents 只作为架构研究对象，用于研究"多 Agent 怎么协作"。** 它不是技术栈参考，也不是可以直接改造为 A 股系统的方案。

### 2.1 研究对象是什么

TradingAgents 的表现形式是一组 Analyst + Bull/Bear Researcher + Trader + Risk + Portfolio Manager，但本质更接近 `State Machine + LLM Decision Nodes + Tool Execution + Conditional Loops`，而不是"一堆 Agent 自己聊天"——真正控制执行的是 Conditional Logic，不是 Agent 本身。它由六类机制组成，这六类机制才是研究对象：

```text
① Agent 负责智能判断          ② Tool 获取外部事实         ③ State 保存研究上下文
④ Graph 控制执行流程          ⑤ Conditional Logic 控制 Loop / Routing / Stop
⑥ Memory / Reflection 把历史结果变成未来上下文
```

整体上它更接近**模拟一家投研机构**，因此值得借鉴的是机制形态，而不是它的 Agent 名单与 Python 实现。

### 2.2 为什么不能直接搬

Aegis 的场景约束是：A 股 / 短线 / 1～2 周 / 板块启动 / 龙头·连板·趋势股 / 市场情绪 / 资金 / 新闻·政策 / 技术形态 / 实时信息 / 策略随市场状态切换。把 `基本面 Analyst → 技术 Analyst → 情绪 Analyst → 新闻 Analyst → Bull/Bear → Trader` 这条流水线直接搬过来，会留下一个结构性缺口：

> **Agent 会非常努力地分析一只股票，但不一定知道"现在到底该不该做这类交易"。**

原因是 TradingAgents 没有把"市场环境"提升为整个系统的第一层决策，而 A 股短线必须这么做。Aegis 的第一问是"现在是什么市场？这个市场适合什么打法？"，而不是"这只股票怎么样？"。两者的目标也不同：TradingAgents 追求一份高质量的股票分析报告，Aegis 追求根据当前市场状态选择策略、再寻找符合策略的短线机会。

### 2.3 值得吸收的机制

- **Agent Role 的职责隔离**：每个 Agent 有自己的输入、工具、分析任务、输出与上下文，不做"Agent 1 / Agent 2"式切分
- **Debate**：让不同角色真正质疑已有研究结果，而不是让 LLM 把"看涨 / 看跌"简单综合；Debate 应由 Decision Agent 发现 Evidence 冲突时触发，而不是每只股票固定跑满若干轮
- **Decision Engine**：Aegis 要超过它的地方——先判断市场环境允许什么策略，再判断个股是否满足策略，最后才判断是否执行
- **Data / Tool 与 Agent 的边界**：数据访问契约与 point-in-time correctness，渠道细节不进 Agent
- **Backtest 与 Agent 分离**：Agent 负责判断，Backtest Engine 负责验证判断

### 2.4 机制映射

| TradingAgents | Eino | Aegis |
|---|---|---|
| Analyst + Analyst Tool | ADK Agent + Eino Tool | 研究 Agent 及其数据 Tool |
| Analyst → Tool Loop | ADK Agent Loop | Agent 自主补数据 |
| Bull / Bear Researcher | ADK Agent | 多空研究 Agent |
| Debate Loop + Conditional Logic | Graph + Conditional Edge | 受控辩论循环 / 路由 / 退出 |
| Research Manager | Supervisor / Host / Agent | 研究协调 Agent |
| Trader / Portfolio Manager | ADK Agent + Domain Logic | 交易决策 / 仓位决策 |
| Risk Manager | ADK Agent + Domain Logic | 风控 Agent |
| Memory / Checkpoint | Eino Memory / Checkpoint | 交易历史 / 长任务恢复 |
| Signal Processing | —— | Go deterministic logic |
| Backtest | **不属于 Eino** | 独立回测引擎 |
| Market Regime / Strategy Selection | —— | **Aegis 业务核心** |

末三行是 Aegis 必须自己定义的部分：信号解析用确定性逻辑，回测是独立引擎，市场环境与策略选择是业务核心。

## 3. Eino 的定位：Agent 运行基础设施

**Eino 是 Agent 运行基础设施（Agent Runtime / Agent Development Foundation），不是业务架构。** 它提供"Agent 怎么运行"，不提供"交易怎么做"。

### 3.1 三层职责

| 层 | 归属 | 内容 |
|---|---|---|
| Agent 运行基础 | **Eino** | Agent 接口、Runner、ReAct、Tool、Callback、Middleware、Interrupt / Checkpoint、MCP、Skill、Filesystem |
| Agent 组装与编排 | **Aegis** | 有哪些 Agent、各自用什么模型 / Skill / 工具、怎么调度 |
| 交易领域 | **Aegis** | 市场环境、策略、候选、研究、决策、风控——**不能交给 Eino 定义** |

结论：**不要自己造 Agent Runtime**，除非确认 Eino 的抽象真的不够。

### 3.2 分层图

```text
┌──────────────────────────────────────────────┐
│              Trading Application             │
│  Market Regime   Strategy     Candidate      │
│  Signal          Decision     Risk           │
│  Position        Backtest                    │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│        Trading Agent Runtime（Aegis）         │
│  Trading Session   Trading Context           │
│  Agent Registry    Research Context          │
│  Decision Context  Agent Collaboration       │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│                    Eino                      │
│  ADK          Agent          Tool            │
│  Runner       Memory         Callback        │
│  Supervisor   Host           Handoff         │
│  Graph        Workflow       Interrupt       │
│  Checkpoint   Resume         Middleware      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
   LLM / Market Data / News / Policy / Technical
   Sentiment / Capital Flow / MCP / Skills
```

依赖方向自下而上：业务定义领域状态与角色 → Runtime 组装 Agent → Eino 承担运行机制 → 最底层是模型与数据。

### 3.3 Agent 是业务角色，Graph 是执行机制

**Agent 是业务角色，Graph 是执行机制，不能反过来设计。** 错误方向是从 Eino 概念出发推导业务：先决定"要用 Graph"，再把交易流程塞进节点；正确方向是先定义业务角色与领域状态，再决定每个角色由 ADK Agent 还是 Graph 承载。

领域状态属于 Aegis，不能交给 Eino 定义，且应按语义拆分而不是维护一个超级大 struct：

```text
TradingContext
├── MarketState      ├── ResearchState
├── StrategyState    ├── DecisionState
├── CandidateState   ├── RiskState
                     └── ExecutionState
```

这样扩展到不同市场（A 股 / 美股 / Crypto / 期货）时，不会把整个 Agent 拖成一团。

## 4. Graph 与 ADK 的分工

**流程确定的地方用 Graph，Agent 自主判断的地方用 ADK。**

| 场景 | 使用 |
|---|---|
| 固定流程 | Graph |
| 智能判断 | ADK Agent |
| 工具调用 | Tool |
| Agent 自己决定下一步需要什么工具 | ADK Agent Loop |
| 多 Agent 自由协作 | Supervisor / Host |

两条互补的职责描述：**Graph 不负责"思考"**，它负责"什么时候做什么"（阶段、顺序、路由）；**Agent 不负责"流程"**，它负责"面对当前信息应该怎么判断"。即：ADK 管 Agent，Graph 管流程；Graph 管"阶段"，ADK 管"智能行为"。

### 4.1 不要把整条交易链路全 Graph 化

把 `Market → Strategy → Candidate → Research → Debate → Decision → Risk` 做成一张大 Graph 是**太死了**。更合理的形态是让 Agent 承担智能行为，只在阶段边界上使用 Graph：

```text
Trading Agent ── ADK ──→ Decision Agent
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
          Research       Strategy       Risk
            Agent         Agent        Agent
              └─────────────┼─────────────┘
                            ▼
                  Tools → Market Data / News
```

Graph 承担的是稳定的阶段边界：`Market State → Strategy Selector → Candidate Selector → Research Agent → Decision Agent → Risk Agent`。Research Agent 内部**不要写死**顺序，而应给它自主选择能力：

```text
Research Agent
      ├── technical_tool      ├── sentiment_tool
      ├── news_tool           └── specialist_agents
      └── capital_flow_tool
```

反向也成立：**一个确定性的 Graph / Workflow 可以直接成为 Agent 的 Tool**（GraphTool / Agent Tool），不必把 Agent 展开成 Graph。

### 4.2 循环类流程的处理

对"固定参与者 + 有状态循环 + 最大轮数 + 条件退出"这类流程（例如多空辩论），使用 `Graph（Bull Agent → Bear Agent → Conditional Edge）`，而不是 `Supervisor Agent → 让 LLM 决定 Bull / Bear`。判断依据：**不要让 LLM 决定一个程序已经知道的事情。** 只有真正需要自由协作时，才引入 Supervisor / Host。

## 5. 不包一层 `internal/eino/`

禁止创建 `internal/eino/agent/`、`internal/eino/graph/`、`internal/eino/tool/` 这类目录。理由：

- Eino 是基础设施，不是业务领域；包一层会把实现细节提升为领域词汇
- 代码名词应该表达 `Trading Agent` / `Trading Context` / `Market Tool` / `Decision`，而不是 `Eino Agent` / `Eino Graph`
- 一旦在目录上固化，Eino 的升级或替换会变成跨层重构，并反向诱导"Eino 概念直接映射为业务概念"

Eino 只应出现在实现内部：业务层写 `Trading Agent` / `Trading Context` / `Decision` / `Market Tools`，Eino 侧提供 `ADK` / `Compose` / `Graph` / `Runner` / `Tool`。

## 6. V1 目标与范围

V1 定死在**验证 Agent 基础架构**，先不碰复杂交易逻辑。

### 6.1 目标

V1 不是完整选股系统，只验证一件事：

> **Eino ADK 能不能作为 Trading Agent 的 Agent Runtime，并稳定完成"理解问题 → 调用工具 → 综合信息 → 输出结构化判断"。**

V1 是实验平台，不是"简化版最终系统"。它验证"Eino 能不能承载目标 Agent 架构"：可以就往上长，某个地方别扭就先改基础。

### 6.2 三个核心构件

```text
① TradingContext   股票 / 分析时间 / 市场基本上下文 / 分析目标
② Tools            MarketSnapshot / TechnicalIndicators / News
③ Decision         MarketView / Evidence / Risk / Action / Confidence（见 §1.3）
```

Tools 的重点不是数量，而是验证 Agent 能否主动决定"什么时候需要什么数据"：

```text
输入：分析 XXX
Agent：先看价格与成交量 → MarketSnapshot；发现放量上涨 → TechnicalIndicators
       发现今日重大政策新闻 → News；综合判断 → Decision
```

### 6.3 V1 的 Graph

V1 不需要复杂 Graph，Agent 内部的 Tool Loop 交给 Eino ADK：

```text
START → Trading Agent（Tool Loop: MarketSnapshot / TechnicalIndicators / News）
      → Decision Validation → END
```

原则：**ADK 负责智能行为，Graph 负责以后需要显式编排的流程。** Agent 自己能完成的事情，不要为了"用了 Graph"而强行拆成 Graph。

### 6.4 V1 不做清单

```text
❌ Market Regime        ❌ Risk Debate       ❌ Checkpoint
❌ Strategy Selection   ❌ Multi-Agent       ❌ Backtest
❌ Candidate Pool       ❌ Supervisor        ❌ 自动交易
❌ Bull / Bear Debate   ❌ Memory / Reflection
```

这些能力并非没有价值，而是**当前没有必要证明它们能工作**。

### 6.5 Action 不做 Buy / Sell

V1 的 Action 只取 WATCH 一类观察值，不设计 Buy / Sell。理由：先验证 Agent 的分析链路，避免一开始就把"交易决策"和"Agent 架构"耦死。Action 一旦包含下单语义，Decision 结构、校验规则与后续 Risk 层都会被一起锁死，V1 就无法只作为架构实验。

### 6.6 验收标准

| 验收项 | 判定 |
|---|---|
| Agent 能不能自己选择 Tool | 不是固定调用 A、B、C |
| Tool 数据能不能真正影响推理 | 没有新闻时 Agent 不应凭空编造新闻 |
| Agent 能不能处理信息冲突 | 技术面强、新闻面弱时应意识到冲突，而不是机械拼接 |
| Decision 能不能稳定输出 | 不同输入都收敛到可解析的结构化 Decision，而不是不可解析的作文 |
| 整个 Runtime 是否值得继续扩展 | **V1 最重要的验收标准** |

最后一项的判据：多次运行后若 `Eino ADK + TradingContext + Tools` 好用就继续加架构；若 Agent Loop、状态管理、Tool 管理很别扭，应先解决基础问题，而不是继续增加 Bull / Bear、Risk Agent。

## 7. 目录演进策略

### 7.1 V1 初始目录

```text
aegis/
├── AGENTS.md   README.md   go.mod
├── cmd/aegis/main.go
├── internal/
│   ├── agent/trading/agent.go
│   ├── context/trading.go
│   ├── tool/{market,technical,news}/
│   └── decision/decision.go
└── docs/architecture.md
```

每个目录只解决一个问题：`cmd/` 程序怎么启动；`agent/` Agent 怎么思考、怎么调用 Tool；`context/` 一次交易研究需要携带什么上下文；`tool/` Agent 能获得什么外部能力；`decision/` Agent 最终产出的结构化判断；`docs/` 架构和设计决策。

### 7.2 不提前铺空目录

**禁止**预先创建这些目录：

```text
internal/strategy  internal/risk       internal/portfolio
internal/memory    internal/reflection internal/debate
internal/research  internal/backtest   internal/candidate
internal/market
```

它们以后大概率会出现，但现在建出来只会得到"空目录 + 预设架构"。

### 7.3 目录本身应该成为项目演进的记录

```text
V1  agent  tool  context  decision
V2  + market  + strategy
V3  + candidate  + research
V4  + risk  + backtest
V5  + memory  + reflection
```

目录随能力增长而生长，而不是先按最终形态铺满再往里填代码。

## 8. 包组织原则

### 8.1 每个 Agent 自己组装、自己测试

**每个 Agent 都在自己的包内完成组装与测试；`main` 只作为入口，最后负责调度。** 具体形态是 `internal/agent/<name>/` 内并置 `agent.go`、`context.go`、`prompt.go`、`validator.go`、`agent_test.go`、`integration_test.go`。共享能力（Runtime）先不抽，**等出现真实的重复再抽**。

### 8.2 main 只负责编排

`main` / Graph 只负责编排，不承载 Agent 自身逻辑——**Agent 数量与能力变化不应迫使入口层大改**。长期目标是可自成长的 Harness，因此每个 Agent 只是当前版本的 **Agent Definition / Composition**，不把 Runtime 能力写死进去；Prompt、Skill、Strategy、Memory、输出契约保持**可替换、可版本化**。

模型选择属于每个 Agent 的组装配置，因此 Runtime 不持有 Model，Runtime 只是共享的 Harness 能力，不同 Agent 可选不同供应商：

```yaml
default_model: default
models:
  default: { provider: deepseek, model: deepseek-chat, api_key: DEEPSEEK_API_KEY }
  strong:  { provider: openai,   model: gpt-5.6,      api_key: OPENAI_API_KEY }
agents:
  trading:    { model: strong }
  reflection: { model: claude }
```

解析规则：Agent 有 override 用 override，没有就用 `default_model`；引用不存在的 profile 或 `default_model` 为空则报错。`ModelProfileForAgent(agentName)` 只负责选 profile，不关心 Provider 差异。

### 8.3 Runtime 的边界

```go
rt, err := runtime.New(ctx, runtime.Config{
    SkillsDir: skillsDir,
    TimeZone:  "Asia/Shanghai",
})
handlers := rt.Handlers()
```

两点约束：方法名用 `Handlers()` 而不是 `AgentHandlers()`——Runtime 本来就是给 Agent 使用的，不必多一个词；Runtime 不持有 Model。Runtime 自身按职责切分：

```text
internal/runtime/
├── runtime.go       组装入口，对外只暴露 New + Handlers
├── context.go       运行时上下文注入（时间、目录约定）
├── skill.go         Skill Middleware 装配
├── filesystem.go    Filesystem + Shell 装配
├── time_context.go  TimeZone → 注入"现在是什么时候"
└── mcp/             MCP Server 配置加载 / 连接 / 工具聚合
```

## 9. 增量实现纪律

| # | 纪律 | 依据 / 后果 |
|---|---|---|
| 1 | **先跑通、后收紧** | Skill 先只接 Middleware + Execute，不做安装与创建；过早收紧能力集只会拖慢闭环验证 |
| 2 | **不提前抽象** | 不建空目录；`OverviewProvider` 只保留 1 个方法；Runtime 等重复出现再抽——抽象一旦提前出现，就会反过来定义还不存在的需求 |
| 3 | **一次只动一小块，验证没坏** | "原本能跑 → 只抽 Runtime → 仍然能跑"；每一步都要有可运行的基线 |
| 4 | **不把目标架构写成当前代码** | 目标架构中的 `runtime.New()` / `llm.NewManager()` / `config.ModelProfileForAgent()` 曾被直接写进测试并回退；引用未实现 API 的测试会把设计债伪装成进度 |
| 5 | **测试去适配语义，不是语义适配测试** | `as_of` 必须填实际用于判断的数据日期，不由 mock 决定；语义被测试带偏会让整个系统的数据基准失准 |

配套的节奏约束：**先让 Aegis 跑起来，再让 Aegis 变聪明**，不要反过来。大体方案确定后按架构逐步迭代，而不是继续往实现细节里钻。

## 10. 版本演进主线

```text
V1 单 Agent + Tool → V2 Graph + Market Context → V3 Market Regime → Strategy Selection
V4 Candidate Selection → V5 Research Agents → V6 Debate / Review → V7 Risk + Trade Plan
V8 Backtest → V9 Reflection + Memory → V10 完整 Trading Agent
```

两条不变的要求：**每一阶段都必须是可运行、可验证的闭环**；下一步只由真实运行结果决定，而不是先设计 30 个 Agent、100 个 Tool，再补 Memory / Debate / Backtest。
